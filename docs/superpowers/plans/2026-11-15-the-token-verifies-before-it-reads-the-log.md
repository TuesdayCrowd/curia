`TokenEndpoint.IssueAsync` hands the assertion to `ClientAssertionValidator.ValidateAsync` (`src/Curia.Api/Issuer/TokenEndpoint.cs:127-129`), which resolves the key at `ClientAssertionValidator.cs:95` and only then checks the algorithm (`:102`), the signature (`:108`), the claims (`:111-139`) and consumes the `jti` (`:144`). The resolver the endpoint injects is `LogBoundAgentKeyResolver` (`src/Curia.Api/Adapters/LogBoundAgentKeyResolver.cs:16-25`, registered at `src/Curia.Api/Program.cs:141`), which calls `LogBoundKeys.ResolveAsync`, which is `ResolveLiveAsync` (`src/Curia.Application/Credentials/LogBoundKeys.cs:91-93`): the store's lookup (`:109`) **and then a read of the whole log and a verified fold** (`:112`, `ReadAsync` at `:197-211`, `ReadAllAsync` at `:203`). So every token request that names a registered `kid`, signed or not, costs a whole-log read **before** its signature is looked at, and a fault of that read leaves the assertion unspent. ULG18 (d) (`tests/Curia.Api.Tests/StoreFaultTokenTests.cs:113-142`) pins the consequence: after a fault at that read, **the same assertion with a proof from another key answers `200`**, a token for the victim's identity bound to the captor's key. The fix is an order: **look the key up in the store, verify, check the claims, consume the `jti`s, and only then read the log to bind the key.** The log read after consumption makes a fault there spend the assertion, and a request whose assertion does not verify reads nothing.

## The design

1. **The order is the requirement; the type carries only what it can.** Nothing makes `IssueAsync` call `RequireBoundAsync` after `ConsumeAsync` and before the standings read except probes: `IlCallSites` returns the calls of a body and not their order (`tests/Curia.Architecture.Tests/EmbedderFenceTests.cs:12`; trap 277). VBR1 to VBR3 carry the endpoint's order, VBR7 carries the seam (the adapter reads nothing). Recorded as non-property (e).
2. **The port keeps its name and shape; its adapter and remarks change.** Renaming `IAgentKeyResolver` would touch `InMemoryAgentKeyResolver`, `RecordingAgentKeyResolver`, `ClientAssertionScenario`, `ClientAssertionValidatorTests` and `PostgresAgentKeyStoreTests` and buys a name; VBR7 is the check that the adapter cannot grow the log read back. If Task 2 finds the rename smaller than counted, it may do it and says so.
3. **Both `jti`s are spent before the log is read.** One rule for every log fault after the assertion verifies (the binding read and the standings read), the rule R5.23 already states for the second. The alternative (spend the assertion only) leaves the proof's state to a probe of its own and a sentence nobody asked for. Cost: a client retries with a new proof as well as a new assertion, which the reference client already does and R5.23 already requires.
4. **A key store fault precedes consumption and spends neither** (the key row is not the log; `FaultableKeyStore`, `tests/Shared/FaultableStore.cs:474-505`): unchanged, and now **said** (R5.23 (rev.)) and probed (VBR4).
5. **A bad signature under a never-bound kid is now a bad signature.** Today it is `NotBoundByTheLog` (the binding is checked first); after, `SignatureInvalid`. The answer is the same byte for byte (R5.12: `OAuthRefusal` serves a fixed description; `src/Curia.Api/Issuer/OAuthRefusal.cs:29`, logs the slug only, `:54-56`); the operator's log slug differs. An assertion that verifies under a stored-but-unbound key now consumes its `jti` and is then refused as not bound. Accepted: only the key's holder can cause it. Recorded as non-property (f).
6. **No wire change, no new refusal, no new word.** VBR5 and the existing token suites are the evidence. No cold read (ruling 9).
7. **No new conformance vector.** `conformance/` holds frozen formats and retrieval numbers; this PR changes neither, and the Rust verifier does not model the token endpoint. R14.6's differential gate is untouched (same wire), expected green and recorded.
8. **A stale answer from a read that preceded an append is not in scope.** The window this PR closes is the **fault-widened replay**; it does not stop first-use-wins (non-property (c)).
9. **No cold read, by measurement of its own precondition:** no word a person reads changes (no help text, no refusal description, no banner, no member). The reason goes in the PR body so its absence is a decision.

## G72 — The token endpoint verifies before it reads the log: an assertion is checked under the key the store holds and consumed, and only then is the log read to bind the key, so a request that does not verify reads nothing and a fault of the log spends the assertion

**Location.** R5.20 (the key an assertion is verified under), R5.14 (the `jti` replay cache), R5.23 and R5.24 (a store fault at the token endpoint; the one read of the whole log), R4.35 (a key is honoured only if the log binds it), R5.12 (a refusal's description is fixed); register item 282; PR N's review (N-F-M3, N-F-L1; ULG18 (d)).

**How it surfaced.** PR N made the key's binding a whole-log read and left it where the key's resolution always was, ahead of the signature. Its review found the consequence by reading: a fault at that read leaves the assertion unspent, and the same assertion presented with a proof from another key answers `200`. ULG18 (d) pinned it as today's behaviour so that the lead was a decision and not a drift. Task 0 of this entry's PR measured it on the unmodified tree (the Status below).

**Class.** A resolver that does two jobs in one call (look a key up; vouch for it against the log) placed before verification, so that the second job, which costs a read, is made for every caller that names a registered `kid` and not only for one who proves it holds the key, and whose fault leaves the credential reusable. Each half was correct and tested; the order was nobody's requirement.

### The finding

The token endpoint resolved the assertion's key through `LogBoundKeys`, which asks the store and then reads and folds the whole log, and only then checked the algorithm, the signature, the claims and the `jti`. (1) A caller who names a registered `kid` (the key set publishes them) and signs with nothing caused a whole-log read. (2) A fault of that read, answered `503 temporarily_unavailable` (R5.23), left the assertion's `jti` unspent, so a party that held only the assertion could present it again, signed over by a DPoP proof of its own key, and obtain a token for the victim's identity bound to the captor's key, for as long as the assertion lived; the fault lengthened that window by its own duration. Measured on the unmodified tree (Task 0, twice, over a real application role with `SELECT` on `events` revoked for one request): the first presentation answered `503`; the same assertion with a captor's proof answered `200` with a token whose `cnf.jkt` was the captor's key; and the victim's own next presentation of that assertion answered `401`, spent by the captor's use.

### Decisions this entry makes

(the four rulings of the plan that belong in the record: the store's lookup comes first and the binding read after both `jti`s are consumed; both `jti`s are spent by a fault of the log and neither by a fault of the key store; a bad signature under a never-bound `kid` is answered as a bad signature, with the same fixed description; the wire does not change.)

### Requirement text

**R5.25** The token endpoint SHALL verify a client assertion's signature under the key the Registrar's key store holds for the agent and the `kid` (R5.20), check its claims (R5.1), and consume its `jti` (R5.14) and then the DPoP proof's, **before** it reads the event log; it SHALL then read the log, and only then, to bind the key (R4.35, R5.24: the honoured binding holds exactly the bytes the assertion was verified under, and the key is live) and to read the agent's standing. A request whose assertion does not verify, whose claims are not accepted or whose `jti` is spent SHALL read nothing of the log. A key the log does not bind, or no longer holds live, SHALL still be refused `invalid_client` (R5.20, R5.24), and the assertion that verified under it is spent. The reason: a read made before the signature is checked is a read any caller can cause by naming a registered `kid`, and a fault of it that left the assertion unspent let a captured assertion be presented again with a proof from another key; checking first removes the unauthenticated read and the replay together.

**R5.23 (rev.)** *(the middle sentence only; the rest stands as G68 left it)* Replace "A fault of the read that resolves the key (R5.24) precedes the consumption of the client assertion's and the proof's `jti` and spends neither; a fault of a store the request touches after it (the read of the agent's standing) follows it and spends both." with: "A fault of the key store's own lookup precedes the consumption of the client assertion's and the proof's `jti` and spends neither; a fault of a read of the log (the read that binds the key, R5.25, and the read of the agent's standing) follows it and spends both." The reason: the key's binding is read after the assertion verifies, so a fault of it can no longer leave a verified assertion reusable.

**R5.24 (add.)** At the token endpoint the read of R5.24 is made after the assertion's consumption (R5.25), and a log that cannot be read at it answers `503` `temporarily_unavailable` with the assertion spent.

### Non-properties (stated so that no later reading takes them for guarantees)

(a) The key store's lookup, which precedes verification, is a read of one table and not of the log; a request that names a registered `kid` still causes it. (b) A request whose assertion verified still reads the whole log twice (the binding, the standings), and every enrolled agent holds a key that can cause both; the cost of an anonymous or near-anonymous whole-log read is not removed, only its pre-verification form (register item 314). (c) **First use wins.** A captured assertion presented by the captor before the victim's own request obtains the token; R5.25 closes the window a *fault* widened (the assertion unspent after a failed read), not the capture of an assertion in flight, which the assertion's 60-second lifetime (R5.1) and the transport bound. (d) A request whose assertion is spent never consumes its proof. (e) The endpoint's order is carried by probes and the adapter's half by a fence; a new caller that reads the log before it verifies compiles. (f) A bad signature under a `kid` the log never bound is logged as `curia/authn/signature-invalid` and not `curia/keys/not-bound-by-the-log`; the answer is unchanged byte for byte (R5.12); so is a stored row whose bytes cannot verify the assertion (a raw-bytes row, a P-384 key under `ES256`), which the endpoint used to refuse as not bound before it looked at the signature. An assertion that verifies under a stored key the log does not bind is consumed before it is refused. (g) Ingest still resolves an author's key (the store, then the log) before it verifies the envelope's signature (R6.2, R6.56); it is behind a token and the stream version it reads is the one its append is conditioned on. Not changed, and not re-examined by this entry.
