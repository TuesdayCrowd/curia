## What this is

The Forum can now say what its name is (G82), but nothing a person could follow takes it from a clean box to an announced instance, and nothing checks that a deployment is the one the documents describe. This stage writes that down **where a probe can fail it**: every command in a runbook is read against the tool that runs it, every configuration file is parsed against the rule it exists to carry, and a readiness script calls the live Forum and says, per check, PASS, FAIL or NOT CHECKED. The failure mode this repository has shipped is a correct document nobody could follow (the `Curia:Issuer` fallback, `AllowedHosts`, a runbook whose command named a verb that no longer existed): so the pack is held by artifacts it does not derive from (the operator's `--help`, the source's variable names, the white paper's R-text, a real Forum on a real socket).

**Not in scope:** any Forum, client, operator or MCP source change (a stage that needs one stops and files an item); `.github/` (the owner's merge: see Ruling 5); `db/` (the owner applies db/0002 and db/0006 on the hosted database; this stage only writes the check that they are applied); item 278 (the hosting read cost, next stage); the guard's lift; item 293. `curia-mcp` stays 0.12.8.

## Rulings (decided, not asked)

1. **The edge owns the limits; the Forum builds none.** G82 deliberately reads no forwarded header, so the Forum cannot key a per-client limit without reintroducing exactly the trust G82 removed (R5.26: no forwarded header for any name). A Forum-side per-IP limiter is therefore not a missing feature but a refused design. A Forum-side *global* concurrency cap on the nonce route is a different lever and is a lead (item 397 (b)), not this stage.
2. **A per-address limit is a cost bound, not an abuse control.** Sybil economics, checked as the vacuity test asks: a fleet spreads across addresses at zero marginal cost, and one honest operator behind one NAT pays the full price. So the recipe's numbers are sized to the honest case with room (many agents behind one address must not be throttled in ordinary use), are labelled **provisional and not an abuse control**, and the runbook says the control that bounds abuse is possession plus the owner's attestation (G79 non-property (a), (i)), not this. The stage does **not** claim item 371 closed as "abuse bounded"; it closes the gate as "an edge exists and is shown to answer 429".
3. **The numbers are measured, not picked.** Task 0 measures per-call cost of `GET /v1/enroll/nonce` against a local Postgres (the first call of an epoch is two statements, a later call adds a `SELECT`: read from code, never measured) and the honest rate from the reference client (`curia enrol` fetches the nonce once and retries once; `curia` fetches a token per session with one DPoP-nonce challenge). The recipe's burst and rate are set from those two numbers and the measured cost at the proposed ceiling, and the plan's table says so. A number with no measurement beside it is a restatement.
4. **Requirement text is kept to what a probe can fail.** R7.33 (edge SHALL limit the two unauthenticated routes before the Forum; the Forum SHALL NOT key any limit on a forwarded header) and R11.110 (a readiness report SHALL give each check as PASS, FAIL or NOT CHECKED, exit 0 only if every check PASSed, and SHALL NOT report a check it could not run as passed) are the two. If Task 1's argument shows either is only a recipe note, it goes in the runbook and the number is not taken.
5. **No `.github/` change.** The readiness probes run as xUnit tests that start a real Forum and call the script with `python3` (the project's pattern: `tests/Shared/TestSigner.cs` runs a real signer in another process and fails, never skips, without `python3`), so they ride the existing legs and `api-legs.py check` accounts for them. A new CI step would be the owner's merge; the stage avoids needing one and says so in the PR body. The script's own falsifier (`tools/deploy/falsify-readiness.py`) is run by preflight's list only if `ci.yml` already runs it: it does not, so it is a developer gate named in the plan and **a lead for a ci.yml line** (item 397 (c)), never added here.
6. **One proxy recipe, exercised; another only if the owner asks.** An unexercised configuration file is a restatement. See Owner question 1.

## The readiness script: checks, outcomes, and the probe for each

`readiness.py --origin <https://name> [--declaration-kid K] [--operator-kid K] [--log-kid K] [--probe-limits] [--db-admin-url U] [--app-role R] [--max-head-age S] [--allow-http]`. Every check returns **PASS**, **FAIL** or **NOT CHECKED** with a reason that names no secret and echoes no response body. **Exit 0** only if all PASS; **1** if any FAIL; **8** if none FAIL and any NOT CHECKED (the project's "could not be checked" code). R11.110's rule, and vacuity question 3: a check that did not run must not look like one that passed; a probe asserts exit 8 and the reason when its input is missing, not exit 0.

# Rulings on the nine points

## P1. Finding 9: no body cap in the Forum

**What I read.**
- **R6.39** (white paper line 1614): "ADMIT's four size-shaped limits", the submission size 1 MiB, measured over the document ADMIT is asked to admit. It is a limit on what ADMIT **admits**, and says nothing about what the host **reads to find out**.
- **R10.68** (errata, the rationale cap, line ~7676) says in terms that the check "bounds what is screened and stored, **not the request body, which the host's own limit bounds**". So the project already wrote a requirement that delegates the body bound to a limit it never set.
- **R11.33** requires every route to answer a body it cannot read with a 4xx **problem document**, never a 5xx. **ULG50** (`StoreFaultEdgeTests.cs`) records that the host answers an oversized body `413` "as it answers it on a healthy store" and the middleware writes nothing. `ThrowOnBadRequest = false` (`Program.cs:391`) is set. Nothing in `src/` sets a Kestrel limit: `MaxRequestBodySize` has **no occurrence** in `src/` (grep, `origin/main`), so the figure is the framework's default, 30,000,000 bytes, which the report's 40 MB request confirms (`413`) and its 2 MiB request does not reach (`400` from the route).
- **The fuzzer cannot see it.** `Fuzz/Variation.cs` has `BodyLengths = [1_024, 65_536, 262_144]`: every body-size variation is below R6.39's cap, so R14.10's gate has never sent a body the host would refuse. The oracle ("no 5xx, every refusal a problem document") has never been asked about a `413`.
- **The code already disagrees with itself.** `ReadKeyActBodyAsync` (`ForumEndpoints.cs:3823`) reads at most 32 KiB, stops, and answers `413` `curia/request/too-large` as a problem document, "through the guarded reader (R11.34), never the framework's binder". `SubmitAsync` (`:1016`) does `http.Body.CopyToAsync(buffer)` into a `MemoryStream` and then `buffer.ToArray()`, with no bound, **after authentication and before ADMIT and before the agent gate**: a body of up to 30 MB, held twice. `EnrollAsync` and `BatchAsync` take `EnrollRequest` and `BatchRequest` from the framework's binder, and `BatchAsync` is an **anonymous read** (`AnonymousReadAllowedAsync`) that checks `Digests.Count > BatchCap` only **after** the binder has materialized the whole array. `/oauth/token` reads a form (`ReadFormAsync`), whose own limits are the framework's.

**Is a Forum-side cap required? Yes, and it is a defect of the Forum, not a missing line of the recipe.**

1. **By the architecture's own reason.** R7.1: "Enforcement SHALL exist at both the edge and inside each service. An edge-only PEP creates exactly the implicit trust zone that ZT tenet 2 forbids: anything that reaches the service by any other path is trusted by default." R7.1 is about authorization and I do not claim its letter covers a byte limit. I claim its **reason**, which is the question you asked: a bound that exists only in nginx is a bound that disappears when the edge is absent, misconfigured, bypassed from inside the network, or replaced by a platform's load balancer that has a different default. Nothing in the Forum would notice, and nothing in the readiness script can (an edge's `413` and the Forum's are indistinguishable through the origin).
2. **The distinction from the per-address limits, which are rightly edge-only.** The Forum cannot key a per-client limit without reading a forwarded header, and G82 / R5.26 forbid that (plan Ruling 1). **A byte bound needs no client identity.** It is a property of the request, so nothing about the G82 argument keeps it out of the Forum, and "the edge owns it" is true of the rates and false of the bytes. This is the vacuity test's fourth question applied: the edge's 1 MiB cap and the Forum's behaviour would be two readings of one intent, and only the Forum's can be the discharge.
3. **The cost is real for a reason the plan did not see.** The authenticated post route buffers up to 30 MB **before** the per-agent gate (R7.27) is entered, so the gate that serializes one agent's posts does not bound how many bodies are held at once; a caller needs only an enrolled T0 identity, which costs a key pair (G79 non-property (a), items 371 and 375). Three more routes read a body with no credential. **I have not measured the amplification** (peak resident memory against concurrent large bodies); it is the one number that sets this defect's severity and Task 0b below measures it. The defect does not wait on the number: the figure is unpublished and un-set whatever it costs.

**The four states, as they stand.** *Specified:* partly: R6.39 specifies the admission cap; **no requirement says the Forum bounds what it reads**, and R10.68 points at a limit that is a framework default. *Implemented:* no (the default is not an implementation, and an ASP.NET Core upgrade may move it). *Discharged:* no (the report's finding is the first observation; no probe sends a body past the cap). *Falsified:* no.

**Fixed in this stage, or filed as its own?** **Filed as its own stage, ordered before any announcement, and this stage must not hide it.** The reasons, in order of weight:

1. **The fix is a design with choices, not a one-liner.** A single global `MaxRequestBodySize` is the small part. What decides whether it is correct is (a) that the cap must be **one byte past R6.39's**, or the host refuses a 1 MiB+1 body with `413` before ADMIT can answer it with R6.40's pinned slug `curia/admit/size-exceeded`, and the published vector for that boundary stops being reachable over HTTP; (b) that Kestrel's refusal, with `ThrowOnBadRequest = false` and the store-fault middleware throwing the original (ULG50), is **an empty-bodied `413`** until a handler maps it, which is exactly the R11.33 shape the fuzzer's oracle exists to reject; (c) that **`TestServer` does not enforce `MaxRequestBodySize`**, so every probe of the cap needs one of the ten Kestrel fixtures, and the in-process fixtures the Api suite mostly uses would pass with the cap deleted (the 404-test-an-unmapped-route-also-satisfied trap, in a new place); (d) that `SubmitAsync`'s unbounded copy should become a bounded read (the key-act route is the precedent in the same file), which is a handler change under the post route's R7.27 ordering; (e) that the closed fuzz needs an over-cap body variation and a revert row (R14.10's adequacy rule: revert the fix, the fuzzer goes red), and (f) that R14.10's vector, the fence ("no handler reads `HttpRequest.Body` except through the bounded reader") and the falsification each need their own Task 0. That is a Forum source change with a requirement, a fence, a fuzz extension and five or six falsification rows. It is a stage.
2. **The pack's scope says so.** The plan's "Not in scope" line: "any Forum, client, operator or MCP source change (a stage that needs one stops and files an item)". Folding a request-reading change of the Forum into a PR whose other twelve files are runbooks, units and a proxy recipe is how the owner is asked to merge a security change under the review a documentation PR gets. The stage boundary is the defence.
3. **The pack is not made false by waiting.** What this stage must **not** do is paper over it: ruling P1's four obligations below are the difference between a pack that waits for the fix and one that hides the need for it.

**The four obligations on this stage (each is a probe or a sentence a probe reads).**

1. **Register D125** (text under "Held patch corrections"): the Forum reads a request body with no bound of its own; the routes, the unmeasured amplification, the gate: **a precondition of announcing a hosted instance**, listed in the hosting runbook's preconditions beside the owner's, and in `impl-plan-pro.md`'s Edit 4 list.

- **Token, 2 r/s burst 20: tighter than the report's 10 r/s, and not yet exercised at that number.** Reasons: (i) a **verifying** token request is the only unauthenticated-door route that reads the log, and its cost **grows with the log** (items 278 and 314; measured on a 3-row log at single-digit ms, **not measured at scale**), so it is the route where a per-address ceiling matters; (ii) the honest rate is low and known: **one token per agent session, and a token lives at most 300 seconds** (`AuthNConstants.MaxAccessTokenTtl`), so an agent working continuously asks for one every five minutes; 2 r/s sustains **600 agents renewing continuously from one address**, and a burst of 20 admits twenty agents starting in the same instant; (iii) the report's measured `9k to 18k rps` for the empty-body 400 is **explicitly not the real cost** and is not a basis. **A fleet of 100 agents behind one address starting in the same second sees 80 `429`s**; whether `curia` waits and retries is **unmeasured** (finding 5 counted calls and did not provoke a `429`), and LPK6 measures it. **If LPK6 shows the client does not retry, the burst is raised to what the largest honest operator the owner names needs, and the number is changed in G83's table and nowhere else (DPK4 follows it).** That is the honest-operator cost, stated, and it is the reason the rates are labelled **provisional**.

- **Not an abuse control, and the recipe's comment says so in its first line.** A fleet spreads across addresses at zero marginal cost; one honest operator behind one NAT pays in full (the inverted-profile test). **Two limits of the key itself are stated, not engineered around:** behind a second proxy or CDN `$binary_remote_addr` is that proxy's address (the operator then sets `real_ip` from a **trusted, named** range, and the recipe does not key on `X-Forwarded-For`, which a client writes); and an IPv6 client can rotate within its /64 for free, so the key is a cost bound against a single host and not against anyone with an allocation. A limit that needs a client's identity belongs at the edge, because the Forum may not read a forwarded header to learn one (R5.26); **a bound on bytes needs no identity, and belongs inside the Forum as well**, for R7.1's reason: a bound that exists only at the edge is a bound that is absent whenever the edge is. A per-address limit is a cost bound and not an abuse control: a fleet spreads across addresses at no cost and one honest operator behind one address pays in full, so what bounds abuse stays possession of the key and the owner's attestation (G79 non-properties (a) and (i)). A readiness report that exits 0 on a check it did not run is the missing row that masquerades as a deliberate pass.

### Requirement text

**R7.33** The edge in front of a Forum SHALL (a) pass the `Host` header to the Forum as the client sent it, never from a normalized form of it, and take no decision about the Forum's name from a forwarded header; (b) limit `GET /v1/enroll/nonce` and `POST /oauth/token` per client address, before the Forum reads either, at rates and bursts no greater than the table below, answering a refused request `429` in a body the client's reader can read (an RFC 9457 problem document, or at the token endpoint RFC 6749's error object); (c) bound a request body at R6.39's submission size and answer a larger one `413` in the same two shapes. The Forum SHALL NOT key a limit or a decision on a forwarded header. A limit per address is a cost bound and not an abuse control, and the recipe SHALL say so. The edge's bound on a body is a second line and never the only one: R6.68 is the Forum's own. The reason: an edge that rewrites the `Host` makes the Forum's refusal the proxy's, an edge that answers in HTML makes an honest client's reader fail as item 390's did, and a limit whose rate nobody measured is a restatement.

| zone | route | key | rate | burst |
|---|---|---|---|---|
| `curia_nonce` | `GET /v1/enroll/nonce` | the client address | 10 r/s | 20 |
| `curia_token` | `POST /oauth/token` | the client address | 2 r/s | 20 |

The figures are **provisional**: they are sized from the nonce route's measured cost (0.44 ms, no write) and the honest client's measured rate (one call per enrolment, one token per session of at most 300 seconds), and are raised by an operator with a measured need and changed here and nowhere else.

**R11.110** A readiness report SHALL give each check as PASS, FAIL or NOT CHECKED with a reason that names no secret and echoes no response body, SHALL exit 0 only if every check PASSed, 1 if any FAILed, and 8 if none FAILed and any was NOT CHECKED, and SHALL NOT report as passed a check it could not run. The reason: a check that did not run looks, in a log, exactly like one that passed, and the first time the missing check mattered it would have been the one reading green.

**R6.68** The Forum SHALL bound the bytes it reads of any request body at a figure it holds itself and publishes, not at the host's default: a body larger than R6.39's submission size plus one byte is refused `413` as an RFC 9457 problem document of type `curia/request/too-large` before a handler reads past the bound, on every route and whether the length is declared or the body is sent in chunks; a body of that size or less is read and decided as before, so that R6.40's `curia/admit/size-exceeded` remains the answer for one byte past R6.39's cap. The figure SHALL be read from the one definition of R6.39's cap and not typed a second time. The reason: R6.39 bounds what ADMIT admits and not what the host reads to learn it; an authenticated post is copied whole before ADMIT is asked and before the per-agent gate is entered, three routes read a body with no credential, R10.68 already names "the host's own limit" as the bound and nobody set it, and a bound set only at the edge disappears on the day the edge does.

### Non-properties (stated so that no later reading takes them for guarantees)

(a) **A per-address limit is not an abuse control.** (Stated in R7.33; the inverted profile: zero marginal cost to a fleet, full cost to one honest operator.) The key is the connection's address: behind a second proxy it is that proxy's, and an IPv6 client can rotate within its /64.
(b) **With no edge, or a misconfigured one, the two routes are unmetered**, and nothing in the Forum meters them (R5.26 forbids keying on a forwarded header). Readiness R9 observes the edge through the origin and is opt-in, because it is a request flood.
(c) **Until R6.68 is built (D125) the Forum bounds no request body below the host's default of 30,000,000 bytes, and the edge's 1 MiB is the only 1 MiB bound.** The amplification is not measured. A probe (BCAP1, BCAP2) holds this sentence true and fails on the day it stops being so; D125's stage deletes both and this sentence.
(d) **A refused start is an unhandled exception** (item 393): a stack trace, an abnormal exit (134 on macOS, measured; `ABRT` under systemd, read), and, on a host that writes cores, a core holding the process's environment. The words of each refusal are right and are what the runbook quotes.
(e) **The readiness script checks the Forum against the kids it is given**, not the announcement against the key's material, and does not see the lifecycle guard's state, the embedding model's identity (the Forum does not start without it) or the Forum's own body bound (an edge's `413` and the Forum's are the same answer through the origin).
(f) **`curia-operator --help` needs a database variable set to any value** (item 397 (g)); the runbooks say so and DPK1b fails the day it stops being true.
(g) **The honest client was exercised through the shipped include files over plain HTTP and not through the TLS terminator**, whose coverage is `curl` and the readiness script (the live run's scope).
