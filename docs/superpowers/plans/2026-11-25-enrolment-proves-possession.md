## What this is

**The defect (item 364).** `POST /v1/agents` takes an identity and the public key it will sign with "and nothing else" (`EnrollRequest`, `src/Curia.Api/ForumEndpoints.cs:47`; the handler's own remarks, `:690-699`: "R4.11's proof of possession ... is missing and is not pretended otherwise"). R4.11 (white paper, l.717) requires a proof; errata G5 and G16 record it was never built. The consequences are four, all measured or read in earlier stages:
1. **A public key can be enrolled by anyone who can read a key set** (the key set serves every key; `GET /v1/jwks?agent=`). Key-bytes K8 measured the enrolment of a second identity under another identity's bytes (accepted); K8 held the private half but did not need it (G78 Amendment 1, ruling 20).
2. **Lost-row restoration is open to a holder of the public half.** R4.31 (rev.) lets the first request that re-presents the bound `kid` register the row again (`EnrollIdentity.cs`, the `restore` branch: `AddAsync` of whatever bytes arrive for a pre-R4.34 identity, or the bound bytes for a later one). Re-announcement ("succeed and register nothing") is likewise open to the public half.
3. Item 362 (one key under two identities) is accepted as a non-property **because** possession is unshown; "reconsidered only after item 364 lands".
4. Item 293's squat and lock-out legs and the unsigned enrolment root cannot be closed by a signed enrolment until there is a proof to sign.

**What this stage is not (said first, because the cost is borne by honest operators).** Possession is not an abuse control. A fleet absorbs it at zero marginal cost (one key pair per identity) and one honest operator pays a round trip and a signature; it is §4.6's inverted profile and the plan does not claim otherwise. It makes an enrolment mean "the submitter holds this key". It does not authenticate the owner (R4.10's code, R4.30), does not stop first-come squatting of an *identifier*, and does not limit enrolment rate (R4.13, unbuilt).

**Class:** a requirement the project wrote, derived a threat model from (G5: "what makes that safe and is untouched") and then never built, so that three entries (G5, G14, G16) leaned on it for their arguments. The probes this stage needs are the three kinds the project has paid for: vectors whose verdicts are written from the construction and never by running a verifier; probes red on today's tree **by their own assertion**; and probes that **sign with a key other than the submitted one**, because a proof that verifies under whatever key the request supplies is the green that carries no information (trap 298 is reserved for that, if a falsification row shows it).

## Rulings (decided, not asked)

1. **What the proof covers.** A compact JWS, `typ` **`curia-enroll-pop+jwt`**, `alg` the request's `alg` (EdDSA or ES256, the R4.15 allow-list), header `kid` the request's `kid`, **signed by the private key of the request's `public_key`**. Payload claims, all required: `agent_id` (the request's, byte-equal), `jkt` (the RFC 7638 thumbprint of the request's key as the Forum renders it: the thumbprint of `PublicJwk.Of(key)`'s `kty`, `crv`, `x` (`y`), which is the key as the log binds it and the key set serves it, so a reader can recompute `jkt` from a key set), `nonce` (ruling 2), `aud` (the absolute URL of `POST /v1/agents` **as the Forum received it**, built as `TokenEndpointUrl` builds the token endpoint's; never a configured value, so a proof for one host is refused at another, the failure the DPoP `htu` check was written for), `iat` (within `MaxSkew`, 30 s, of the Forum's clock) and `jti` (`Jti.Parse`, single-use, ruling 3). **A claim set rather than R4.11's concatenation**: a concatenation of code, nonce and thumbprint has no field boundaries and nothing to pin a purpose to but the string; a typed claim set binds each element by name and the `typ` separates it from a DPoP proof (`dpop+jwt`), a client assertion (`JWT`, `aud` the token endpoint) and a post (a detached JWS over canonical bytes). Unknown claims are ignored. **R4.10's enrolment code is unbuilt, so the proof does not contain one**; the erratum says that the stage that builds R4.10 adds a `code` claim and that a proof without it is then refused, and that until then a claim named `code` is read by nothing. The proof binds the **identity** (`agent_id`), the **key** (`jkt`, and the signature under the request's own key), the **name** (`kid`, in the signed header), the **Forum** (`aud`) and the **moment** (`iat`, `nonce`, `jti`). It does not bind an owner.
2. **The nonce is the Forum's epoch nonce, not a per-request value; the proof's `jti` is what is single-use.** *This departs from the ordering ruling's sentence "the nonce is single-use and consumed before any log read", and the reason is the point of the ruling:* a per-request single-use nonce needs **a new table** (`authn_dpop_nonces` holds one row per epoch and is shared by design, so a second use of the existing store is not an option; the store's own remarks reject per-call rows), and a new table is `db/0007`, which makes the PR the owner's to apply on the hosted database. It would also store one row per **anonymous** `GET`, a cost paid by the Forum for a request that costs an attacker nothing (the Sybil-economics reflex, inverted), and it would add nothing the `jti`, `iat` and `aud` do not: the proof is useful only to the Forum (it travels over TLS to it), so what must not happen is **its reuse**, and that is the `jti` in the shared replay cache (R5.14, atomic, `authn_replay`, no change). The server-supplied nonce then does what R4.11 says it is for and what B4 gave it for DPoP: **no proof can have been made before the Forum chose today's value.** Its acceptance is the store's existing rule (current and previous epoch: five to ten minutes). **Consumption order: the `jti` is consumed once the proof verifies and the nonce is current, and before the log is read** (ruling 5). If the owner prefers a per-request nonce, that is a `db/` change and the owner's; the plan's probes (EPP13) are the ones to flip.
3. **The nonce route.** `GET /v1/enroll/nonce`, anonymous, `Serves(ServedContent.None)`, no PDP (as `POST /v1/agents`); `200` `{"nonce": "<DpopNonce>", "expires_at": "<instant>"}` with `Cache-Control: no-store`, from `IDpopNonceStore.IssueAsync` (the current epoch's value; `expires_at` is the epoch's end, and the store honours the previous epoch too, so a client that signed just before the boundary is not refused). A fault of the nonce store is the middleware's existing `503` (`StoreFaults`). **No new port, no `db/` change, no `ci.yml` change.** The route reads no log. The existing `use_dpop_nonce` challenge (`NonceChallengeOrProblemAsync`) is **not** reused for enrolment: it would make every fresh client's first enrolment a wasted request and a second signature (an external signer that asks a person to touch a device would ask twice), and a dedicated route lets the client sign once.
4. **Refusals: seven problem types, all `400`, `curia/enroll/proof-...`**, each a constant in `EnrollmentErrors` with a title and a detail that names a **member or claim and never a value**: `proof-required` (no `proof` member, or an empty one), `proof-malformed` (not three base64url segments, a header or payload that does not read, a wrong `typ`, an `alg` outside the allow-list, a required claim absent or of the wrong type; detail `member=`), `proof-mismatch` (a claim or header member does not name this request; detail `claim=agent_id|kid|alg|jkt|aud`), `proof-not-possessed` (the signature does not verify under the request's key), `proof-window` (`iat` further than 30 s from the Forum's clock), `proof-nonce-stale` (absent, not a `DpopNonce`, or not the current or previous epoch's value), `proof-replayed` (the `jti` is spent). **`400`, not `401`:** a `401` promises a scheme to authenticate with (RFC 9110 requires `WWW-Authenticate`), and enrolment has none; the project's own rule is that a refusal of a request's own content is `400` (R6.58) and the author-mismatch `401` is for a caller the Forum could have authenticated. A `RefusalKind.Content` refusal, so `curia` exits as it does for every other `400` (Task 0, T0-6 prints it). Each type is distinct because each has a different remedy for the sender: stale is fetch-and-sign again, window is fix the clock, replayed is a new proof, mismatch and not-possessed are a defect of the sender's construction or signer, required is an older client. **A reflection fence in the shape of `R4_18_EveryRefusalTheUseCasesReturnIsMappedByTheRoutes`** asserts every `EnrollmentErrors` proof constant is mapped to `400` and not `500` (a constant added without its row fails the build).
5. **The order of the route** (G72's shape; each step is a refusal by name, and a refusal at a step leaves the store and the log as they were). (1) The existing text checks, **unchanged and first** (identifiers' text, NFC, control characters, blank, length, `alg`, key present, base64, `Jwks.CanPublish`), so an identifier refused for its own reason keeps its own name whether or not a proof is attached (`EnrollmentIdentifierTests` stays as it is for every refusal that precedes the proof); (2) `AgentId.Parse` and `Kid.Parse` (R11.34); (3) `proof-required`; (4) **the pure checks, no I/O:** split and header (`typ`, `alg` in the allow-list and equal to the request's, `kid` equal to the request's), the signature under the request's key (the verifier chosen by the pinned `alg`), then the payload's claims (`agent_id`, `jkt`, `aud`, `iat`); (5) the nonce is current (one read of the nonce store, the first I/O); (6) the `jti` is consumed (one write of the replay cache); (7) **only now** `EnrollIdentity.EnrollAsync`, whose first act is the log read. So a request whose proof does not verify touches **no store at all**, a request with a stale nonce touches the nonce store only, and **a fault of the log after step 6 spends the proof** (the same rule R5.23 states for the token endpoint). The signature is checked before the payload is parsed: an unsigned claim is not trusted. The validator is `Curia.AuthN.EnrollmentProofValidator` (a sibling of `ClientAssertionValidator`: pure `Validate`, then `ConsumeAsync`-shaped store steps), taking the replay and nonce ports; the route calls it and holds the order; **no fence over the order beyond probes** (non-property (h)), plus **one fence over the callers**: `EnrollIdentity.EnrollAsync` has exactly one production caller, the route (Task 0, T0-2, confirms it today), and a second caller fails the build with a reasoned-row exception list in the shape of `CS-15`'s.
6. **Every enrolment request carries a proof: first, repeated, and a restoration.** `R4.31 (add.)`. A re-announcement that registers nothing still proves the submitter holds the key it re-presents; a lost-row restoration (`restore` in `EnrollIdentity`) registers a key row only for a holder. This closes the public-half legs of items 1 and 2 above for every identity whose log binds the bytes (R4.34). **It does not close** the pre-R4.34 identity whose log binds the `kid` alone: that restoration registers whatever bytes arrive with a proof *by those bytes*, still first-come (non-property (d); alpha, no such identity is hosted).
7. **The proof is signed through `IAgentSigner.Sign` (the `sign` verb); no new external-signer verb.** A `sign-enrolment` verb (the shape of `sign-lifecycle`, R4.39) would let a signer's policy refuse enrolment proofs from a process that may only post. The cost is a protocol change in `ExternalSigner`, `test-signer.py`, the three tests that run a real signer, and the signer's refusal list; the gain is that a process with `sign` access cannot mint a proof that binds the key to a **new identifier**, whose harm is the one item 362's owner-accepted non-property already holds (the same key under two identities, which a holder can already do). Recorded as a lead (item 373), not built. A proof's `typ` makes it distinguishable to any signer that wants to refuse it.
8. **The client's enrolment** (`R11.107`). `ForumClient.EnrolAsync(agent, clock, ct)` (TimeProvider only, CS-9): GET the nonce; build the proof through the agent's signer (**one signature on the success path**; a test counts external-signer calls); POST. **One automatic retry, only for `proof-nonce-stale`:** a new nonce, a new `jti`, a new signature. No retry for any other type, and none for a `503` or an unheard send (the continuation below is the remedy). The words are one definition, `EnrolWording`, whose spans are published in G79's `**R11.107 words.**` paragraph and **read from the errata by the probes** (the pattern G77's `KeyPagesWords` and `PublishedClientWords.Paragraph` use: the probe's expected text is in a different artifact from the code). Draft of the words the cold read tests (Task 8 may correct them; the errata carries the final): `proof-window`: "nothing was registered: the Forum's clock and this host's differ by more than 30 seconds. Correct this host's clock, then run the same command again." `proof-not-possessed`: "nothing was registered: the signature over the enrolment does not verify under the key being enrolled. For --signer, the key the signer describes is not the key it signs with; check the signer, then run the same command again." `proof-required` (an older client): "this Forum requires a proof of possession from the key being enrolled and this client did not send one; update curia." And, from a Forum with no nonce route (a client newer than its Forum): "this Forum does not offer an enrolment nonce, so it predates proof of possession at enrolment; nothing was sent." `proof-nonce-stale` after the one retry, `proof-replayed`, `proof-malformed` and `proof-mismatch`: a line naming the cause and "this is a defect of this client or of its signer; nothing was registered."
9. **The continuation: `curia enrol` on a slug whose profile was created and never enrolled sends the enrolment again with the profile's own keys.** Today a refused or unheard enrolment leaves a profile that `ProfileStore.Create` refuses to reuse (`ProfileExists`: "keys are never overwritten"), so the first transient refusal this stage introduces (a clock, a nonce at the boundary, a `503`) would end with "an agent by that name is already enrolled", which is false, and with the owner deleting a directory. A profile is **resumable when `identity.json` records no `enrolled_at`** and the request's `--agent-id` and `--forum` equal the profile's; the verb loads the profile (no key is generated; no key is replaced) and runs the same enrolment, saying "continuing an enrolment that was not completed". A profile **with** `enrolled_at`, or with other identifiers, is refused as today. The re-send is safe because the Forum treats a re-presented bound key as a re-announcement (R4.31) and now requires the proof. **Cut line:** if Task 0 (T0-6) finds `identity.json` cannot distinguish a never-enrolled profile (it holds `EnrolledAt = null` until `RecordEnrollment`, read at `ProfileStore.cs:484`), this ruling drops to words only (`proof-window` and the rest say "remove the directory named, then run again") and item 370 is filed; the cold read says which.
10. **Item 299 does not join this PR; it is the next PR, and may run in parallel on its own branch.** The closure (a second `agent.enrolled` root in a stream that holds one is skipped and counted) is a change to the lifecycle **fold and every reader of it** (`LifecycleFold`, `LifecycleCheck`, `curia-testis` twice) and to the honoured and lifecycle corpora (new cases, every pin site of key-bytes' ruling 15, OAS39 rewritten), a falsification set of its own, and the differential-agreement gate the key-bytes PR needed. This PR touches none of those files, and the route's refusal of a second root (R4.31) is already in force: **the two close different doors** (one is a row the credential writes, the other is a request the route takes), and neither probe set reads the other's. ## The errata entry (G79), proposed text

Appended **after G78** in the errata, status "specified; not built" until Task 9. Pasted by Task 1 after the controller's immediate re-read of the file. The Status paragraph is written from the run by Task 9, its shape G78's.

> ## G79 — Enrolment proves possession: a request to enrol a key carries a proof signed by that key over the identity, the key, the Forum and a nonce the Forum chose, a proof that does not verify touches no store, and a fault of the log spends it
>
> **Location.** R4.11 (the proof of possession), R4.10 (the enrolment code, unbuilt), R4.31 (what a repeat and a restoration register), R4.34 (what the log binds), R5.14 (the shared `jti` cache), R5.19 (the Forum's nonce), R5.25 (verify before reading the log); errata G5 ("the agent still supplies its own key"), G14, G15, G16 ("R4.11's proof of possession, and an EdDSA point check"); register items 364, 362, 293 and 299.
>
> **How it surfaced.** Not found by a defect: named, three times, as the thing that was not built. G5 called the proof "what makes that safe and is untouched" and G14's annotation records it was "never built"; G16 states that a key nobody can sign with "is bound as readily as any other"; the key-bytes PR's K8 measured an identity enrolled under another identity's public bytes and its Amendment 2 ruled that cross-identity reuse waits on this proof. The owner decided on 2026-11-24 that it is built before beta hosting.
>
> **Class.** A control two entries relied on and no stage built, so that each argument inherited a premise nothing checked. Here the premise is cheap to state and was never exercised: **the submitter of a public key holds its private half.**
>
> ### The finding
>
> `POST /v1/agents` registered whatever public key it was sent for an identifier that held none (R4.31), re-announced and restored rows for whoever presented a bound `kid` (R4.31 (rev.)), and bound the key in the log (R4.34). A key set is public by design, so anyone could enrol, or present for restoration, a key whose private half they did not hold. The consequences are bounded by what the Forum already refused (a key enrolled for an identifier that holds one is refused; a post is accepted only if the author's key verifies it), but they are not nothing: an identity bound to a key its enroller cannot sign with is unusable and lost to its rightful holder (a squat of an identifier together with a victim's public key), a second identity can hold a first's bytes (item 362), and a lost row can be restored by a holder of the public half.
>
> ### Decisions this entry makes
>
> The proof is a compact JWS of its own `typ`, signed by the key being enrolled, over a claim set naming the identity, the key's thumbprint, the Forum's URL, a nonce the Forum supplies and a `jti` the Forum consumes. The nonce is the Forum's existing epoch nonce (R5.19), fetched from a route of its own; it is shared and not single-use, and the proof's `jti` is single-use in the shared replay cache (R5.14). The route verifies with no I/O, reads the nonce store, consumes the `jti`, and only then reads the log. Every enrolment request carries a proof, a repeat and a restoration included. R4.10's code is not built, so the proof carries none; the stage that builds it adds a claim. Nothing in the log changes. The client fetches a nonce, signs once, sends, retries only on a stale nonce, and continues an enrolment it did not complete.
>
> ### Requirement text
>
> **R4.46** An enrollment request SHALL carry a `proof`: a compact JWS whose protected header names `typ` `curia-enroll-pop+jwt`, an `alg` in R4.15's allow-list equal to the request's `alg`, and the request's `kid`, signed by the private key corresponding to the request's `public_key`, over claims `agent_id` (the request's), `jkt` (the RFC 7638 thumbprint of the request's key as R4.34 renders it), `nonce` (R4.47), `aud` (the absolute URL of the enrollment route as the Forum received it), `iat` (within R5.16's permitted skew of the Forum's clock) and `jti`. The Forum SHALL refuse, by name and with status `400`, a request whose proof is absent (`curia/enroll/proof-required`), is not a JWS of that `typ` and `alg` or lacks a claim (`proof-malformed`), names another identity, `kid`, `alg`, key or URL than the request (`proof-mismatch`), does not verify under the request's key (`proof-not-possessed`), is outside the skew (`proof-window`), carries a nonce the Forum did not choose in the current or previous epoch (`proof-nonce-stale`) or carries a spent `jti` (`proof-replayed`); a refusal SHALL name a member or a claim and SHALL NOT name a value. The checks SHALL be made in that order, the first five with no read or write of any store; the nonce SHALL be checked before the `jti` is consumed, and the `jti` SHALL be consumed before the event log is read, so that a request whose proof does not verify reads and writes nothing, and a fault of the log after it verifies spends the proof (R5.23's rule). A refused request SHALL leave the key store and the event log as they were. The proof SHALL carry no enrollment code until R4.10 is built; the stage that builds it SHALL add the code as a claim, and the Forum SHALL then refuse a proof without it. The reason: a public key is public, so a request that names one shows nothing of who sent it; the proof shows the sender holds the key, names what the signature is for so that it cannot be reused for another identity, Forum or moment, and is checked before it costs the Forum a read.
>
> **R4.47** The Forum SHALL serve, to any caller and without a token, `GET /v1/enroll/nonce`, answering `200` with the nonce of R5.19's current epoch and the instant that epoch ends, and `Cache-Control: no-store`; it SHALL accept as the proof's `nonce` the value of the current epoch or the one before it, and no other. The nonce is the Forum's choice of when a proof may have been made, and it is **not** single-use: the proof's `jti` is (R5.14, R4.46). The reason: single-use state per anonymous request is a cost the Forum pays and a sender does not, and a single-use proof gives the property the nonce was asked for without it.
>
> **R4.11 (rev.)** R4.11's proof is the proof of R4.46, with R4.46's claims in place of the concatenation of R4.11's three elements, and without the enrollment code until R4.10 is built. R4.11's last sentence stands: a public key submitted without a proof of possession is an unauthenticated claim, and since this entry the Forum refuses one.
>
> **R4.31 (add.)** A request that re-presents the `kid`, algorithm and public key the Registrar already holds for its identifier, and a request that restores a row the key store lost, SHALL carry the proof of R4.46: a repeat and a restoration register or report only for a holder of the key.
>
> **R5.14 (add.)** The proof of R4.46's `jti` is consumed in the cache R5.14 shares between client assertions and DPoP proofs, retained as `DpopProofValidator.ConsumeAsync` retains a proof's.
>
> **R5.19 (add.)** The Forum's nonce (R5.19) is also the nonce of R4.46; it is served at R4.47's route as well as in the challenge of a write path.
>
> **R11.107** `curia enrol` SHALL fetch the nonce of R4.47, sign the proof of R4.46 once, through the agent's signer (the registered key, in this process or in the external signer), and send the enrollment with it; SHALL, on `proof-nonce-stale` alone, fetch a new nonce, sign a new proof and send once more; SHALL NOT otherwise send an enrollment a second time in one run; SHALL word a refusal of the proof by its cause and say whether anything was registered (nothing was, for every refusal of R4.46); SHALL, for an agent whose profile was created and records no enrollment, continue it with that profile's keys and the same identifiers, and refuse a profile that records an enrollment or other identifiers as before; and SHALL say, of a Forum that serves no nonce route, that it predates the proof and that nothing was sent. The words are those of the paragraph `**R11.107 words.**` below. The reason: an owner who is refused for a clock, a nonce at a boundary or an unheard send has not enrolled, and must be able to run the same command again, which a profile the client will not reuse had made impossible; and a proof an owner must sign twice is a prompt an owner must answer twice.
>
> **R11.107 words.** *(the spans the probes read; the cold read corrects them before the Status is written)*
> - `Proof, window`: "nothing was registered: the Forum's clock and this host's differ by more than 30 seconds. Correct this host's clock, then run the same command again."
> - `Proof, not possessed`: "nothing was registered: the signature over the enrollment does not verify under the key being enrolled. With --signer, check that the key the signer describes is the key it signs with, then run the same command again."
> - `Proof, required`: "this Forum requires a proof of possession from the key being enrolled and this client did not send one; update curia. Nothing was registered."
> - `Nonce, absent`: "this Forum does not offer an enrollment nonce, so it predates proof of possession at enrollment. Nothing was sent."
> - `Continuing`: "continuing an enrollment that was not completed, with the keys already in this profile."
> - `Proof, other`: "the Forum refused the proof (<type>); nothing was registered. This is a defect of this client or of its signer."
>
> ### Non-properties (stated so that no later reading takes them for guarantees)
>
> (a) **This is not an abuse control.** A fleet makes one key pair per identity at no cost; R4.13's per-owner limits are unbuilt; an identifier is still first-come; an anonymous caller can still enrol any number of identities, each now holding its key. (b) **The proof is not retained.** The log's `agent.enrolled` and `agent.key-bound` rows are unchanged, so a third party cannot check that possession was shown, only the Forum's word; item 293's signed enrolment root is the stage that retains it. (c) **One key under two identities is still possible**, by a holder of the private half (item 362, accepted by the owner). What is removed is the holder-of-the-public-half path. (d) A restoration for an identity enrolled before R4.34, whose log binds the `kid` alone, registers whatever bytes arrive with a proof by those bytes: still first-come. (e) **The nonce is shared and reusable**: any number of proofs may carry one epoch's value; the `jti` is what is single-use (R4.47). (f) A process that may call the signer's `sign` can make a proof; there is no separate verb (item 373). (g) R4.10's code and R4.30's owner are not shown by a valid proof: it shows the submitter holds the key, not who owns the identifier. (h) **The route's order is carried by probes, and the one fence is over callers**; a new caller of the use case that skips the proof fails the build, and a reordering of the route's steps is caught by EPP only. (i) The nonce route writes on every call (`IssueAsync`: an insert that conflicts and a delete) and is anonymous; it is as costly as the existing `use_dpop_nonce` challenge and as unmetered, until an edge exists (R7.1's gateway is unbuilt; item 371). (j) A client older than this build is refused `proof-required` and a client newer than the Forum meets `404` at the nonce route; alpha, no migration. (k) Existing identities need nothing; their next re-announcement needs the key. (l) A refused or unheard enrollment leaves the profile it created, and a continuing `curia enrol` reuses it; when the Forum did record the first send, the continuation is answered as a re-announcement (R4.31) and registers nothing.
>
> **Status:** specified; not built.

## Amendment 1 (2026-11-24, from the security review and the owner's answers)

The cybersecurity agent reviewed this plan before Task 0 (severity medium; sound to build). Its rulings and the owner's answers the same day:

- **Q1 (epoch nonce, single-use `jti`): ruled sound.** The effective replay window is the `iat` window (plus or minus 30 s), not the nonce's epoch; a per-request single-use nonce adds nothing the single-use `jti`, `iat` and `aud` do not. The departure from single-use stands; no `db/0007`.
- **Q2 (claim binding): ruled adequate.** EPV11, EPV15 and FEPP1 are kept; FEPP1 is the row showing the signature is checked under the request's key and never a key from the proof.

> ## G79 — Enrolment proves possession: a request to enrol a key carries a proof signed by that key over the identity, the key, the Forum and a nonce the Forum chose, a proof that does not verify touches no store, and a fault of the log spends it
>
> **Location.** R4.11 (the proof of possession), R4.10 (the enrollment code, unbuilt), R4.31 (what a repeat and a restoration register), R4.34 (what the log binds), R5.14 (the shared `jti` cache), R5.16 (permitted skew), R5.19 (the Forum's nonce), R5.25 (verify before reading the log); errata G5 ("the agent still supplies its own key"), G14, G15, G16 ("R4.11's proof of possession, and an EdDSA point check"), G72 (the order this entry copies) and G78 (non-property (a)); register items 364, 362, 293 and 299 and register defect D41.
>
> **How it surfaced.** Not found by a defect: named, three times, as the thing that was not built. G5 called the proof "what makes that safe and is untouched" and G14's annotation records it was "never built"; G16 states that a key nobody can sign with "is bound as readily as any other"; errata G78's non-property (a) records that an identity enrolled under another identity's public bytes is accepted and that a refusal across identities waits on this proof. This stage's Task 0 reproduced the four consequences below on a real Forum, with no private half: another identity's public bytes enrolled under a fresh identifier and kid (201, two rows appended), a third identity under the same bytes (201), a re-announcement by a presenter holding only the public half (201, nothing appended), and a lost key-store row restored by that presenter (201, the row back). The owner decided on 2026-11-24 that it is built before beta hosting.
>
> **Class.** A control two entries relied on and no stage built, so that each argument inherited a premise nothing checked. Here the premise is cheap to state and was never exercised: **the submitter of a public key holds its private half.**
>
> ### The finding
>
> `POST /v1/agents` registered whatever public key it was sent for an identifier that held none (R4.31), re-announced and restored rows for whoever presented a bound `kid` (R4.31 (rev.)), and bound the key in the log (R4.34). A key set is public by design, so anyone could enrol, or present for restoration, a key whose private half they did not hold. The consequences are bounded by what the Forum already refused (a key enrolled for an identifier that holds one is refused; a post is accepted only if the author's key verifies it), but they are not nothing: an identity bound to a key its enroller cannot sign with is unusable and lost to its rightful holder (a squat of an identifier together with a victim's public key), a second identity can hold a first's bytes (item 362), and a lost row can be restored by a holder of the public half.
>
> ### Decisions this entry makes
>
> The proof is a compact JWS of its own `typ`, signed by the key being enrolled, over a claim set naming the identity, the key's thumbprint, the Forum's URL, a nonce the Forum supplies and a `jti` the Forum consumes. The nonce is the Forum's existing epoch nonce (R5.19), fetched from a route of its own; it is shared and not single-use, and the proof's `jti` is single-use in the shared replay cache (R5.14). The URL the proof is bound to is the one the Forum received, which binds a proof to a Forum only as strongly as the Forum's knowledge of its own name (register defect D41); hosting needs that closed, and until it is, a proof made for a host a request names is accepted at that host (non-property (n)). The route verifies with no I/O, reads the nonce store, consumes the `jti`, and only then reads the log. Every enrollment request carries a proof, a repeat and a restoration included. R4.10's code is not built, so the proof carries none; the stage that builds it adds a claim. Nothing in the log changes. The client fetches a nonce, signs once, sends, retries only on a stale nonce, continues an enrollment whose refusal was of the moment, and says plainly when the refusal was of the request and the profile cannot be enrolled as it is. R4.46's verdicts are also published as a conformance family, `conformance/enroll-proof/`, whose expected results are written from each case's construction and not by running a verifier; the Status says which readers judge it.
>
> ### Requirement text
>
> **R4.46** An enrollment request SHALL carry a `proof`: a compact JWS whose protected header names `typ` `curia-enroll-pop+jwt`, an `alg` in R4.15's allow-list equal to the request's `alg`, and the request's `kid`, signed by the private key corresponding to the request's `public_key`, over claims `agent_id` (the request's), `jkt` (the RFC 7638 thumbprint of the request's key as R4.34 renders it), `nonce` (R4.47), `aud` (the absolute URL of the enrollment route as the Forum received it), `iat` and `jti`. The Forum SHALL refuse, with status `400` and by name, at the first of these steps that applies, and a refusal SHALL name a member or a claim and SHALL NOT name a value: (1) a request with no `proof`, or an empty one: `curia/enroll/proof-required`; (2) a `proof` longer than 8,192 characters, not three unpadded base64url segments, whose header does not read as an object, whose `typ` is not `curia-enroll-pop+jwt`, whose `alg` is outside R4.15's allow-list, or which has no `kid`: `proof-malformed`; (3) a header `alg` or `kid` that is not the request's: `proof-mismatch`; (4) a signature that does not verify under the request's key, the verifier being chosen by the request's `alg` and never by the proof: `proof-not-possessed`; (5) a payload that does not read as an object, or lacks `agent_id`, `jkt`, `aud`, `iat` or `jti` or holds one of the wrong type: `proof-malformed`; then an `agent_id`, `jkt` or `aud` that is not the request's, in that order: `proof-mismatch`; then an `iat` further from the Forum's clock than R5.16's permitted skew: `proof-window`; (6) a `nonce` that is absent, is not a nonce value, or is not one the nonce store reports current (R4.47): `proof-nonce-stale`; (7) a `jti` already consumed: `proof-replayed`. Steps 1 to 5 SHALL read and write no store; step 6 SHALL come before the `jti` is consumed; step 7 SHALL come before the event log is read, so that a request whose proof does not verify reads and writes nothing, and a fault of the log after step 7 spends the proof (R5.23's rule). A refused request SHALL leave the key store and the event log as they were. The signature SHALL be checked before the payload is read, so that no claim is trusted before it is signed. The proof SHALL carry no enrollment code until R4.10 is built; the stage that builds it SHALL add the code as a claim, and the Forum SHALL then refuse a proof without it. The reason: a public key is public, so a request that names one shows nothing of who sent it; the proof shows the sender holds the key, names what the signature is for so that it cannot be reused for another identity, Forum or moment, and is checked before it costs the Forum a read. Reuse of a proof is bounded by its `iat` window, its `aud` and its single-use `jti`, and not by the nonce, which is why the `iat` check is among the steps that touch no store.
>
> **R4.47** The Forum SHALL serve, to any caller and without a token, `GET /v1/enroll/nonce`, answering `200` with the nonce of R5.19's current epoch and the instant that epoch ends, a body of exactly `nonce` and `expires_at`, and `Cache-Control: no-store`; it SHALL accept as the proof's `nonce` a value the nonce store reports current (R5.19: a value it issued for the current epoch or the one before it) and no value it did not issue; and it SHALL ignore a query string on the route, which takes no parameter that one could be taken for. The nonce is the Forum's choice of when a proof may have been made, and it is **not** single-use: the proof's `jti` is (R5.14, R4.46). The reason: single-use state per anonymous request is a cost the Forum pays and a sender does not, and a single-use proof gives the property the nonce was asked for without it.
>
> **R4.11 (rev.)** R4.11's proof is the proof of R4.46, with R4.46's claims in place of the concatenation of R4.11's three elements, and without the enrollment code until R4.10 is built. R4.11's last sentence stands: a public key submitted without a proof of possession is an unauthenticated claim, and since this entry the Forum refuses one.
>
> **R4.31 (add.)** A request that re-presents the `kid`, algorithm and public key the Registrar already holds for its identifier, and a request that restores a row the key store lost, SHALL carry the proof of R4.46: a repeat and a restoration register or report only for a holder of the key.
>
> **R5.14 (add.)** The proof of R4.46's `jti` is consumed in the cache R5.14 shares between client assertions and DPoP proofs, retained as `DpopProofValidator.ConsumeAsync` retains a proof's.
>
> **R5.19 (add.)** The Forum's nonce (R5.19) is also the nonce of R4.46; it is served at R4.47's route as well as in the challenge of a write path.
>
> **R11.107** `curia enrol` SHALL fetch the nonce of R4.47, sign the proof of R4.46 once, through the agent's signer (the registered key, in this process or in the external signer), and send the enrollment with it; SHALL, on `proof-nonce-stale` alone, fetch a new nonce, sign a new proof and send once more; SHALL NOT otherwise send an enrollment a second time in one run; SHALL word a refusal of the proof by its cause and say whether anything was registered (nothing was, for every refusal of R4.46); SHALL, for an agent whose profile was created and records no enrollment, continue it with that profile's keys and the same identifiers, and refuse a profile that records an enrollment or other identifiers as before; SHALL, for a refusal of the request itself (every `409` of the enrollment route and every `400` that is not one of R4.46's seven types), say at the refusal, in the first run and in a continuation alike, that nothing was registered and that the profile cannot be enrolled as it is, name what to do (remove the profile's directory and enrol again under a different identifier or kid), edit nothing, and send nothing more in that run; and SHALL say, of a Forum that serves no nonce route, that it predates the proof and that nothing was sent. The words are those of the paragraph `**R11.107 words.**` below. The reason: an owner who is refused for a clock, a nonce at a boundary or an unheard send has not enrolled, and must be able to run the same command again, which a profile the client will not reuse had made impossible; an owner whose identifier or kid the Forum refuses cannot succeed by running it again, and must be told so, not left to run it; and a proof an owner must sign twice is a prompt an owner must answer twice.
>
> **R11.107 words.** *(the spans the probes read; the cold read corrects them before the Status is written)*
> - `Proof, window`: "nothing was registered: the Forum's clock and this host's differ by more than 30 seconds. Correct this host's clock, then run the same command again."
> - `Proof, not possessed`: "nothing was registered: the signature over the enrollment does not verify under the key being enrolled. With --signer, check that the key the signer describes is the key it signs with, then run the same command again."
> - `Proof, required`: "this Forum requires a proof of possession from the key being enrolled and this client did not send one; update curia. Nothing was registered."
> - `Nonce, absent`: "this Forum does not offer an enrollment nonce, so it predates proof of possession at enrollment. Nothing was sent."
> - `Continuing`: "continuing an enrollment that was not completed, with the keys already in this profile."
> - `Proof, other`: "the Forum refused the proof (<type>); nothing was registered. This is a defect of this client or of its signer."
> - `Not continuable`: "nothing was registered, and this profile cannot be enrolled as it is: the Forum refused what the profile names (<type>), and the same command would be refused again. Remove <directory>, then enrol again under a different --agent-id or --kid."
>
> In `Proof, other` and `Not continuable`, `<type>` is the refusal's type written as a display literal (R10.65) and `<directory>` is the profile's directory written as a display literal; no other value of the response is printed.
>
> ### Non-properties (stated so that no later reading takes them for guarantees)
>
> (a) **This is not an abuse control.** A fleet makes one key pair per identity at no cost; R4.13's per-owner limits are unbuilt; an identifier is still first-come, and a caller can still enrol an identifier with a key of its own that the identifier's rightful holder had not yet enrolled. The owner accepted that first-come squatting on 2026-11-24, to be revisited when R4.10's code or R4.30's attestation is scheduled. An anonymous caller can still enrol any number of identities, each now holding its key. (b) **The proof is not retained.** The log's `agent.enrolled` and `agent.key-bound` rows are unchanged, so a third party cannot check that possession was shown, only the Forum's word; the owner chose on 2026-11-24 not to retain it now and to build retention (item 293, the signed enrollment root) before any hosting that claims non-repudiation of enrollment. (c) **One key under two identities is still possible**, by a holder of the private half (item 362, accepted by the owner). What is removed is the holder-of-the-public-half path. (d) A restoration for an identity enrolled before R4.34, whose log binds the `kid` alone, registers whatever bytes arrive with a proof by those bytes: still first-come. (e) **The nonce is shared and reusable**: any number of proofs may carry one epoch's value; the `jti` is what is single-use (R4.47). (f) A process that may call the signer's `sign` can make a proof; there is no separate verb (item 373). (g) R4.10's code and R4.30's owner are not shown by a valid proof: it shows the submitter holds the key, not who owns the identifier. (h) **The route's order is carried by probes, and the one fence is over callers**; a new caller of the use case that skips the proof fails the build, and a reordering of the route's steps is caught by the probes only. (i) The nonce route writes on every call (`IssueAsync`: an insert that conflicts and a delete) and is anonymous; it is as costly as the existing `use_dpop_nonce` challenge and as unmetered, until an edge exists (R7.1's gateway is unbuilt; item 371). (j) A client older than this build is refused `proof-required` and a client newer than the Forum meets `404` at the nonce route; alpha, no migration. (k) Existing identities need nothing; their next re-announcement needs the key. (l) A refused or unheard enrollment leaves the profile it created. When the refusal was of the moment (a clock, a nonce, a replay, a fault, an unheard send) a continuing `curia enrol` reuses the profile, and when the Forum did record the first send the continuation is answered as a re-announcement (R4.31) and registers nothing; when the refusal was of the request itself the profile cannot be enrolled, the client says so, and it does not edit the profile or offer another kid. (m) **The nonce store bounds an epoch below and not above**: `IsCurrentAsync` accepts any epoch from the previous one upward, so a nonce issued while the Forum's clock was ahead stays current after the clock steps back. It is harmless to this proof because the nonce is public and Forum-chosen and reuse is bounded by `iat`, `aud` and the `jti`; it would not be harmless if the nonce were ever the only bound, and the store is shared with the DPoP nonce of the token endpoint (register lead). (n) **The `aud` binding is only as strong as the Forum's knowledge of its own name.** The Forum builds the URL from the request's `Host`, as the token endpoint does (register defect D41), so a proof signed for a host and sent under that `Host` is accepted whoever relays it: a hostile Forum A can relay a victim's proof to this Forum under `Host: A`, with the harm of a non-consensual but correct binding of the victim's own key to the victim's identifier here, and no impersonation. A pin (EPP23) holds the behaviour of both routes today. Hosting needs D41 closed (a configured origin, not `AllowedHosts` alone, whose refusal is an HTML page and not a problem document), and behind a TLS-terminating proxy without it every enrollment is refused `proof-mismatch` `claim=aud`, which is loud. Nothing fails loudly until then. (o) The proof's reuse is bounded by its `iat` window and its single-use `jti`; a proof is never accepted after the replay cache has forgotten its `jti` only because the `iat` check is pure and precedes the cache.
>
> **Status:** specified; not built.
