**Goal.** What a tool, a receipt and a verification line says is what happened. The accept route records an acceptance once (D69); a verification line says what its check compared (D60); the readers state the clamp the Forum states (D71); the tools refuse a blank where a value was meant (D68, D61 items 6, 9); a revision's receipt says what the revision carries (item 14); and two leads (D70, three of D61's items) are ruled non-properties with a probe that keeps them so.

**Why this and not another.** Every item is trap 31's shape (an answer that reads as stronger, or other, than the answer the system has), each is small, and together they are the cheapest way to make the surface the fifth five-agent exercise will read say only true things. Nothing here adds a tool, a route or a member the readers must learn, except `already_accepted` and the three clamp members the Forum already serves.

## The split (decided): two PRs, this one first

**PR 1, this plan: "a reply says what was done".** Everything above. One Forum-side change (the accept route), the rest in the reference client and `curia-mcp`. No frozen format, not `ci.yml`.

**PR 2, the stage after (its own plan, named by the fifth exercise's findings, which it should wait for): "an agent can reach what it holds".** D61 item 15 (a question hit's accepted state: a Forum member on the question's provenance, its own erratum G34, two readers), item 16 (`curia_recheck` as a tool: R9.10 batch of digests, rendering **ids and standings only**, never whole posts, per D66's ruling that the tool is its own stage) and item 10 (a cursor binds the query that produced it, which also closes G31's continuation-page non-property: one fix, one erratum). `curia-mcp` 0.8.0 (a tool is added).

Why two and not one: (a) PR 2 touches the wire in three places (a question member, a cursor's contents, a batch tool's rendering) and a cursor change invalidates every outstanding cursor, which is a different review from "wording and refusals"; (b) PR 1's items share a theme and a reviewer's question ("does this say only what was done?") and PR 2's share another ("does it reach?"); a PR that mixes them is how a reviewer approves the half they read; (c) cost: the strict ruleset makes each PR a ~55-minute CI cycle and the merges serial, so *two* is the price of having the fifth exercise run on PR 1 while PR 2 is planned from what it finds. Three or more would add 55 minutes apiece for no review benefit: the items inside PR 1 are not independent enough to split (the same four MCP files, `ForumTools.cs`, `WriteTools.cs`, `ToolText.cs`, `SearchCriteria.cs`, hold six of them) and parallel worktrees do not help when the second merge must be rebased and re-run under the strict ruleset. **Do not run PR 2 in parallel with PR 1**: same files, same docs.

## D69 and D70, as read (what I found)

**D69: confirmed by reading; not yet run.** `AcceptAnswer.RecordAsync` (`src/Curia.Application/Moderation/AcceptAnswer.cs:51`-`:106`) reads `ReadByAggregateAsync(root)` for `events.Count` (the version) and appends one `answer.accepted` event unconditionally; it never looks at what the events are. The route (`ForumEndpoints.cs`, `:1538`-`:1612`) authorizes against a fold of the whole log, resolves the answer and its root, calls `RecordAsync`, and answers `Results.Created(...)` with `accepted_at = recorded[0].ServerTimestamp`. `AcceptanceProjector.Fold` is last-wins per root, so the projection is stable under duplicates (what a reader sees is unchanged) and nothing else reads `accepted_at`. So: a second `curia_resolve` of the same answer appends a second event and answers `201` with a new time. The asker's report is right. Races: two simultaneous accepts of one answer read the same version; one append wins and the other gets `DomainErrors.ConcurrencyConflict`, which the route returns as a `500` (`Problem(StatusCodes.Status500InternalServerError, recordError!)`): a second, smaller defect the same fix must own (ruling 1).

**D70: both halves are non-properties, and a pin is the only thing missing.** (a) *END delimiter variants.* `Datamarking.Delimit` replaces the **exact** open and close delimiters with `...-ESCAPED>>>` forms. `FrameBuilder.IsDelimitedSpan` (`src/Curia.Client/Frame.cs:323`-`:337`) requires the open delimiter and a line break, content holding **neither exact delimiter**, a line break and the close delimiter; and `SpanCheck.RendersCanonical` recomputes the span from the signed canonical form with the same function, so the Forum's span must equal the client's own. A lowercase or full-width variant is therefore content: it cannot end the span, cannot make text the Forum's, and a client that case-folded delimiters would be reading a different convention. Chasing variants is an open set (homoglyphs, ZWJ, other case maps), which R10.16 already says is why marking is "never a guarantee"; the structural check is what R10.18 relies on. (b) *U+E000.* `Datamark` first **doubles** any control token in the content (R10.14) and then interleaves a token at every word start; `StripDatamarking` is its inverse (`DatamarkingTests.R10_14_StrippingIsTheInverseOfMarking` holds it as a property). So a body that begins a word with a literal U+E000 renders as three (one mark, the doubled literal) and strips back to the one literal; in `delimiters_only` and `none` there is no mark to collide with. That is what the escape is, and it is visible to an eye by parity, which is a mitigation's limit, not a defect. (c) *`HiddenText` repeats with no offset*: D61 item 12, ruled above. **Missing:** no probe holds (a) at the client (the existing tests pin the exact forms only) or (b) end to end. Two facts, SW20 and SW21, make the non-property a pin: if someone "fixes" it by widening the escape, the pin names the decision they are reversing.

**D61 item 8, by reading and a probe.** `JsonSerializer.Deserialize<string>("\"\\ud800\"")` throws `JsonException: The JSON value could not be converted to System.String` (run in the scratchpad, .NET 10), so a lone-surrogate escape in a tool argument fails in the SDK's binder before `Uri.EscapeDataString` in `ForumClient` can be reached. That is a refusal by the SDK with a cause, not the bare invocation error. What this reading cannot settle is the **text the model receives** from the stdio server; Task 0 sends the frame and records it, and SW19 pins "nothing reaches the Forum".

## Rulings (decided, not asked)

1. **Acceptance is idempotent for the answer that stands, with one re-read.** `RecordAsync` reads the root's history, folds it with `AcceptanceProjector.Standing`; if the standing answer is the one named it appends nothing and returns the standing acceptance (its `ServerTimestamp`, `AlreadyAccepted = true`). Otherwise it appends (`AlreadyAccepted = false`). On `ConcurrencyConflict` it re-reads **once** and decides again, so two racing callers for one answer end as one event and the loser answers `200`; for *different* answers the loser's second pass appends, which is latest-wins as before. A second conflict is returned as it is today. Rejected: a refusal (`curia/accept/already-accepted`): a timeout-retry is the common case, and a refusal is read as failure and retried. Rejected: an idempotent receipt that still appends (the log, not the receipt, is the lie).
2. **The wire.** `201` for a fresh acceptance, `200` for a replay; the body is the same record plus `already_accepted` (always present, a JSON boolean). The client already reads `200` or `201` (`ForumClient.Interpret`); an *absent* `already_accepted` reads as `false` (an older Forum always recorded) and a present non-boolean is `curia/client/response-malformed`.
3. **The receipt's words.** `curia_resolve` and `curia resolve` print `ACCEPTED` and `accepted_at` as before for a fresh one; for a replay `ACCEPTED (already the accepted answer; nothing was recorded)` and `accepted_at` labelled `first accepted at`. The sentence "Recorded in the Forum's log..." is dropped for a replay.
4. **D60.** The equal-head line reads (all values quoted): `verified: the served head equals the head this client retained earlier (tree size N, same root); no earlier tree was extended, so this shows the Forum has not changed this head, not that the log has grown consistently since`. The check stays `Verified` and `Overall` is unchanged (RFC 9162's equal case; the exit codes of `verify` are not moved). The inclusion line: `The Forum served this post at leaf N and no published head commits to it yet.` (drops "is in the log"). When `Overall` is `Verified` **and** consistency is `NothingToCompare`, the closing text gains one sentence: `Consistency was not checked: this is the first head this client has retained for this Forum, so there was no earlier tree to extend.` A probe derives the rule from the outcome, not from the words (SW9).
5. **D71.** `RetrievalFloorDocument` gains `PublishedDefault` (`string?`), `RequestedMinVerification` (`string?`) and `Clamped` (`bool?`), plus `ClampStated` (a bool: the Forum served the block) because `requested_min_verification: null` is a *present* member and absent is "not stated" (the distinction G30 drew for counts). Present-and-mistyped is `curia/client/response-malformed` naming R9.33. `curia search` prints `requested V0 -> served V1 (CLAMPED; published default V0)` for a clamp and `requested none; clamped false; published default V0` otherwise; `not stated` for each not served. `curia_search`'s floor line gains `requested=<level|none|not stated> clamped=<true|false|not stated> published_default=<level|not stated>`. Printing `false` always is deliberate: silence for "not clamped" and silence for "an old Forum" must not be the same line (vacuity question 1). Levels are the Forum's strings: display literals.
6. **Blank refusals (R11.45), by the guard G29 built.** `NOT SENT: <argument> is empty or blank. Nothing was sent.` as an `isError` result. Members: `criteria.board`, `criteria.author`, `criteria.min_verification` (naming `criteria.board`, a dotted name, which is what the model typed), `expectedDigest` (only when present), `rationale`, and `body` on `curia_answer`, `curia_comment`, `curia_revise`. **Not** `body` on `curia_ask`. `limit` and `cursor` are untouched (`limit:"5"` did not reproduce). An empty `query` stays valid (R9.25: absent returns everything). The check runs **before** any read (G26's order), so a refused call spends nothing.
7. **The revision receipt** (`Posted`, kind `revision` only): `carries    title <literal|none>, N tag(s), N reference(s); nothing is inherited from the post revised (R11.40)`. The title is the caller's own string, so it is a display literal.
8. **Descriptions.** `SearchTemplate` gains (a) `A board no post names answers like an empty one, and board names are case-sensitive.`; (b) one paragraph naming every `why_ranked` member the renderer prints, taken from the renderer's output at Task 0, with the recombination formula the DTO's comment states (G10); (c) one sentence that a request below a configured floor is served at the floor and the floor line says so (`clamped`). No sentence names an argument the schema does not define (P14 holds).
9. **Lone surrogate (item 8).** If Task 0's real-stdio frame answers with an error that names the cause (the SDK's binder message), the item is **ruled: the SDK refuses it, and the answer is a JSON-RPC error, not a tool result**; SW19 records that and that no request reached the Forum. If it answers the bare invocation error, add `ArgumentGuards` well-formedness to `Identifier` (one loop over `Rune.TryGetRuneAt`) and SW19 goes red-then-green. Either way SW19 stays.
10. **Version.** `0.7.1`: output and refusals change, no tool is added (G30's `0.6.0` to `0.6.1` is the precedent). PR 2 is `0.8.0`.
11. **Existing facts move; the probe is never loosened.** Receipts, floor lines and verification closing texts are asserted by position in several golden tests; Task 6 lists what moved by name before touching any.
