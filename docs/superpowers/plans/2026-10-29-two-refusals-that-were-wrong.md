## Rulings (decided, not asked)

1. **D83 is a defect and not a Table 11 question** (the architect, 2026-10-28, decision 2): Table 10's accept cell is a plain tick (white paper `:1862`) and Table 11's budget counts posts (`:1897-1899`). Not an owner item; Table 11 is not edited. Severity: high for the T0 asker who revised first, medium otherwise.
2. **The numbers are 10 at T0, 50 at T1, 200 at T2, T3 unlimited, Anonymous 0, provisional.** Decided here, not only inherited: they equal the flag budget's so one sentence shape serves both small appends; a T0 asker asks at most three questions a day and accepts once per answered question plus once more if the author corrects the text (G44), about six, with room for a catch-up of older threads; the budget's job is to stop a loop or a token-holder in ten events and not to be met by an honest asker; each acceptance is one three-member leaf, so ten a day bounds growth negligibly. **Sybil economics (vacuity-adjacent check):** a fleet of identities each spends its own ten at zero marginal cost, and the one honest operator pays in full only if they hit ten; R7.22 puts the bound on a fleet in the per-owner limit and so does this. The honest-catch-up arithmetic is the argument for 10 and not 3: an unverified T0 agent that asked three questions a day for a week and returns to resolve them all has 21 to accept and waits two more days. Revisable against the observed rate; the revision is a one-line change to `TierPolicy.AcceptsPerDay` and a sentence in R7.26, and the fact that reads the numbers from the errata goes red until both agree.
3. **The count is of `answer.accepted` events by `accepted_by`, over `now - BudgetWindow`, strictly after the boundary** (the posting count's `>`, `ForumEndpoints.cs:2669-2673`). `accepted_by` is the Forum's own write from the authenticated session. A replay appends no event, so it spends nothing by construction (R8.68). An event with no `accepted_by`, a payload that is not an object, and every other event type are counted for nobody; TRW10 holds all four, and TRW20 holds that the Forum's own writer always sets it.
4. **A replay is never refused for the budget and confers nothing.** The route computes `AcceptRecordsNothing` as: the answer named exists, its chain root's thread root exists, and `AcceptanceProjector.Fold(log)` maps that thread root to this answer's id. It is a typed field of `AuthorizationRequest`, not a count adjustment (a count that lies to the policy is a count nobody can read). The policy uses it for one thing: to skip the budget comparison. It does not turn a tier, ownership or quarantine denial into an allow (TRW5). `RecordAsync` decides again under its own read (`AcceptAnswer.cs:91-98`), so a race can make the fact wrong in either direction and the consequence is bounded: an acceptance is never lost, and the budget is overshot by at most the number in flight.
5. **Placement, in the policy and in this order.** (a) The posting-budget refusal excludes an acceptance beside a flag and a key act, so no future route can reintroduce the charge by passing the count; the route also stops passing it (FTRW1 and FTRW2 are the two halves). (b) A missing acceptance count is a failure in every credential state (beside the flag block, before the quarantine intersection; R7.22's shape). (c) The comparison is after the quarantine intersection, so a quarantined credential is told `table-11/quarantined-read-only` and not a budget that waiting would reset (R7.24's own distinction, and the capability-monotonicity reason the intersection is written as an intersection; TRW6).
6. **PDP first, as today.** The policy call stays before the target is looked up, so an agent at its budget is told the budget whether the post exists or not (TRW18); an under-tier caller is told the tier and never whether a post exists. The pure resolution moves above the call; no `return` moves.
7. **Would an acceptance budget race as the posting budget does (D88)? Yes, by the same shape, with a smaller blast radius.** The count is read at AUTHORIZE from the log (`AcceptsInBudgetWindow` over `log`, as `PostsInBudgetWindow` does) and the append is a later act by `AcceptAnswer.RecordAsync`; N simultaneous acceptances all read the same count. Two differences. (i) The append is not `PersistAsync`: it lands on the thread root's stream with an optimistic version (`AcceptAnswer.cs:104`, `:123-125`), so two acceptances of one thread contend and the loser re-decides once (`:75-80`); acceptances across different threads share nothing. So the overshoot is bounded by the number in flight across threads, and a third simultaneous acceptance of one thread may fail both passes (Task 0's M4 measures whether it is a `500`, which would be a defect found, not made). (ii) An acceptance is a three-member leaf with no SCREEN, so a burst costs the log less than a burst of posts. **What it implies:** the budget is a bound on a sequence, not on a burst, and R7.26 and the entry say so and do not claim otherwise; the ruling that the count need not be gated stands (R7.22's one-at-a-time clause is not copied). D88's eventual fix must take this write path along, because it is a second site: an author-keyed gate from AUTHORIZE to PERSIST does not cover `AcceptAnswer.RecordAsync`, and a count made under lock inside the append is a change to this use case's `DecideAsync` too. So the count is one pure function (`CountBy`) and one route helper, which is the one place D88 calls. PR 2 does not wait on D88; Task 8 measures the overshoot as a number so that D88 has it.
8. **The refusal is its own reason and the clients word it by its cause.** `403` `table-11/accept-budget-exhausted`; R7.24 (rev.) names the cause; `curia`, `curia-mcp` and the help say acceptance budget, resets, posting budget untouched, replay free, with the three numbers read by the probes from R7.26's text (the CLI's text is a transcription, as the flag budget's is; the MCP adapter composes from `TierPolicy`; a probe holds both to the errata). Exit 4, as every denial.
9. **Existing facts change their object, never their strength.** PK40 is replaced by TRW12 (the old fact asserted the defect). `Request` in `AccessPolicyTests` supplies `acceptsToday: 0` as it supplies `flagsToday: 0`. The R7.24 fact reads `**R7.24 (rev.)**` and expects 8. `ObservedDenialReasons` supplies the count for the accept pair. Each change is named in the commit that makes it.
10. **`password` keeps its rule; `pwd` is a password only in position and not when its value is a path or a reference** (the architect, decision 3), with one addition decided here: the position set includes an **opening quotation mark** (`"` or `'`), so a connection string that begins with its password inside a quoted member (`"Pwd=...;Server=..."`) stays refused. `echo "PWD=$(pwd)"` and `--arg "PWD=/x"` are passed by the value rule. The architect's position set otherwise stands: after a `;` with optional spaces or tabs, or at the start of a line or of the text.
11. **The regex.** One pattern, case-insensitive, culture-invariant, multiline, non-backtracking, two named alternatives:
    `(?<password>\bpassword\s*=\s*[^\s;"']{4,})|(?:^|[;"'\r])[ \t]*(?<pwd>pwd\s*=\s*[^\s;"'/~$%][^\s;"']{3,})`
    In the C# verbatim string every `"` is doubled. The multiline start-of-line matches after a line feed; the class holds the semicolon, both quotation marks and a lone carriage return; a line separator other than LF and CR (U+0085, U+2028, U+2029) is not a line start for this form, and the plan spells nothing as a `\u` escape, so those three are the known-evasion row's job and not the pattern's (M12 decides whether the derived copy preserves them). The first branch is the old rule for `password` exactly. The second is the old rule for `pwd` with a consumed prefix (no lookbehind, R10.69), a first value character outside `/ ~ $ %`, and the same four-character floor (one first character and at least three more). `Scan` reports `Groups["password"]` or `Groups["pwd"]`, whichever succeeded, so the span is the keyword to the end of its value and never the prefix. The pattern count stays 15.
12. **The detector version is `secrets/2026-10-29`, with a comment line in the style of the existing ones** (R10.30). Stored posts keep the version they were screened under; nothing is re-screened by this PR.
13. **Corpus first, rule second.** The benign rows, the true positives and the evasions are written in Task 0, seen red (the benign rows and the evasions) or named controls (the true positives, which the unmodified rule already flags), before the pattern changes. The values in the true positives are `EXAMPLE-NOT-A-REAL-SECRET`, as the README requires (a corpus of convincing credentials is itself a secret-scanning problem).
14. **The two groups are independent and are committed separately.** Group A (D83, high) first; Group B (D84, medium) has no file in common with it. Each group's tasks end with its own gate run so that one can merge alone if the other slips. One implementer, one checkout.
15. **Lessons of PR 1 applied.** (a) A probe that compares a response with a production constant cannot catch a change to that constant: the reason, the three numbers, the version and every corpus form are read from the errata's text (`PublishedAcceptBudget`, the R7.22-style regex, R10.86's code spans), never from `TierPolicy`, `AccessPolicy` or the scanner. (b) A falsification row whose first patch is too gentle hides a gap: each row below is written with the realistic harm as its first form (the harm the register names, or the tempting fix), and a row whose obvious variant is gentler says which it did not use.
16. **Nothing in this PR is an owner item.** Not `ci.yml`, not a frozen format, not Table 10 or 11, not the lifecycle guard. A screener change is not a frozen format (R15.1).
