## What the reading found that the register did not know

1. **D95 cannot be fixed at the validator alone, and cannot be fixed at the store alone.** Making the store report (the register's own sentence: "the store reports a failed read as a failed `Result`") turns eleven call sites of `ReadEventsAsync` (`ForumEndpoints.cs:2699`) into `403 table-10/denied tier=Anonymous`; leaving the store throwing leaves the `Result` arms unreachable against Postgres. The plan therefore **removes the swallow in the same task as it adds the mapping** and rules that the store *throws*, not reports (G52 decision 2).
2. **A `Result` is the wrong carrier even on its own terms.** I read every caller that propagates a failed read: `ParentLookup`, `EnrollAgent`, `EnrollIdentity`, `AttestOwner`, `RaiseFlag`, `AcceptAnswer`, `ApplyModeration`, `KeyActs` pass the error up, and the routes answer it six different ways. `StatusForKeyAct` (`:3307`, its `LogUnreadableType => 503` arm `:3336`) maps the type to `503`, but `ForumEndpoints.cs:675` (enrollment), `:1069` (PERSIST) and `:2054-2058` (the accept record; only `Contended` is `503`) answer **a use case's failed `Result` as `500` whatever its type**, and the flag route's `StatusFor` answers a type it does not list `400` (`:1271`), the sixth way. *(Amended by Task 0, M7: the plan's third site `:1871` is the lifecycle approval record, not a store failure; a moderation record has no HTTP route.)* A reported failure would have reached `500` or `400` at those sites even after the swallow was gone. The fix is that `Problem(status, error)` (`:2935`), the factory every route calls, maps either type to `503` whatever status its caller chose.
3. **The gates already hold the classification, twelve times.** `PostgresAgentWriteGate.cs:123,128,173,177`, `PostgresRevisionGate.cs:81,88,142,146` and `PostgresFlagRaiserGate.cs:93,100,154,158` each catch `NpgsqlException` and `TimeoutException` directly: a fault wrapped one level deep (an `InvalidOperationException` or `AggregateException` around a driver fault, which a pool timeout may be) escapes a gate that was written to catch it. One predicate walks the `InnerException` chain.
4. **The Api suite's hosts do not show the defect as Production does.** *(Amended by Task 0, M9: the first version said the in-process host rethrows to the caller; it does not.)* Both fixtures run in `Development`, where ASP.NET's developer exception page answers an unhandled exception `500` `text/plain` with the exception's text and stack as the body (2 to 4 KB, measured for an `InvalidOperationException` and for an `NpgsqlException` around a `TimeoutException`, on a read and on a token-bearing write, on both hosts). The body-less `500` the live Forum answers is Production's. So a probe over these hosts sees a third thing, and one that leaks (the page carries the message); a probe that says "a body-less 500" is red only on a Production host. The probes' assertions are the same in both environments (a `503` problem document, a body without the sentinel); the environment changes the recorded red text, and the real-store legs run Production (ruling 11).
5. **A body-less `500` is a refusal that "names no problem type".** The client reports `curia/client/unreadable-problem` for it (`ForumClient.cs:579`). G52 decision 9 makes the unclassified exception a problem document too, so the only `500` left says what it is.
6. **The token route spends the client's `jti` before it reads the log** (`TokenEndpoint.cs:140-148`: `ConsumeAsync`, then `ReadAllAsync`), so a store fault after it makes the identical request a replay. *(Amended by Task 0, M3: only when the fault follows the key read, which precedes the consumption; a fault at the key read spends nothing. The replay is `401 invalid_client`. Against Postgres the fault is a body-less `500` and not `server_error`, whose arms need a reader that reports.)* The reference client builds a new assertion and proof per call (`ForumSession.cs`, `_signer.ClientAssertion(endpoint, now)`), so its retry is fine; R5.23 states it for any other client.
7. **A write route's receipt is the thing that must not read a store after the commit.** D92 did it for the vector; the budget receipt is "computed inside the hold, no second read" (R7.29). Whether the post, accept and flag routes read anything else after their append is read, not run: M5.
8. **The fuzzer's oracle is blind to this in the way D61 item 49 names for another reason**: it runs a healthy store and counts any `5xx` as a finding. The sweep this PR adds arms the fault *after* the exemplars are seeded.

## Rulings (decided, not asked)

1. **The store throws; it does not report.** A `Result` can be read as empty; an exception has one meaning at one place; twenty callers and five mappings cannot be audited into agreement (reading finding 2). The operator keeps every word the driver said as the wrapped exception, which a failed `Result`'s `Detail` (reduced to the slug by `LogBoundKeys.LogUnreadable`) would have lost.
2. **The swallow is removed in the task that adds the mapping**, never before and never after.
3. **One predicate, by type, walked to depth eight, shared by the gates and the edge.** Rejected: SQLSTATE classes (a drifting list); `Exception`.
4. **One outermost middleware and one factory; `Problem` carries the mapping** so the three sites that answer a use case's failure `500` are covered without a status edit each.
5. **Two 503 types** (`log/unreadable` = a read, nothing recorded; `store/unavailable` = anything else, unknown) and one OAuth code; **an unclassified exception is `500 curia/server/fault`**, a problem document.
6. **A committed act is answered from what it holds** (R8.82), proved by a fault armed after the first append.
7. **No `Retry-After`, no new exit code, no client retry.** The words carry the repeat rule. *(Amended 2026-10-31, ruling 21: the second sentence of the first form, "the refusals that make a repeat safe already exist", is true of the same bytes and false of the verb run again; see rulings 21 to 26.)*
8. **The Kestrel host carries the probes that need a real socket and a real client** (ULG4, ULG19 to ULG24, ULG39, the client's parse of the problem document); the in-process host carries the sweep. *(Amended by Task 0, ruling 10: the in-process host does not rethrow; its red is a `text/plain` developer page, as Kestrel's is.)*
9. **The real-store faults are made, not simulated:** `REVOKE SELECT ON events` from the app role (restored in a `finally`, and checked restored by a test-end assertion), a row-level-security policy whose function raises on rows only a whole-log scan reaches (the D90 PR's Task 10 method), and a Forum run at `Maximum Pool Size=4;Timeout=1`. *(Amended by Task 0, ruling 13: the first two on a host that connects as the application role, which no Api fixture did.)*
