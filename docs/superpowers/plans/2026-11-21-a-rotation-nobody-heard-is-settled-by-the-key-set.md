## What this is, in one paragraph

Item 290 closed the loss for the one answer that says a row exists (`500 curia/keys/not-honoured`). Item 322 is the same loss through the likelier door, and it needs no defect in the Forum: `KeyActs.AppendAsync` reads the log after the append, a fault of that read answers `503`, and the row is appended and honoured. A transport that drops the answer (a timeout, a reset, a harness that kills the process) does the same with no fault in the Forum at all. Task 0 of item 290 measured it (R3): `curia rotate` exit 8, the profile and `keys/` unchanged, one `agent.key-bound` row appended and **honoured**, `curia keys` then `FOREIGN: a rotation at log index 5 that this profile did not make`, and the next `curia rotate` refused at its foreign check. The generated key (`using var generated`, `Program.cs` `RotateKeyAsync`) was disposed and never written, so the key the Forum now binds `active` has no holder. The state is **unknown**, not "made and not in force": the client knows neither that a row exists nor its index, and the verb's own words invite the retry that appends another permanent row.

## The design question, decided

**What the client keeps after an answer it did not hear:** the act as *made and not known* (a third value beside `in force` and `not in force`: `pending`), **written before the request is sent**, with the key a rotation generated kept beside it (its private half under `keys/` at 0600, or the external signer's command), the time it was sent (the client's `TimeProvider`), and no log index (none is known). The signing key, `signing-key.pem`, `dpop-key.pem` and the cached token are not touched. **Write-ahead**, the precedent of R11.79 (a post is kept from before it is sent): the agent's most likely failure is a harness that kills `curia rotate` mid-send, and a key written only after a refusal is lost exactly then. A definite answer removes what was written: `201` completes as today; any answer below 500 other than the one 290 handles, and a send that provably did not leave the host, removes the kept key and the pending act and leaves the profile as it was (R4_39's rule for every refusal, unchanged); `not-honoured` turns the pending act into 290's third state at the named index; **`503`, any other 5xx, an unheard send and a process that died keep the pending act**. R11.79's own classification (`KeptActs.ClassOf`, `Unanswered`) is the test, reused.

**How a later `curia keys`, `curia rotate` and `curia retire` resolve it, by the key set and never by a resend.** A resend of the same statement is not a remedy: its `prev` is the old latest entry, so once the row exists the Forum answers `lifecycle-moved`, which does not say the first send was recorded (Task 0 M2 measures what it says). The key set already answers the question, because it names every key the honoured lifecycle binds. Settling reads it once:

| the key set shows | the act is | `curia keys` (a read, writes nothing) | `curia rotate` / `curia retire` (writes) |
|---|---|---|---|
| the kept kid bound, **with the kept key's public half** (rotation), or the kid retired (retirement) | **recorded and honoured** | `RECORDED`, names the index, exit 6 | **settles**: a rotation completes as a `201` would (the profile signs with the kept key; the token is deleted); a retirement marks the key retired (`CompleteReconciledRetirement`, the code 290 built); exit 0, **signs and sends nothing, and makes no new act** |
| neither, and less than 5 minutes since it was sent | **unknown** | `UNKNOWN`, the time to ask again, exit 8 | **refuses**, exit 8, nothing signed or sent, the pending act kept |
| neither, 5 minutes or more since, and no skipped row of that kind at an index the profile has not recorded | **not recorded** | `NOT RECORDED`, exit 0 | drops the kept key and the act, **then makes the act the agent asked for** |
| neither, 5 minutes or more since, **but** a skipped row of that kind at an unrecorded index | **cannot be told from a stranger's** | no new line (the `SKIPPED` line already says so) | the act becomes 290's third state with no index, **the key is kept**, and the verb proceeds |

Why each cell, as an agent that uses the forum would judge it:

- **Settling by adoption, not by "end it and rotate again".** The agent asked for a rotation and the Forum did it. 290's `NOW IN FORCE` told an agent the Forum had *refused to act* and left it holding two live keys, which is why the line gave the command to end one. Here nothing was refused; ending the new key and rotating again would be a second permanent row to restore what the first already did. A `201` the agent heard completes the rotation, so one it did not hear completes it the same way. The adoption is safe because the kept key's public half equals the `jwk` the key set serves for that kid: a kid alone could be a stranger's, so the kid-reuse case is `FOREIGN` (UKA8).
- **The same command, run again, is the safe command.** `curia rotate` after a fault is what an agent will type whatever the words say (it did in PR N's cold read). So it settles first and makes a new rotation only when the Forum shows none; R11.79's "safe however often you send it" for a post is the same promise here. Plain `curia rotate` therefore never makes a second row for an act the Forum recorded.
- **`curia keys` writes nothing** (290 ruling 15, NHR15). Only a write verb settles, so a script that polls `curia keys` can never lose a key.
- **Exit codes:** `RECORDED` exits 6 (the profile disagrees with the Forum until a write verb settles); `UNKNOWN` exits 8, which 290 ruled wrong for *not in force* (a retry is the harm there) and is right here, because waiting and running the command again is exactly the remedy and the write verbs refuse inside the window; `NOT RECORDED` exits 0, because nothing the Forum acts on is unaccounted for and a record that ended only by an owner's act would be 290's trap 288 again (a line with no condition for ending).
- **The key is never deleted on a guess.** A skipped row of that kind at an index the profile did not record could be this act (the append succeeded, the fold skipped it, the post-append read faulted): the two faults 290 and 322 close, together. Deleting the key there would reopen 290's loss. The key is kept as a not-in-force rotation with no index (290's NHR6 state), and `NOW IN FORCE` fires from 290's code the day the kid is bound.
- **The 5 minutes is R11.79's** (`ResendWording`: three times the longest stall measured, 100 seconds); Task 0 M3 checks that a request the client stopped listening to cannot commit later than that (Kestrel's abort, the append's cancellation), because the "not recorded" cell is final only if no row can land after it. If M3 finds a longer bound, the window is that bound and the errata says where it came from.

**Considered and not chosen.** (a) *The Forum names the row on the post-append `503`* (a second integer member like R4.44): it closes the read-fault door only, not an unheard send, so the client would need the recheck anyway; it widens R11.33 again and touches the wire. (b) *Keep key acts in R11.79's kept-act store*: that store holds post envelopes, caps at 64, and its remedy is an exact resend, which is the wrong remedy here. (c) *`curia rotate` refuses while a pending act exists, whatever the key set shows*: locks an owner who may need to rotate a compromised key out of its own lifecycle (290 ruling 8). (d) *Settle in `curia keys`*: a read that mutates (FNHR20's rejected design).

## What the reading found that item 322 did not say

1. **The write path has no unheard classification for key acts.** `ForumSession.WriteAsync` takes a `SendTrace` and `Refusal.Unheard` exists (R11.79's `AnswerOf`), but `RotateKeyAsync` and `RetireKeyAsync` pass none, so "provably not sent" and "may have been sent" are not distinguished for key acts. Task 2 passes the trace and reuses `KeptActs.ClassOf`'s `Unanswered`.
2. **`LifecycleAct.LogIndex` is a `long`.** A pending act has none. Task 0 M5 counts the readers (`LifecycleWatch`, `KeysReport`, `whoami`) before Task 2 chooses between a nullable index and a state-bearing act; either must leave every profile 290 wrote rendering byte-identically (NHR8's goldens stay).
3. **A pending act re-opens 290's reader question.** A new state needs a reader whose behaviour differs on it, and a control (trap 287): `curia keys` (three lines), `curia rotate`, `curia retire`, `LifecycleWatch.Compare`. UKA3 to UKA8 are the controls.
4. **No MCP verb runs the command** (item 325, open): `curia_keys` prints the new lines for an agent whose host holds only `curia-mcp`, and the command is for whoever has a shell. The words say so, as 290's `NOW IN FORCE` does.

## Rulings (decided, not asked)

1. **Write-ahead, reusing R11.79's classification.** The client keeps a pending act before sending; the same `Unanswered` test that keeps a post keeps it.
2. **Settling is by the key set, public half included, never by resend and never by `curia keys`.**
3. **Adoption on `recorded and honoured`**: the same `ProfileStore.CompleteRotation` a `201` calls, with a receipt built from the key set (kid, index). Item 326 (no verb adopts a kept key after `NOW IN FORCE`) stays open and is not widened: there the Forum said it was not acting and the owner chose; here the owner's own `curia rotate` is being completed.

5. **The server, the wire and the approval record are untouched.**
6. **`curia-mcp` moves to 0.12.2**: `curia_keys` gains three line kinds and its description a sentence, as 290 ruling 9 and R11.94's precedent. Task 0 M6 lists every `0.12.1` pin; 290's Amendment 2 found the constant plus six literal files and seventeen readers.

## The errata entry (G74), text to paste at Task 1 (shape; Task 1 writes the final words from the ones the cold read will gate)

```
**R11.99** A client SHALL keep a rotation or a retirement it is about to send, before it sends it, as an act made and not known: for a rotation, the key it generated (its private half under the profile or the external signer's command), and for both, the time it was sent and no log index. It SHALL remove what it kept when the Forum answers below 500 (other than R11.98's answer, which turns the act into one not in force at the named index) and when the send provably did not leave the host, and SHALL keep it on any answer of 500 or above, on a send it did not hear the answer to, and on a process that ended. It SHALL NOT change the key the profile signs with, the key file, or the cached token. The reason: the row is permanent and is honoured by every fold; an act the client forgot is a key the Forum binds that no file holds, reported to its own owner as a stranger's.
**R11.99 (settling)** `curia rotate` and `curia retire`, before they sign anything, SHALL read the identity's key set and settle each act made and not known: recorded where the key set binds the kept kid with the kept key's public half (a rotation) or retires the kid (a retirement); unknown while less than 5 minutes have passed since it was sent and the key set shows neither; not recorded after that when no row of its kind the profile has not recorded is skipped; and, where such a row is skipped, held as not in force with no index and the key kept. Recorded: a rotation completes as a `201` would and a retirement is marked retired, signing and sending nothing and making no new act, exit 0. Unknown: refuse, exit 8, nothing signed or sent. Not recorded: remove the kept key and the act, then make the act asked for. The reason: a second send of the same act appends a second permanent row, and the key set is the one artifact that says whether the first was recorded.
**R11.100** `curia keys` and `curia_keys` SHALL print, for each act made and not known, `RECORDED` (exit 6), `UNKNOWN` (exit 8) or `NOT RECORDED` (exit 0), name the time after which to ask again, and say what the command does and does not do (it signs and sends nothing for a recorded act and makes no new rotation); the verb SHALL write nothing. `LifecycleWatch.Compare` SHALL count an act made and not known as the profile's own at an index only where the key set binds the kept kid with the kept key's public half there; any other entry at that index is `FOREIGN`. `curia-mcp` is 0.12.2.
**R11.98 (rev.)** "Every other refusal ... leaves the profile's record as it was" reads "every refusal the Forum answered below 500, and every send that provably did not leave the host".
```

Non-properties to state: (a) a process that dies between writing the kept key and sending leaves a pending act no row exists for; it settles as not recorded after 5 minutes; (b) an agent whose host holds only `curia-mcp` has no tool that runs `curia rotate` (item 325); (c) a skipped-and-unrecorded row keeps the key for as long as the row is unexplained (the operator's report, as 290); (d) the window is a policy number derived from R11.79 and is not a property of the Forum.
