## Rulings (decided, not asked)

1. **`excluded_by_floor`, in the floor block beside `excluded_disputed`, computed as `fused.Length - admitted.Length`** at `HybridSearch.cs:115`, before `Diversify` (`:116`, which defers and never drops) and before the window (`:118`). `ForumEndpoints.cs:216`-`:224` gains `[property: JsonPropertyName("excluded_by_floor")] int ExcludedByFloor`; the construction at `:1789`-`:1795` passes `page.ExcludedByFloor`. **`SearchPage` gets the member with no default, and `ExcludedDisputed`'s `= 0` (`HybridSearch.cs:43`) is removed**: a forgotten pass-through must not compile into "the floor removed nothing" (vacuity question 3). One construction site exists (`:123`), so the removal costs one line. Every page of one query states the same number because the list is fixed by the cursor's bound, the query and the floor. **The list is the fused candidate list, which each channel cuts at `HybridRanking.CandidateDepth` (200, `HybridRanking.cs:47`; the vector channel at `HybridSearch.cs:156`), so the count is a lower bound on what the floor hides from the corpus, not a corpus count.** R9.24 (rev.) and R9.30 both say "from the fused candidate list", so this is the requirement read exactly, and the readers' wording says "removed by the floor" and not "hidden"; the plan records it so that no reader's text promises a corpus total.
2. **Only the floor has a count** (R9.30; G30 decision 3). `q`, `board`, `author`, `kind`, `tags` narrow the corpus before `HybridRanking.Rank`; what they exclude was never in the fused list. The answer to R9.24 (rev.)'s "every other criterion that removed results" is none today. Probe S2 holds the corollary: a floor over a candidate list of ungradable kinds states `0`. A test (S12) classifies the ten members as filter, floor, paging or presentation; an unclassified eleventh fails by name, so a future criterion that removes from the fused list cannot arrive without its decision.
3. **Always stated; absent means "not served", not zero.** Forum side: the member is always present. Client side: `RetrievalFloorDocument` gains `int? ExcludedByFloor` and `int? ExcludedDisputed` (after `NotApplicableTo`, `ForumDocuments.cs:82`-`:83`), parsed beside the other floor members (`:367`-`:372`) with `ClientJson.Member` (`ClientJson.cs:114`) to tell *absent* from *present*, then `ClientJson.WholeNumber` (`ClientJson.cs:104`, which is null for a fraction and a non-number alike, so the presence test must come first; `corpus_bound` at `ForumDocuments.cs:374` uses `ClientJson.Number`, `:93`, and a cast, which would truncate a fraction and is not the model here). A member that is present and is not a non-negative integer (a fraction, a negative, a string) is `Result.Fail(ClientErrors.ResponseMalformed("search page states a floor count that is not a count (R9.30)"))`; it is not coerced. An absent member is `null`. Nothing in the repository constructs `RetrievalFloorDocument` outside `:367`.
4. **A withheld post is in neither count.** `SearchProjector.Fold` drops it before fusion (`SearchProjection.cs:70`, which skips what `FlagProjection`'s `MayServe`, `FlagProjection.cs:20`, says may not be served); `excluded_by_floor` is computed after, so it inherits that. S7 holds it. Without the probe, "withheld posts do not leak into a count" is a sentence in an errata paragraph (R9.24 rev.'s confirmation-oracle clause).
5. **Disputed and floor are disjoint.** `excludedDisputed` counts the disputed posts in `diversified` (`HybridSearch.cs:121`), the floor's survivors; a disputed answer below the floor is counted by the floor and not by dispute. S5 pins it (a post counted twice, or by the wrong one, is the failure).
6. **The renderers ride in this stage (reversed from v1).** v1 deferred `curia search`'s floor line and `curia_search`'s floor block and description to a stage after G28 because those files were in flight; G28 and G29 have merged, so the reason is gone, and two reasons for riding are new.
