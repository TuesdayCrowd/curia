## What this is

The Forum reads a request body with no bound of its own. G83 specified R6.68 and shipped the pack without it; the bound in force is the host's default of 30,000,000 bytes, and the edge's 1 MiB is the only 1 MiB bound. Task 0b measured about 5 bytes of resident memory per body byte for an `a`-filled body (8 x 29 MB: +1,140 to +1,228 MiB on three routes; the live run measured the worst shape at about 10). This stage builds the bound, where it can be probed on the host the suite already has, and closes what the measurement found beside it: the post route answers an **empty-bodied** `413` in Production (R11.33 violated) and a developer page that **echoes `Authorization` and `DPoP`** in Development.

**Not in scope:** tightening any route below the global figure (lead, item 399 (a)); a cap on bodies in flight (the edge's, item 399 (b)); moving the three binder routes onto R11.34's guarded reader (lead (d)); a start refusal for Development with a public origin (ruled below, lead (c)); `.github/`, `db/`, conformance vectors (the bound is the host's and R6.39's four vectors are unchanged), Rust, the approval record and the lifecycle guard. `curia-mcp` stays 0.12.8; no client change is expected (the client screens R6.39 locally and never sends past it), and Task 0 checks that rather than assuming it.

## Rulings (decided, not asked)

1. **The control is one middleware, not Kestrel's `MaxRequestBodySize`.** D125's lead said a global Kestrel limit. Rejected, for three reasons read from the code. (i) Kestrel's limit fires on the **first read** of the body and throws `BadHttpRequestException` out of whichever handler reads; on the post route that exception passes `UseStoreFaults` (which excludes it) and `UseStatusCodePages` (which only fires when `next` returns) and reaches the host's own writer: that *is* the measured empty 413 and the Development page. A limit at the host needs a catch at every reading site (`SubmitAsync`, `ReadKeyActBodyAsync`, the token endpoint), three places to forget; a middleware has one. (ii) `TestServer` does not enforce the limit, so every probe would need Kestrel (ten fixtures) and the in-process suite would stay green with the limit deleted; a middleware is enforced identically on both hosts, so BND1 to BND9 run in-process **and** on a socket. (iii) It makes the declared case a check on a header before any handler runs, which is R6.68's "before a handler reads past the bound" in its plain meaning. **Shape:** `app.UseBodyBound()` placed immediately inside `UseUnreadableRequests()` (so the status it sets is composed into a problem document, or RFC 6749's object at `/oauth/token`, by the one function that already does that for 400, 404, 405, 413 and 415), before `UseUtf8JsonBodies()` and before routing: (a) a declared `Content-Length` greater than the cap sets 413 and returns, on every method and path, mapped or not; (b) otherwise `Request.Body` is replaced by a counting stream that throws `BadHttpRequestException(…, 413)` on the byte after the cap; (c) one `catch (BadHttpRequestException e) when (!Response.HasStarted)` around `next` sets `e.StatusCode` and returns. The cap is `AdmitLimits.Default.MaxBytes + 1`, read from the definition (a fence, Task 5). **Fallback if Task 0.2 shows the binder or the form reader bypasses the replaced `Body`:** also set `IHttpMaxRequestBodySizeFeature.MaxRequestBodySize` in the same middleware, and give each of the two controls its own probe row (a control with no probe that reddens on its deletion is a restatement). **What would reverse this ruling:** Task 0.2 finding that the replacement stream is not what `ReadFromJsonAsync` or `ReadFormAsync` reads and the feature being unavailable on a host the Forum runs on.
2. **Reads do not become streaming.** ADMIT and VERIFY need the whole document (a parse to a tree, re-canonicalization, a signature over bytes), so the post route is whole-buffer by construction and stays so; the three binder routes buffer the JSON they bind; the token route's form reader has its own limits. The measured amplification is a property of **size**: at 1 MiB the eight-body deltas were +21 to +44 MiB (2.6 to 5.5 MiB per 1 MiB body), at 29 MB +1,140 to +1,228 MiB. The bound takes the worst case from about 150 MiB per body to about 5.5 MiB per body (28x). **The stage does not change `SubmitAsync`'s `MemoryStream` + `ToArray` copy** and therefore does not need to be shown to leave the copy's cost alone. A rule committed before any measurement: **if Task 0.8's eight concurrent at-cap bodies show a delta over 64 MiB on any of the five routes (8 bytes per byte), an exact-size read is filed as item 399 (b) and this stage is not widened; if not, nothing is filed.** The bound is per request: **the number of bodies in flight is not bounded** (the post route copies before the R7.27 gate; three routes need no credential), and R6.68's reason must not say otherwise. That is the edge's burst and the owner's memory limit, and the runbook says so.
3. **R6.68's text is revised (rev.), four points**, and Task 1 writes them: (a) "an RFC 9457 problem document on every route" contradicts R11.33 at the token endpoint; add "and at `/oauth/token` RFC 6749's error object (`invalid_request`, status 413)", which `UnreadableRequests` already composes; (b) "a figure it holds itself **and publishes**" has no publication: nothing serves the figure and the white paper states R6.39's number, not this one. Replace by the figure stated in the requirement (R6.39's size plus one byte, 1,048,577) so that a probe parses it from text and not from `AdmitLimits`; (c) the reason says "three routes read a body with no credential"; **a fourth does**: `RaiseFlagAsync` takes `FlagRequest` as a binder parameter, so the binder reads the body before the handler authenticates, and R10.68's rationale cap (4,096) is checked after that (Task 0.1 confirms by a measurement and the reason is revised only if it holds); (d) add the second sentence: a request the host's own reader rejects while a handler reads (too large, too slow, wrongly framed) is answered by R11.33's rule and never reaches the host's own response writer, because that writer's answer is empty in Production and in Development a page that echoes the request's headers. R10.68 gets "which R6.68 bounds" for "which the host's own limit bounds".
4. **The Development exception page: a probe for every route the host can reject, and no start refusal.** Ruling on how far it goes. The page is reachable only by an exception that passes `UseStoreFaults`, and `UseStoreFaults` catches every one except `BadHttpRequestException`. After this stage that exception never leaves `UseBodyBound`'s catch while the response is unstarted, so **no request the host rejects reaches the page**; BND6 sends each such request (declared over cap, chunked over cap, a stalled body for the host's minimum-rate refusal, a malformed chunk frame) at the post route on a Kestrel fixture **started in Development**, asserts a problem document and that the body contains neither `Authorization` nor `DPoP`, and is shown able to see the page by the revert row (FBND7). What this does not prove: that no other exception class could bypass `UseStoreFaults` on some future route, or that a hosted Forum is not Development. **A start refusal (Development with a non-loopback origin) is not built here.** It would be a new refusal at start, an unhandled exception today (item 393), with words to cold-read and a fixture change (the fixtures run Development), and the unit ships `Production` and DPK reads it. Filed as item 399 (c) with its probe named: a start with `ASPNETCORE_ENVIRONMENT=Development` and an `https` origin must fail, and a revert row must turn it green.
5. **`BCAP1` and `BCAP2` are inverted in Task 2 and deleted in Task 4**, in that order, so that the stage shows them red against the built bound **for their own assertion** (the checked-in `red-bcap-inverted.txt` method) before they go, and not merely removed.
