## What the reading found that the ruling did not know

The architect's ruling (decision 1 of 2026-10-28) decides the rule. Reading the tree to write this plan found nine facts it did not have; each changes a detail, none changes the decision.

1. **The post is appended to nothing per `prev`.** `IngestPipeline.PersistAsync` writes one aggregate per post at `AggregateVersion.New` (`IngestPipeline.cs:240`, `:257`), conditioned on the author's *key* stream (`:259`), which only key lifecycle entries move (R6.56; `IngestAttempts.cs:27-35` re-decides only that conflict). So the store gives two revisions of one `prev` nothing to collide on; there is no version to lean on, and the gate is not optional. (`PostgresEventStore.cs:162-184` is one global lock for ordering, `:186-223` the two version checks; neither knows a `prev`.)
2. **The log `SubmitAttemptAsync` holds at AUTHORIZE is older than any hold that follows it.** It is read once at `ForumEndpoints.cs:826` and used for posture, the PDP (`:836-846`), Table 10's "(own)" discharge (`:853-854`, `RevisesOwnPost`, `:1841-1848`) and the deny at `:856-859`. A successor check on that read is the race again. The check reads the log a second time after the gate is held.
3. **`ReadEventsAsync` fails open for this use.** It answers an empty log when the store cannot be read (`ForumEndpoints.cs:2362-2367`, "no events means no standing, which denies"). For authorization that is conservative; for a successor check an empty log means no successor, which allows. The read under the hold uses `events.ReadAllAsync` and answers `503` on a failure (as `ParentLookup`'s caller does, `:871-873`).
4. **There is no duplicate-envelope path to keep.** The ruling says a retry of the very envelope "is the existing duplicate path" and asks Task 0 to read which refusal that path gives. Read: `PostEnvelope.Nonce` is parsed and signed (`PostEnvelope.cs:62`, `:130`) and compared by nothing in `src/Curia.Application/Ingest/` or the endpoint; `PersistAsync` mints a post id per call (`IngestPipeline.cs:180-184`); the only near-duplicate check (`DuplicateCheck.AssessAsync`, `:55-95`) refuses a *question* only (`DuplicatePolicy.cs:53`) and only above a similarity floor. A revision is a discussion kind (`PostKind.cs:178-179`), so the check runs and annotates, never refuses. So a retried identical revision most likely stores a second post with the same digest. Ruling 6 below takes that default and Task 0 item 2 measures it. **Measured (M2): two events, `201` twice, for a revision, an answer and a comment, and a stored duplicate then makes `DuplicateCheck` throw on every later submission of that kind on that board (top note, ruling 15). Ruling 6 is superseded by ruling 17.**
5. **The model gate takes a transaction-scoped lock, not a session lock.** The ruling says "a session advisory lock". `PostgresFlagRaiserGate` is `pg_try_advisory_xact_lock` in a transaction the hold owns (`:75-80`) so a process that dies holding it releases it with its session, and the hold writes nothing (`:129-163`). The plan follows the model, which is the stricter form; a session lock would outlive its holder on a pooled connection.
6. **Both gates would share one pool of a quarter of the Forum's** (`PostgresAdapters.cs:46-53`, `:107`). The flag hold covers reads and one append; a revision hold covers the near-duplicate check, SCREEN and the append. Task 0 item 3 times a hold with a 256 KiB body.
7. **The fuzzer's revision row cannot meet the gate by accident.** `FuzzRun.SendAsync` runs the row's `Prepare` before every send (`FuzzRun.cs:331-335`), and the revision row's `Prepare` asks a fresh question each time (`Exemplars.cs:245-253`), so no send revises a `prev` an earlier send revised, and clause 4 (the exemplar is answered 2xx, `:398-399`) holds. The closed pass therefore does not reach the new refusal; the problem-document shape of the two `409`s is held by facts RVO14 and RVO31 instead. `ExpectedFaults.Rows` stays empty (`ExpectedFaults.cs:23`).
8. **R8.4 already says this.** "A revision's `prev_digest` must match the current head" (white paper §8.1, `:2012-2016`) and property P6, "a single path with no cycles and a unique head" (`:3518`), are normative, and `git grep -n "P6"` over `src/` and `tests/` finds only comments. The Forum has been producing logs that violate a property it never probed. RVO2's oracle is that property's first probe. G34 decision 3's remark that "Table 6 allows forks by design" cites the credential lifecycle table; the errata entry says so.
9. **A `409` is already a client category.** `ForumClient` maps 409 to `RefusalKind.Conflict` (`ForumClient.cs:515`), `Cli.cs:87` maps that to exit 3, and `Refusal.Summary` (`ForumResult.cs:96-128`) has one arm for the flag gate's `raise-in-flight` (`:109-111`) and a generic one (`:122`). The wording for both new refusals goes in that one place, so `curia` and `curia-mcp` (`WriteTools.cs:549-550`) cannot word them differently.

## Rulings (decided, not asked)

1. **The Forum refuses the second revision of a served `prev` under a gate** (the architect, 2026-10-28, decision 1; evidence: 5 of 5, and every fork is one author's: Table 10 "(own)" is discharged at `ForumEndpoints.cs:853-859`). Not an owner item. Severity from the agent's seat: medium, irreversible.
2. **Where.** `SubmitAttemptAsync`, for `v.Envelope.Kind is PostKind.Revision` only, immediately after the `!d.IsAllowed` return (`:856-859`) and before the R8.70 parent block (`:861`). The hold is a local `IAsyncDisposable?` released in a `finally` that wraps everything from the gate to the end of PERSIST's result handling (`:920-928`); indexing (`:934-942`) happens after the release. A lost race on the key stream returns `null` (`:925-927`), the `finally` releases, and `IngestAttempts` runs the attempt again, which enters the gate again and re-checks on the log as it then stands.
3. **The gate.** `IRevisionGate` is the flag gate's shape. The Postgres adapter is `pg_try_advisory_xact_lock(hashtextextended(key, 0))` in a transaction the hold owns, on the gate pool, key `<schema>:revision_prev:<digest>`; it never waits; an `NpgsqlException` or `TimeoutException` is `RevisionGateUnavailable`. The in-memory adapter is a try-add set of digests (R11.4). The port's parameter is a `string` that is not an identifier a caller chooses: it is a digest the route has already found in the log (`RevisesOwnPost` compared it ordinally against projected posts' digests), so the string fence gets a reasoned row (`PortStringAllowlist.cs:34` and `:42` are the precedents). Sharing the gate pool with the flag gate is chosen over a second pool; open risk 2.
4. **Served, not stored; one rule.** After the hold: `var fresh = await events.ReadAllAsync(...)`; a failure is `Problem(503, readError)` and nothing else; `PostProjector.Fold(fresh)`; the original is the post whose digest is `prev` (absent from a log that grew only by appending, so absence is `503`, never a pass); `CorrectionIndex.Fold(posts, Servable(fresh)).For(original)` filtered to `PostId is not null` (`CorrectionIndex.cs:79-86`, `:135-136`; `Servable` is `ForumEndpoints.cs:2301-2308`). The same fresh read feeds the identical-digest check of ruling 17, which runs first (a retried revision is `already-recorded`, naming its copy, and never reaches the successor check). There is no second filter for "served": `superseded_by`, the batch's `successors` and this check cannot answer differently (R9.32's reason). The refusal names the first served successor in log order.
5. **Refusals.** `409` `curia/ingest/already-revised`, title "This post already has a revision", detail exactly `successor=<post id>` (nothing an author wrote: not the digest, the `parent`, the body, the title); `409` `curia/ingest/revision-in-flight`, detail `retry once the other revision is recorded (R8.77)`, naming no post and no digest; `503` `curia/ingest/revision-gate-unavailable` through the existing `ServerFault`, whose detail is not served (`ForumEndpoints.cs:2631-2634`). A refused revision stores nothing, spends nothing (the budget counts stored posts), and is not screened. **A third `409`, `curia/ingest/already-recorded`, title "This post is already recorded", detail exactly `post=<post id>` (the Forum's id of the earlier stored copy: nothing an author wrote), answers a submission of any kind whose digest equals a stored post's (ruling 17, R8.78); it spends and stores nothing and is not screened.**

A client that sent a revision and lost the answer reads the successor and sees its own text. If Task 0 item 2 finds an existing refusal of identical bytes, **that refusal is kept first**, RVO9 becomes the control that holds it, and R8.77 narrows to "a different digest". This is the one ruling the architect should confirm before Task 1; the plan builds the default.~~ M2 found no refusal for a revision, an answer or a comment, and found the stored duplicate to be a permanent `500`; ruling 17 widens the default to every kind and renames its slug.
7. **No client retries for the caller.** `revision-in-flight` is worded as retryable and the verb or tool stops. An automatic retry would hide the refusal from the agent whose parallel call it was, and the agent should read the winner before it signs a second text.
8. **The guards stay the first line.** R11.47's and R11.51's refusals are made after a verified read and before anything is signed, so a fork they can prevent never reaches the signer. The Forum's gate is what holds after the read.
9. **Wording lives in `Refusal.Summary`.** Two `RefusalKind.Conflict` arms, keyed by `Error.Type`, one function for `curia` and `curia-mcp` (`ForumResult.cs:109-122`, `WriteTools.cs:549-550`). Exit code 3 for both (`Cli.cs:87`); the entry for 3 in `Help.cs` gains `curia/ingest/revision-in-flight` beside `curia/flag/raise-in-flight` as the retryable one (`:295-298`).

11. **No stream change.** Nothing is appended for a gate; no migration; the event payload and R15.1's set are untouched. Logs that already hold a fork replay as they did.
12. **CS-15: a gate must not become a second write path.** `IRevisionGate` has one member and no store; the Postgres adapter writes nothing and takes a `NpgsqlDataSource`, not an `IEventStore`; the route holds `IEventReader` for the check and reaches the writer only through `IIngestPipeline.PersistAsync`. 14. **Not an owner item.** No frozen format, no `ci.yml`, no Table 11. The standing owner items (D10, D41, the guard lift, any PR touching `ci.yml`) are untouched.

> **D82 — closed by the "A post is revised once" PR (errata G45: R8.77, R11.61; `curia-mcp` 0.8.8).** The Forum refuses the second revision of a post that already has a served one. A revision is entered, after AUTHORIZE and before the parent checks, the near-duplicate check, SCREEN and PERSIST, under a gate keyed by its `prev` (`IRevisionGate`, the shape of the flag gate: a try-only transaction-scoped advisory lock on the gate pool; no table, no migration), and the Forum reads the log again under the hold and refuses `409` `curia/ingest/already-revised` (detail `successor=<post id>`) when `CorrectionIndex.For` lists a revision it serves, or `409` `curia/ingest/revision-in-flight` when the gate is held, or `503` `curia/ingest/revision-gate-unavailable`; a revision the Forum does not serve does not count; a retry of the same bytes is refused as already revised; the hold is released on every path. Property P6's first probe: the events table never holds two served revisions of one `prev` after a race of 2 and of 8, 50 repetitions each. The clients' guards (R11.47, R11.51) stay the first line; `curia` and `curia-mcp` word the two refusals by their cause (R11.61). The event's payload is unchanged; R9.43's `fork`, `recheck` and every FORKED word stay because they describe logs that already hold a fork. Probes RVO1 to RVO52 (seen red first; the controls named), falsification FRVO1 to FRVO44. **D87 closes with it** (R8.78, R9.47): digest-keyed structures tolerate a repeated digest (first in log order) and an identical resubmission of any kind is refused `409` `curia/ingest/already-recorded`.
>
> **D87 — a stored duplicate digest makes every later submission of that kind on that board a 500, permanently** (see `IMPLEMENTATION_PLAN.md`; found by this PR's Task 0, M2; closed by this PR).
>
> **Trap 49.** A map keyed by a value the writer never made unique is a write that was safe on the day it was written and a crash on the day the writer retried. `DuplicateCheck` built `ToDictionary(p => p.Digest)` over a log in which nothing forbade two posts of one digest, and its author tested a log in which that never happened; two other structures in the same directory used `TryAdd` for the same key. ## Open risks (named so the reviewer can look)

1. **The second full-log read under the hold** (finding 2). **Measured (M5): 39 ms at 1,000 events, 175 ms at 10,000, 2.3 s at 100,000; ruled acceptable at this stage (ruling 20).** The remedy named is a narrower reader port for "the served revisions of this digest"; `ReadByAggregateAsync` cannot be it (a successor is another aggregate) and the `prev` sits inside the payload's `canonical` text, so it needs an index, which is a `db/` change; named, not built, with its trigger in ruling 20.
2. **The gate pool is shared with the flag gate and the revision hold is longer than a flag hold** (finding 6). **Measured (M3): the pool is 25, a hold is about 80 ms at the largest legal body (261,900 bytes), 23 ms at 2 KiB; not material by this measure.** A burst of revisions of distinct posts holds one connection each through the near-duplicate check and SCREEN; past the pool's size they are told `503` `revision-gate-unavailable`, and flags share that exhaustion. M3 times a hold. If it is material, the revision gate takes a pool of its own; the order of acquisition (gate before Forum) already rules out a deadlock between them.
3. **Ruling 6 departed from the ruling's parenthetical (finding 4), and M2 confirmed the default: the retry is stored; ruling 17 refuses it for every kind as `already-recorded`.** A client that lost an answer is told its earlier copy's id. An idempotent `200` for the retry would be better for an agent and is a new response shape for `POST /v1/posts`; not built, named.
4. **The posting budget is counted before the hold** (M8). **Corrected by M8: all N concurrent requests pass AUTHORIZE and, without a gate, all N are stored (a T0 author at one post stored eight); with this PR's gate only revisions of one `prev` are held to one, and every other simultaneous submission of any kind is uncapped.** Register **D88**, not this PR (ruling 19).
5. **A stored fork is refused a third revision naming one successor.** An author of a forked post is told one id and `recheck` tells both. Recorded in G45 (non-property d). **M4 C8: a fork with one branch withheld still reads FORKED while the route's served-only check sees one served successor.**
6. **A moderator's restore can still make a fork** (RVO4 (c)); FORKED tells it. The remedy is a moderator's, as ever.
7. **Transaction-scoped, not session-scoped** (finding 5). The plan departs from the ruling's wording for the model's form; if the architect wants the session form, the pool-return hazard is the argument against it.
8. **The seams are decorators on `IEventStore`, `IPolicyDecisionPoint` and `IRevisionGate` registered through `ConfigureStore` and `ConfigureServices`** (`IngestContentionTests.cs:19-41`). A refactor of the fixture's composition would make a seam silently inert; RVO1 and RVO12 fail by name when their request never parks, so an inert seam is a red and not a pass.
9. **RVO2's cost.** 100 repetitions each with a question and N revisions. If the Api suite's wall clock rises materially, repetitions share a host and a T1 author with the clock advanced, which `FuzzRun.cs:333` already does.
10. **Identifiers are provisional** (see the top): G45, R8.77, R8.78, R9.47, R11.61, D87, D88, 0.8.8, traps 48 and 49, prefixes RVO and FRVO.
12. **The tolerance commit is the only part of this PR that closes an availability defect**, and it is sequenced first (Task 10) so that a slip elsewhere does not hold it back. It resolves a repeated digest to the first post in log order, which is also what `CorrectionIndex` and `VerificationProjection` do; withholding the first copy leaves the second served under a digest the digest-keyed readers report as the first's (ruling 18).
13. **R8.78's check is not atomic with the append for the kinds with no gate** (RVO45); tolerance is what makes that harmless, and a digest-keyed gate for every kind is the named follow-up.
