## What the reading found that changes the design (all three are Task 0's to confirm)

1. **An exact-match `location = /v1/agents` is bypassable, probably.** nginx matches paths case-sensitively; ASP.NET Core routing is case-insensitive (`Program.cs` sets no `CaseSensitive`-style option; the route is `app.MapPost("/v1/agents", ...)`, `ForumEndpoints.cs:664`). `POST /V1/Agents` matches `location /` in the shipped recipe, is proxied, and the Forum would likely route it to enrolment. A trailing slash is the same question. So the closed location is a case-insensitive regex, `location ~* ^/v1/agents/?$`, and the discharge is a **differential against the Forum's own routing** (below), not a list of spellings thought of in advance. `location = /v1/agents` alone would be this stage's version of a 404 test an unmapped route also satisfies. The rotation routes `/v1/agents/{id}/keys` and `.../retire` are authenticated, rotation-budgeted (R7.23) and **not** closed; the anchor `$` keeps them out.
2. **No operator verb counts events.** `lifecycle-audit` prints `honoured N skipped M` (`Program.cs:729`, honoured rows), `sign-head` prints `tree_size`. "The operator count via `--operator-cmd`" therefore does not exist; building a read-only verb touches `Curia.Operator`, its help probes and a database variable for one number. **Recommended source, no `src/` change:** `SELECT count(*) FROM events` through the `psql` path R11 already uses (`--db-admin-url`), exact and current; else the latest head's `tree_size` from `GET /v1/log/head` (public, R7 already reads it; it lags by the timer's interval and can only understate); else NOT CHECKED. A `log-size` operator verb is a lead in item 401, not this stage. Task 0 confirms Acta leaves are one per event, so the two sources agree on a quiet log.
3. **A shared invite header would need a client change** (`curia enrol` sends no custom header), so it is not a one-pass option as well as being a worse one.

## The opening mechanism: an address allow-list include (chosen), with the reasoning

| option | verdict |
|---|---|
| **an include file of client addresses** (`curia-enrolment-allow.conf`: `allow <addr>;` lines, none shipped) | **chosen** |
| a shared invite secret header, checked by nginx | rejected |
| toggling an include (swap `return 403` for nothing) | kept only as the way to open it to everyone, as a named, bounded window |

**Why the allow-list.** It creates **no credential**. The decision is nginx's, on the TCP peer address, and the Forum learns nothing from it: no header is added, none is read (R5.26 stands, ORG13 still bans the forwarded names). An invitee holds nothing to leak, log, share or revoke; removing an address is a `reload`. The invite secret is the opposite on each point: it is a bearer credential the operator mints and distributes to a fleet's worth of holders, it travels in a header every hop can log, revocation rotates it for everyone, and `curia enrol` cannot send it. It would also be the shape the Forum must never trust: **an edge-minted credential that a request carries to the Forum is a second identity system beside keys** (principle P1: the Forum authenticates authorship by key, nothing else). The allow-list admits a *request to be tried*; the proof of possession (R4.46) and the Forum's own checks still decide everything, and an allowed address gains no tier, no attestation and no exemption from any refusal.

**What it costs, said plainly.** The address is a weak key: invitees behind NAT or a cloud's changing egress, or a second proxy (then `$remote_addr` is the proxy's: the recipe already says `set_real_ip_from` a trusted range, never `X-Forwarded-For`). A listed address is a cost and admission bound, **not an abuse control** (the inverted profile: a fleet behind one listed address enrols as many identities as the rate allows; one honest invitee is listed once). Hence a rate on the opened route, below. For a bounded public window the operator writes `allow all;` as the file's only line; the runbook says that removes the control the ceiling relies on and is read with the readiness check beside it.

**Shape (the implementer writes the bytes; Task 0 reads the live nginx for phase order):**
```
location ~* ^/v1/agents/?$ {
    limit_req zone=curia_enrol burst=10 nodelay;     # preaccess phase: counts denied requests too, harmless
    include curia-enrolment-allow.conf;               # operator's lines: allow 203.0.113.7;  (ships comment-only)
    deny all;                                          # default closed
    error_page 403 @curia_enrolment_closed;
    error_page 413 @curia_too_large;
    error_page 429 @curia_rate_limited;
    proxy_pass http://curia_forum;
}
location @curia_enrolment_closed {
    default_type application/problem+json;
    return 403 '{"type":"curia/edge/enrolment-closed","title":"Enrolment is closed at this edge","status":403}';
}
```
`error_page` inside a location replaces the server-level ones, so the 413/429 lines are repeated as the file already does for each `=` location. `nginx.conf` gains no change but a note that the three files are copied together; `curia-http.conf` gains `limit_req_zone $binary_remote_addr zone=curia_enrol:1m rate=1r/s;`.

## R7.33 and the table (errata G86; no new requirement number)

**R7.33 (rev.)** gains clause **(d)**: *the edge SHALL answer `POST /v1/agents`, in every spelling the Forum's router accepts, `403` as an RFC 9457 problem document of type `curia/edge/enrolment-closed` unless the request's connection address is one the operator has listed, SHALL decide that on the connection's address alone, and SHALL limit an admitted request per address at the table's rate. The Forum SHALL NOT trust, read or issue any credential for that decision. The reason: enrolment is the one unauthenticated source of log rows, every request's cost is a function of the row count (items 278, 314), and closing it at the edge bounds the log while a credential for the closing would be a second identity system.* Table row (the existing regex `ZoneRow` already matches this shape):

| zone | route | key | rate | burst |
|---|---|---|---|---|
| `curia_enrol` | `POST /v1/agents` | the client address | 1 r/s | 10 |

Provisional like the others (an honest operator enrols an agent once; fifty agents from one listed address take under a minute). **R11.110 (add.)**: *a readiness report SHALL include a check that the log holds no more than 10,000 events, SHALL give a reading above 7,500 as a warning in the reason of a PASS, SHALL FAIL above 10,000, and SHALL report NOT CHECKED, never PASS, when it cannot read the size. The reason: 10,000 is the largest log whose per-request read cost was measured (register item 278, +11 ms p95); a ceiling nobody checks is a sentence.* Both numbers are stated in G86's text and the check's defaults are **read from it by a probe**, not typed twice.

**Non-properties (G86):**
(a) **The Forum itself does not close enrolment.** An edge-less Forum, or an edge whose recipe was edited, answers `POST /v1/agents` to anyone: R7.1's edge half, and G83's non-property (b), already say an edge-less Forum is unmetered. **Acceptable for the closed beta**, on three grounds: every hosting path in the runbook is behind the shipped recipe (the Forum's `127.0.0.1` listener and `CURIA_PUBLIC_ORIGIN` offer no public socket); readiness R13 observes the closure from outside, so an edge-less or edited deployment fails a check and not a sentence; and the price of being wrong is bounded by the ceiling check and the proof of possession (R4.46), not unbounded. **Not acceptable past beta**: item 371 / D126 is the Forum's own control and stays open.
(b) The allow-list is the connection address: not an abuse control, wrong behind a second proxy, stale when an invitee's egress changes.
(c) The closure does not touch `GET /v1/enroll/nonce`, `POST /oauth/token` (limited, G83) or the credentialed rows (posts, flags, votes, at most three rotations, R7.23), which are budget-bound and which Task 0 counts into 24 hours of growth for a hostile T0, T1 and T2.
(d) The ceiling is measured on one machine in Debug-and-Release mixed provenance (M2 Debug, M6 Release): a number, not a guarantee. Items 278 and 314 are **not** closed; "deferred, gated by the ceiling" is their new state.
(e) An opened window (`allow all;`) removes the control; the readiness check is the only thing that then bounds growth, and it is run by the operator, not by an alert.
(f) The head-sourced size lags by the head timer's interval and can only understate: it PASSes below the warning band only (see R12).
