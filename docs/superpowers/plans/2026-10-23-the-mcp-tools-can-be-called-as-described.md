The errata entry it builds, **G27**, is filed in `curia-whitepaper-ERRATA-AND-ADDENDUM.md` in the working tree, uncommitted: the stage's first commit carries it. After filing, `python3 tools/spec-checks/check-spec.py` printed `spec-checks: clean` (exit 0), and `python3 tools/spec-checks/falsify-spec-checks.py` went red on all four checks naming their cell (citation: `cites R11.997`; duplicate: `R11.16 is defined unqualified in both`; index-orphan: `R11.37 is proposed in an entry but absent from the index`; index-phantom: `R4.1 is listed in the index but no entry defines it`), tree untouched.

**Goal:** a model can call every `curia-mcp` tool the way its description and schema say, and is told, by name, when it cannot. Today a call that leaves out an optional argument fails with `An error occurred invoking 'curia_ask'.` and nothing else; a criterion the record does not define is ignored and the model is handed an unfiltered page; a model cannot turn a page or read a reply's question. This stage makes the tool surface keep its own word, and builds the gate that would have said so: a client that speaks the protocol. Errata **G27**: **R11.37**, **R11.38**, **R11.39**, **R14.11**.

**Why this stage and not another.** Asked as an LLM agent using the Forum, and answered by operating it instead of reading it. The last two stages built the MCP write surface (#108, #109) and checked it with facts that call the methods the tools are bound to; the first `tools/call` a model makes had never been sent. I enrolled T0 identities on a local Forum, started the Release `curia-mcp` and called it over stdio JSON-RPC as a host does ("Observed before this plan", below). `curia_ask` without `tags` fails; so do `curia_answer` and `curia_comment` without `refs`, `curia_verify` without `expectedDigest` and `curia_search` without `criteria`: five of eight tools cannot be called without their optional arguments, because the published schema lists every one of them required. `curia_search` silently drops any criterion it does not know, `min_verification` (the spelling its description, R9.25's prose and its own first line use) included, and answers an unfiltered page it calls filtered. A reply given a `board` ignores it. `cursor` is a member no result gives a value for, so a model cannot page. A comment on a comment reads back without its question. Ten live probes, ten red; none of them needs a tier, a clock or a second implementation. That ranks it first, over my own ranking at the end of #109, whose (1) was D54 with `curia_revise`: it adds a ninth tool, and a reader fix, to a surface whose existing eight cannot all be called as described. D10 (the embedding model) would improve the ranking of pages a model cannot turn, behind a `ci.yml` the owner merges. D41 waits for a deployment story, and `curia_publish_finding` for a T2 agent thirty days out. Re-ranked, in "Next stage after this one".

**Scope:** `src/Curia.Mcp/` only: new `ServerComposition.cs` and `ArgumentContract.cs`; `Program.cs`, `ToolCatalogue.cs` (summary, `Version`), `ForumTools.cs`, `WriteTools.cs`, `SearchCriteria.cs`, `ToolText.cs`. Tests: `tests/Curia.Mcp.Tests/` (new `ToolProtocolTests.cs`, `ArgumentContractTests.cs`; `ToolDescriptionTests.cs` strengthened), `tests/Shared/StubLog.cs` (serves a cursor), `tests/Curia.Api.Tests/` (new `McpToolContractEndToEndTests.cs`), `tests/Curia.Architecture.Tests/` (new `McpHostCompositionTests.cs`); docs. **Touches no frozen format, no wire status, no route, no envelope member, no package and not `ci.yml`**: it is an agent-mergeable PR once CI is green. It does change `curia-mcp`'s published tool schemas (the criteria members' spelling, the `required` lists; version 0.5.0), which the alpha direction (`CLAUDE.md`, "Release stage") allows: the Forum holds no state keyed on either, and a model that spelled `minVerification` as 0.4.0 said is refused by name.

SDK mechanics established on a toy server before this plan (`ModelContextProtocol.Core` 2.2.0, the version in `Directory.Packages.props`; a scratch project, not the repo):
- A delegate parameter with a default (`string[]? tags = null`) leaves `required` and gains `"default": null`; `CancellationToken cancellationToken = default` is bound by type and absent from the schema. Without the default the property is `required` whatever its nullability.
- `McpServerOptions.Filters.Request.CallToolFilters` runs before the binder and can answer a `CallToolResult { IsError = true }` itself. A binder failure (missing, wrong type) reaches the model as the bare generic text; a tool's `McpException` reaches it as `An error occurred invoking '<tool>': <message>`, so a named refusal keeps its words.
- `[JsonPropertyName("min_verification")]` on a record property is honoured by the binder and the published schema. Unknown members of an object argument and unknown top-level arguments are dropped without a word.
- `StreamServerTransport` / `StreamClientTransport` over two pipes and `McpClient.CreateAsync` run the real protocol in-process (`tools/list`, `tools/call`) with no subprocess.
- A sketch of the argument checker ran against the SDK's real schema shapes through that in-process pair: unknown top-level and nested members, absent required members, array/string/object/boolean/integer mismatches, `null` for a non-nullable member and a numeric string for an integer all came out named, and an omitted optional passed. `proposed/ArgumentContract.cs` in the architect's scratchpad, intended path `src/Curia.Mcp/ArgumentContract.cs`; it is not analyzer-clean.

## Rulings (curia-architect, 2026-10-23; the errata is G27)

1. **The server is built in one place, and the gate builds it there.** New `src/Curia.Mcp/ServerComposition.cs`: `internal static McpServerOptions Options(ForumTools tools, string? agentId)` holds what `Program.cs:67`-`:78` builds inline today (`ServerInfo` from `ToolCatalogue.Version`; `ServerInstructions` from `ToolText.ServerInstructions(agentId, ToolCatalogue.WriteToolNames(tools))`; `ToolCollection` from `ToolCatalogue.Build(tools)`) and registers ruling 3's filter. `Program.cs` calls it and constructs no `McpServerOptions`. The Mcp and Api harnesses call it too, so what a fact drives is what a host runs, and an Architecture fact reads `curia-mcp.dll`'s IL (Mono.Cecil, as `tests/Curia.Architecture.Tests/McpLifecycleSigningTests.cs` reads it) and holds that `ServerComposition.Options` is the only method that constructs `McpServerOptions`. A harness that builds its own options tests its own options (vacuity question 4).
2. **Optional parameters get defaults, and the defaults are the schema.** `AskAsync` (`WriteTools.cs:34`-`:41`: `tags`, `notDuplicateRationale`), `AnswerAsync` (`:68`-`:70`) and `CommentAsync` (`:77`-`:79`) (`refs`), `VerifyAsync` (`ForumTools.cs:151`-`:153`: `expectedDigest`), `SearchAsync` (`:233`-`:236`: `criteria`; the `ThrowIfNull` at `:236` becomes `criteria ??= new SearchCriteria()`). Each gains `= null`, and `cancellationToken = default` after it (CS1737 otherwise). Every existing caller passes every argument positionally (`ReaderFrameToolTests.cs:225`-`:237`, `PropertyP22ToolResultTests.cs:309`-`:322`, `McpWriteEndToEndTests.cs`), so none changes. `ReadAsync`, `ResolveAsync` and `FlagAsync` need all they take and stay. `tags` stays optional though Table 12 lists it required for a question: the Forum admits a tagless question (the live `curia_ask` with `tags` null posted) and that gap is R8.62's (register D53), not this stage's.
3. **One checker, read from the schema the model was shown, run before the tool.** New `src/Curia.Mcp/ArgumentContract.cs`: `Check(JsonElement schema, arguments, reasonFor)` walks the call against `properties`, `required`, `type` and `items`, depth first, and returns every fault as (path, Unknown | Missing | WrongType, what the schema has there). It admits what the binder admits and no less: a numeric string for `integer` or `number` (observed: `limit:"3"` answers a page), so it is not a stricter rule than the transport's. A fault never carries the received value (R9.25: "the value where naming it echoes no content"). The server filter (`CallToolFilters`, ruling 1) answers, for a call with any fault and before the binder runs, a `CallToolResult { IsError = true }` whose text starts with the fixed phrase `NOT SENT: this call does not match <tool>'s input schema` (a tool's own `NOT SENT:` refusals, for a credential or a reference form, do not), says nothing was sent to the Forum, names each fault's path as a display literal (a `FrameBuilder` string hole already is one, R10.63) and, for an Unknown, the members the schema does define at that level; for a member named in `SearchCriteria.Refusable` it appends that reason (R9.26). It carries no SDK wrapper. A call to a name outside the collection goes to `next`. **Why a filter, and not `[JsonExtensionData]` or `JsonUnmappedMemberHandling.Disallow`:** the binder's exception is swallowed into the generic text, a bag is a second mechanism beside the top-level closure, and one rule closes every tool at every depth (R11.37). It decides nothing about the Forum (R11.16 (rev.)): its only subject is the schema this adapter published. `JsonReaderFenceTests` does not scan `curia-mcp` by decision (its summary); the checker decodes no string it echoes but a name.
4. **The criteria record is spelled as the specification spells it.** `SearchCriteria.cs:37`-`:68` gains `[JsonPropertyName]` on each member: `query`, `kinds`, `board`, `tags`, `author`, `min_verification`, `cursor`, `limit`, `why_ranked` (`kinds` for R9.26's set; `why_ranked` for R9.8). The oracle is not the record: Appendix E's `GET /v1/search` row (`curia-agent-forum-WHITEPAPER.md:4222`) fixes `board`, `tags`, `min_verification`, `cursor`, and G12's table of editorial amendments fixes "the wire spelling is `min_verification` and R9.6's `verification` is the refused spelling". `Refusable` (`SearchCriteria.cs:80`-`:90`) gains `verification`, its reason naming `min_verification`. `Refuse` (`:132`-`:138`) is unchanged: it words a known member given a value the Forum cannot honour. The camelCase spellings 0.4.0 advertised are not kept alive (reading both was refused for `declared_license`, G25 decision 1).
