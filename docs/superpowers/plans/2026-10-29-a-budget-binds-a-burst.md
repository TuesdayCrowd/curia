## What the reading found that the rulings did not know

The architect's rulings (decisions 1 to 6 and "PR 1's scope, precisely") decide the rule. Reading the tree to write this plan found sixteen facts they did not have; each changes a detail and five change how the work is built.

1. **The Postgres leg holds a pooled connection for the whole write, and the gate pool is shared, so two nested holds on one pool deadlock by construction.** The existing gates are transaction-scoped advisory locks: the hold *is* an open transaction on a connection from `_gateDataSource`, a quarter of the Forum's pool (`PostgresAdapters.cs:46-49`, `:107`, `:113`; `PostgresFlagRaiserGate.cs:63-111`, `:130-163`). The agent gate's hold is longer than either (the whole write), and a revision submission holds the agent gate and then the revision gate (`ForumEndpoints.cs:878`). With both on one pool, as many revising agents as the pool holds would each keep a connection and wait for a second: the deadlock G18 built a separate pool to avoid, reintroduced one level up (`PostgresAdapters.cs:92-99` states the argument for flag against Forum). The rulings say "on a pool of its own sized as G18's is"; this plan reads that as **a third data source**, one more quarter, and fixes the order of acquisition as agent pool, then gate pool, then Forum pool (decision 4; BRB35, the nested-hold probe, and FBRB27).
2. **Every write of every agent now draws on a quarter of the Forum's pool for the length of the write.** Before, only flags and revisions did. If the deployed string leaves Npgsql's default of 100, the agent pool is 25 and the Forum can have 25 writes in flight; at a write of tens of milliseconds that is far from binding, at a write of a second it is. The R7.22 fleet fact (`FlagEndpointTests.cs:1020-1075`: Maximum Pool Size=4, Timeout=3, sixteen raisers) is the precedent and has no twin for posts; BRB36 is the twin, and Task 0 measures the ceiling (M5).
3. **The accept route resolves the principal after it reads the log** (`ForumEndpoints.cs:1749` reads, `:1750` calls `PrincipalOf`). The gate is keyed by the principal and the read must come after the hold, so `PrincipalOf` moves above the read; it is pure and its failure (`403`) is unchanged.
4. **Four places say the opposite of the rule and must change in the PR.** R7.26's sentence "The count is not gated: acceptances made at once MAY each read the same count (register D88)"; G46's decision 6 and non-property (a); G45's non-property (a) ("the posting budget is counted before the hold"); and two code comments, `ForumEndpoints.cs:1783-1785` ("the budget is overshot by at most the number in flight, register D88") and `:2729-2732` (`AcceptsInBudgetWindow`: "the one helper an eventual gate (register D88) would call"), and `README.md:633` and `:643` ("does not yet bind simultaneous requests"). BRB55 holds the list as data.
5. **The port takes `AgentId`, not `string`.** The submit route holds `author`, an `AgentId` (`:777`), and the accept route `acceptor` (`:1750`). A `string` parameter would need a reasoned row in `PortStringAllowlist.cs` (the flag gate's is at `:35`, the revision gate's at `:36`); R11.34's boundary types exist so that a port is not given one. The lock key is `agent.Value`.
6. **The method is `EnterAsync`, not `TryEnterAsync`.** The other two gates are "try, never wait" and their fences say so (`RevisionGateFenceTests`); a `Try` that waits would be read as one that does not. The name is the plan's; the architect's text left it open.
7. **The in-memory adapters are test classes** (`tests/Curia.Application.Tests/InMemory/InMemoryRevisionGate.cs`), so a waiting rule written in each adapter would be written twice and could differ. The queue, with its bound, its order and its idle cleanup, is one class in `Curia.Application` (`AgentWriteQueue`); the in-memory adapter is the queue alone and the Postgres adapter is the queue followed by the lock.
8. **A test host's clock cannot fire a timer.** Both `ManualTimeProvider` classes are settable instants that override `GetUtcNow` alone, so they inherit the base class's timers, which run in real time (Task 0 confirms; `tests/Curia.Application.Tests/ManualTimeProvider.cs`; the Api one in `ForumFixture.cs`). The bound must be driven by `TimeProvider.CreateCancellationTokenSource` (CS-9), and the queue's unit facts need a clock whose timers fire when it is advanced; hand-rolled in `tests/Shared` (the scoping document's package table earmarks `Microsoft.Extensions.TimeProvider.Testing` for later and CS-3 is a policy, so no package is added).
9. **The revision gate's in-flight arm becomes unreachable through the real stack.** Only the author of a post can revise it (`RevisesOwnPost`, `:856`), so two revisions of one `prev` are two writes of one agent and the agent gate has serialized them before the revision gate is tried: the second is refused `already-revised`, never `revision-in-flight`. `RevisionOnceEndpointTests.cs:76-99` ("A parked; B 409 revision-in-flight") and the contract facts keep their strength by running the revision gate with a **pass-through agent gate** (a named double); the combination is observed by BRB33. This is vacuity question 3 turned on the gate: an arm that cannot be reached is recorded (open risk 3), not deleted, because the gate is the second line for a request that reaches it some other way (a pre-gate host, a future second writer of the kind).
10. **The cross-process probe in one OS process can pass for the wrong reason.** `forum.WithWebHostBuilder(_ => { })` gives a second host over the same database, each with its own `PostgresAdapters` (`AgentStandingDurabilityTests.cs:103`), so BRB22 exercises the lock leg. But if the in-process queue were a `static`, both hosts would share it and the probe would pass with the lock leg removed. BRB56 fences static state in the gate types, and Task 9 repeats the burst against two real `dotnet` processes on one database.
11. **Waiters hold an admitted body.** ADMIT runs before the gate (`:767`, after the body is copied at `:762-764`), and a body may be up to 1,048,576 bytes (`JsonReader.cs:13-17`), so a full queue is up to 32 MiB per agent for up to the bound. A fleet pays that per identity. The alternative placement, after authentication and before the body is read (`:760`), holds no body but lengthens the hold by ADMIT and ties the gate to a malformed request; it is **not taken** (the rulings say after ADMIT), and is open risk 4 with the number Task 0 measures (M8).
12. **A denied request waits too.** The gate is entered before AUTHORIZE, so a T0 agent sending sixteen parallel `answer` calls (denied by tier) queues its own sixteen. It harms only itself (the key is the agent), costs it the bound, and is told the tier at the end. Recorded as non-property (e).
13. **`ReadEventsAsync` swallows a read failure into an empty log** (`ForumEndpoints.cs:2495-2500`). Under the hold an empty log makes `PostureQuery.Of` fail (no credential events), which is `500` and not a free pass, so no count is read as zero to a caller's advantage. Recorded; not changed.
14. **The wait is added after the proof was validated.** `AccessTokenValidator.ValidateRequestAsync` runs at `:746` (submit) and `:1734` (accept) before the body and before the gate; a request that waits five seconds is not re-validated. Task 0 reads the proof's `iat` window and the token's lifetime (M6) so that a bound longer than either is a finding and not a surprise.
15. **`IngestAttempts` and `AcceptAnswer`'s eight passes stay** (the rulings say so; D89's loop is the second line). Under the hold, one agent's own appends cannot conflict with each other, so the loops now meet only a conflict from outside the agent (a key act on the author's stream for the first; none for the second, which is the asker's own thread). BRB37 and BRB41 hold both halves: the loops stay, and the hold spans every attempt.
16. **Five existing hosts' facts change their object** (RVO's gate facts, `RevisionOnceEndpointTests`; the accept-race facts, `AcceptRaceEndpointTests`; `RevisionRaceEndToEndTests` RVO37 and RVO38, whose words already accept either refusal; the request fuzzer's write exemplars; `StubIngestRefusalFidelityTests` only if a stub is added). Task 0's M18 lists them by running the suite with the gate in; the plan does not guess the set.

## Rulings (decided, not asked)

1. **The rule (the architect's decision 2, confirmed).** One gate per agent, keyed by the **authenticated subject** as the `AgentId` the route already derived from the token (`:777`, `:1750`), never by the envelope's claim, the token's `jti` or the kind of act. One key for the posting count and the acceptance count (a mixed burst is rare and one key is the smaller thing to prove, and BRB23 proves it). It is entered **after authentication, after ADMIT and after `PrincipalOf`, before the first read of the log**, and released after the act has committed or the request has been refused, on every path out (`await using`).
2. **Where, in each route.** Submit: between `:777` and `:783`, so that every one of `IngestAttempts`' three attempts reads its log under the hold (BRB41). Accept: `PrincipalOf` moves above `:1749`, the gate is entered, then the log is read; the hold covers the PDP decision (`:1791`), the target resolution, `RecordAsync`'s eight passes (`:1855`) and the receipt. The order of gates is always the agent gate, then (for a revision) the revision gate (`:878`, try-only), then the Forum's reads; flags are not gated by it (BRB38, BRB51).
3. **The queue (confirmed, with the plan's additions).** In memory, first come first served (BRB3), at most 32 waiters per agent per process, each waiting at most 5 seconds from its arrival; entries are dropped when idle (BRB8); a waiter whose request is cancelled leaves at once and frees its slot (BRB6); a timed-out waiter frees its slot (BRB5). **Both numbers are starting values** that Task 0 confirms against the measured write time by one criterion: with `p95` the 95th percentile of the write at the largest log size M3 measured, under the load of M3, `32 x p95 <= wait / 2`; if the starting pair fails it, the waiters are lowered to `floor(wait / 2 / p95)` or the wait raised to `2 x 32 x p95`, whichever the clients' timeouts (M6) allow, and R7.27's two numbers are amended in place, dated. A change to either is not a change to the rule. The numbers are written once in `src/` (`AgentWriteGateBounds`) and are pinned to R7.27's text by BRB47, not the reverse.
4. **The lock leg and the pools.** The permit holder, and only it, opens a connection on the **agent pool** and takes `pg_try_advisory_xact_lock` on `AgentWriteLockKey(schema, agent)`; a failed try is retried every 20 ms (a starting value, M12) on the same connection and transaction until the bound set at arrival runs out; the connection open is bounded by the same deadline. **One deadline governs a request**: expiry in the queue or in the lock retries is `agent-in-flight` (another write of this agent holds it, in this process or another); expiry or failure in opening the connection, a pool timeout or a driver error is `gate-unavailable` (the store, not the agent). A request is answered within the bound plus one database round trip whatever else happens (BRB11's upper bound is twice the bound, so a doubled bound is red). Order of acquisition: agent pool, gate pool, Forum pool; no hold is requested in the opposite order (BRB35, FBRB27).
5. **What a loser is told.** The budget refusal, in nearly every case, because it is the truth: the burst waits its turn, the winners take the slots, each later request reads a count that includes them, and is refused `403` `table-11/rate-budget-exhausted` or `table-11/accept-budget-exhausted` exactly as the sequential request is (BRB16, BRB17, FBRB16, FBRB17). `agent-in-flight` is the answer only to a request that waited the whole bound or found the queue full; it says to send again; nothing was counted, stored or spent. **Costs to an honest parallel agent, stated:** the last of N waits about N writes; which of N simultaneous requests takes the last slots is the order they reach the gate, not the order sent; a batch wider than 32 or slower than the bound sees `agent-in-flight` for its tail, and loses nothing by it. **Cost to other agents: none** (BRB21).
6. **Release.** After PERSIST (or `RecordAsync`) has committed or refused, and on every other path (BRB32). The vector indexing that follows PERSIST (`:1013-1021`) stays **inside** the hold unless Task 0's M4 shows indexing is more than a third of the median write, in which case the release moves to after the append commits (the count needs only the append); the decision is recorded in this plan with the measurement, BRB31 is written for the chosen release point, and FBRB49 is the row for the other.
7. **The revision gate, `IngestAttempts` and the accept loop stay** (finding 9, finding 15). The revision gate is the second line; its facts run with the pass-through double; the observable combination is BRB33 and BRB34. Nothing in this PR deletes either loop (FBRB38).
8. **Failure modes.** A gate whose store cannot be reached is `503` `curia/budget/gate-unavailable`, nothing counted or written, served without a detail (a 5xx is served by `ServerFault`, `:2775`) and never read as an entry (principle P6: fail closed on the write path; FBRB29). A request refused before the count (ADMIT `400`, authentication `401`, `PrincipalOf` `403`) never enters (BRB28; FBRB34). A client that goes away leaves the queue (FBRB35).
9. **The clients (R11.64).** `ForumResult.Summary` gains an arm for each type, before the generic arms, shared by `curia` and `curia-mcp`: for `agent-in-flight`, that nothing was recorded or spent, that the act may be sent again, that it is neither a tier denial nor a spent budget, and the bound; for `gate-unavailable`, that the Forum could not take the act and nothing was recorded, and that it may be sent again. The CLI's exit 3 entry names `agent-in-flight` beside the other retryable conflicts (`Help.cs:295-299`); the MCP tools relay it through `Refused` (`WriteTools.cs:564-566`). `curia help` and the five write tools' descriptions state the bound, that one agent's simultaneous writes are processed one at a time in the order they reach the Forum, and that a parallel batch must not assume an order. **No client retries by itself** (BRB45): a hidden loop would defeat the bound.
10. **Version.** `curia-mcp` 0.8.11: no tool is added; a refusal's words and five descriptions change. Task 0 re-reads the pins of 0.8.10 (`AcceptBudgetToolTests.cs:113`, `AcceptTheTextToolTests.cs:316`, `RevisionRefusalToolTests.cs:140`, `README.md:705`, `CLAUDE.md:86`, `ToolCatalogue.cs:41`) and nothing that parses a version.
11. **Lessons of PRs 1 to 3 after the eighth exercise, applied (traps 48 to 57).** (a) *Pin published words and numbers to the errata, never to production constants:* Table 11's three posting limits are parsed from the white paper by `PublishedTable11` (linked into the Api suite), the acceptance limits from R7.26 by `PublishedAcceptBudget.Numbers()`, the bound, the queue, the two types, the statuses and the client words from R7.27 and R11.64 by `PublishedBudgetGate`; no BRB probe reads `TierPolicy`, `AccessPolicy` or `AgentWriteGateBounds` for an expectation (BRB48 scans the new files for them). (b) *Each falsification row's first patch is the harm* (the defect, the tempting fix or the realistic wrong turn), and a gentler form is named where one exists and was not used. (c) *A fact that could read a fixed list where a case may be added is data-driven:* the tiers and widths are a grid, the kinds are drawn from Table 10's create rows, the write paths are found by the call closure from the persist and record calls (BRB51), the write tools are the catalogue's tools whose descriptions carry a budget sentence (BRB44), the stale sentences are a list the fact reads (BRB55), the lock keys are enumerated by reflection (BRB13). (d) *The oracle is the events table*: `post.accepted` events whose actor is the agent and `answer.accepted` events whose `accepted_by` is the asker, inside the trailing 24 hours, counted by the fixture's helper (the shape of `CountEventsAsync`, `ForumFixture.cs`), against the limit parsed from the published text; never an HTTP status, never a response's claim about itself. (e) *A SQL oracle never rebuilds a connection string from a data source* (it drops the password, and CI uses SCRAM): every Api fact that reads the table uses the connection string the fixture holds, verbatim. (f) *Build first, then test `--no-build`*, as CI does, for every baseline and comparison (the previous PR's ruling 24).
12. **A control must see the bug.** Every burst probe has a counterpart that overshoots when the gate is a pass-through (BRB20, deterministic with the parked append), and Task 0 records the unmodified tree's overshoot for the same grid as the baseline the probes must beat. A probe that cannot overshoot with the gate removed carries no information (vacuity question 1).
13. **Nothing in this PR is an owner item.** Not `ci.yml`, not a frozen format (a gate, two problem types and wording are not R15.1's set; the log and the payloads are untouched), not Table 10 or 11 (their numbers are untouched; R7.27 is a rule about when they are counted), not the lifecycle guard.

## Register text to paste

> **D88 — closed by the "A budget binds a burst" PR (errata G48: R7.27, R11.64).** Both write paths enter one gate per agent, keyed by the authenticated subject, after authentication and ADMIT and before the log is read, released after the act has committed or been refused: simultaneous requests by one agent each count the acts of the ones before them, so the budget the Forum states is the budget it enforces for a burst as for a sequence. The wait is in memory (first come first served, at most 32 waiters per agent per process, at most 5 seconds, both provisional and set by Task 0's measurement), followed by a Postgres advisory try-lock on a pool of its own for a second Forum process; a request that waited and then found the budget spent is told the budget, and one that waited the whole bound or found the queue full is told `409` `curia/budget/agent-in-flight`, nothing counted, stored or spent; an unreachable gate is `503` `curia/budget/gate-unavailable`. Measured on the unmodified tree: 32 stored against 25 (T1), 7 against 3 (T0) and 11 acceptances against 10 (T0) in the ninth exercise; after, the grid of BRB18 and BRB19 holds the database count at the limit in every repetition. Flags and revisions keep their try-only gates (D61 item 46). Probes BRB1 to BRB56, falsification FBRB1 to FBRB50 (see "As run").
>
> **Trap 58.** A check and the act it governs were two steps, and every probe was sequential. The count was correct, the append followed, and a request in flight saw the number the one before it was about to change. The probe that carries information parks one request between the check and the append, asserts what the other has read and stored while it waits, and counts the events table; the control is the same interleave with the gate removed, which must overshoot.
>
> **Trap 59.** Two nested holds on one pool. A gate that holds a connection for the length of a write, entered before a gate that holds another, deadlocks a pool exactly as large as the number of agents in flight. The probe that carries information shrinks the pool to the size at which nesting needs more than it has (Maximum Pool Size=4 gives a gate pool of one), so that the deadlock is by construction and not by load.
>
> **Trap 60.** A cross-host probe in one process can share what it was meant to separate. Two hosts built from one factory in one OS process pass a cross-process test if the in-process state is static. The fact that carries information fences static state in the gate, and the live leg runs two real processes.
>
> **Trap 61.** A refusal arm that no request can reach. With the agent gate in front, the revision gate's `revision-in-flight` cannot be reached through the real stack (only the author revises, and the author is serialized). The arm stays as the second line and its facts run with a pass-through double; the observable combination is `already-revised`. When a new gate makes an old gate's refusal unreachable, say so, and keep a way to see the old one red.

## Open risks (named so the reviewer can look)

1. **The pair (5 s, 32) is a guess until M3.** The criterion in ruling 3 decides it; R7.27's numbers are amended in place if it fails. A write of 200 ms at the largest log makes 32 waiters 6.4 s, which is why the criterion is `32 x p95 <= wait / 2`.
2. **The agent pool caps concurrent writes across all agents.** At the default pool of 100 that is 25 writes in flight; M5 compares it with the unmodified ceiling. If it binds, the agent pool is sized larger than a quarter (a one-line change and a recorded one), not the gate removed.
3. **R8.77's in-flight arm is unreachable through the real stack** (finding 9, trap 61). Kept as the second line; its facts use the double. Retiring the revision gate is a lead for after the exercise, not this PR.
4. **Waiters hold an admitted body.** Up to 32 MiB per agent for up to the bound. M8 puts a number on it; the alternative (the gate before the body is read) is recorded and not taken because it lengthens the hold by ADMIT and ties it to a malformed request. Reopen if M8 shows a fleet of 100 agents costs more than the Forum can spare.
5. **A denied request waits** (finding 12). Harms only its sender. Reopen if a transcript shows an honest agent's denied calls delaying its permitted ones; the remedy is to enter the gate only for a request the tier can permit, which needs the PDP before the gate and is the thing the architect rejected.
6. **A host's timeout shorter than the bound.** A tool call that times out client-side after the Forum has stored the act is a lost receipt, not a lost act; M6 reads the defaults, and the bound is lowered if they are below twice it.
7. **Ordering is arrival at the gate.** A parallel batch that assumes its order is recorded in the order it was sent will be wrong (non-property (a)); the descriptions say so (BRB44).
8. **One database, one gate.** The advisory lock is per database (`PostgresFlagRaiserGate`'s remarks); a Forum with replicas on one database is covered, one with sharded databases would not be and has no deployment story in this project.
9. **About fifteen facts change their object.** The risk is a fact weakened instead of retargeted; each is named in its commit, the revision gate's facts keep their strength by running with the double, and Task 6 compares the whole suite with the baseline.
10. **Identifiers are provisional** (see the top): G48, R7.27, R11.64, D90, the two types, 0.8.11, BRB, FBRB, traps 58 to 61.
