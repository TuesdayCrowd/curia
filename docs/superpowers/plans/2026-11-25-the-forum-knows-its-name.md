## What this is

**The defect as filed (D41, found 2026-10-12 by the review of the rotation stage's PR 0; extended by the enrolment PR).** Three sites build "the URL this request was sent to" from the request itself, `{Scheme}://{Host}{PathBase}{Path}`: the token endpoint's expected `htu` and the client assertion's expected `aud` (`TokenEndpoint.TokenEndpointUrl`), the resource server's expected `htu` (`ForumEndpoints.AbsoluteUrl`, six `IncomingRequest` sites), and, since errata G79, the enrolment proof's `aud`, which `EnrollAgent`'s route takes **from `TokenEndpoint.TokenEndpointUrl`** (a builder named for the token endpoint, called with the enrolment request). A fourth, `ReaderContractUrl`, builds the Reader Contract URL that every provenance envelope carries from the same `Host`. D41's probe (a token request signed for `another.example` and relayed under that `Host` answers `200`) was re-measured by the enrolment stage for the enrolment route (LEP10: a relayed proof under its own `Host` answers `201`), so the relay works on three routes and the readers' served URL follows the `Host` too. Beside them the access token's `iss` and `aud` and the authorization-server metadata come from `Curia:Issuer` and `Curia:Audience`, which **fall back silently to `https://forum.local`** (`Program.cs`, `TokenIssuer`): a Forum started without them mints tokens for, and publishes a `token_endpoint` at, a name nobody chose, while its `htu` checks answer to whatever `Host` arrives (the test host does exactly this: tokens say `https://forum.local`, requests say `http://localhost`, and nothing notices, which is the same vacuity as D29's helper).

**Item 374.** `AllowedHosts`, the only mitigation D41 had, answers a foreign `Host` with an HTML `400` before any Forum code, so `curia` prints `curia/client/unreadable-problem`, the request fuzzer's oracle ("every refusal a problem document", R14.10) never sees it (the fixture sets none) and the mitigation ships a refusal outside the Forum's contract. **Item 376's FEPP5c** is the falsification row that built the enrolment route's `aud` from a copy of the URL logic and survived, because the copy equals the original on every request the suite sends (none has a `PathBase`, a foreign `Host` or a scheme other than the fixture's).

**The closure.** One configured public origin, read at start and failing loudly, replaces `Curia:Issuer` and `Curia:Audience` (owner-accepted recommendation, ruling 1) and is the only source of the name: every `htu`, every `aud`, the token's `iss`, the metadata and the Reader Contract URL are built from it and the request's path. The request's `Host`, scheme, path base and forwarded headers are read for none of them (so no forwarded-header trust is needed), a build-failing fence holds that, and the Forum refuses a request whose `Host` is not its own with a problem document of its own (item 374). `AllowedHosts` stays unset (ruling 4).

**Class:** a rule decided at one layer and read at another (trap 299's shape again, here between a configuration and a request), plus a **masked-control hazard** this plan found in its own design (ruling 5): a Host refusal and an `htu` binding that each stop the relay probe alone would leave the binding unprobed. The probes this plan needs are the kind the project has paid for: red on today's tree by their own assertion, discriminating between the two controls, and derived from an artifact other than the one they check (the client's own URL builder, the errata's grammar, the IL).

## Rulings (decided, not asked)

1. **One setting replaces `Curia:Issuer` and `Curia:Audience`; it does not derive them** (the recommendation, accepted). `Curia:PublicOrigin` (environment fallback `CURIA_PUBLIC_ORIGIN`, the order every sibling uses: configuration key, then variable) holds the Forum's one name. The access token's `iss` and `aud`, the metadata's `issuer`, `token_endpoint` and `jwks_uri`, `AccessTokenValidationContext`'s two fields, the token endpoint's and the resource server's `htu`, both `aud`s and the Reader Contract URL all come from it. `iss` equals `aud` because the issuer is co-hosted (TokenIssuer's own remarks); **a split issuer host would need a second setting and its own entry, and is not made configurable here** (lead A). **A key the build no longer reads must not be silently ignored:** a `Curia:Issuer` or `Curia:Audience` present in configuration refuses the start, naming `Curia:PublicOrigin` (ORG3). Alpha: an older token (`iss`/`aud` the old default) is refused after a restart; a token lives 300 seconds.
2. **The setting is the bytes, and the start refuses rather than normalises.** Every comparison downstream is ordinal, and the client signs what `System.Uri` makes of the dialled URL, so the origin is a string both ends must spell identically. The start refuses unless the value **is** its own canonical form: scheme `http` or `https`; host ASCII and lower-case, with no trailing dot; the scheme's default port omitted and any other port numeric; no userinfo, path (a trailing `/` included), query or fragment; the refusal names the canonical form it would have accepted (`Curia:PublicOrigin must read exactly "https://forum.example"`) and quotes the offending value as a display literal and not as markup. A non-ASCII host is refused (configure the A-label); **T0-3 measures what `Uri.ToString()` makes of an A-label and of an IPv6 literal, and if the client's signed form differs from the canonical spelling for either, that form is refused outright and says so.** A silent canonicaliser would make the configuration say one thing and the Forum another, which is D41's own shape. `http` is accepted for a local Forum and for a TLS-terminating front (the scheme is configured, never read from the request).
3. **Nothing in the request names the Forum.** One builder, `PublicOrigin.UrlOf(HttpRequest)`, returns `origin + request.Path` (no query, no fragment) and serves the token endpoint's `htu` and `aud`, `AbsoluteUrl`, and the enrolment route's `aud` (so the `TokenEndpointUrl` name that misdescribes the third use goes: **FEPP5c's copy has nothing left to copy**). `ReaderContractUrl` is `origin + ReaderContract.WellKnownPath`. `request.Path` stays as today's decoded path, and the `%2F` against `%252F` caveat of `KeyRouteValues`' comment is unchanged and bounded as it was (non-property (g)). **The request's `Host`, `Scheme`, `PathBase` and every forwarded header are read by no Forum code except the Host refusal's one comparison and `KeyRouteValues`' strip of a path base from the raw target** (a reasoned fence row, because that read is for routing identity, not for a name). The fence is IL (`Curia.Architecture.Tests`, ORG13, both configurations), the project's idiom for "a new line that does this fails the build".
4. **The Forum refuses a foreign `Host` itself; `AllowedHosts` stays unset and unread** (the recommendation, accepted). A middleware, first after `UseStoreFaults` (it reads no store), compares the request's `Host` with the origin's authority: the host without regard to case, an absent port equal to the origin scheme's default port and an explicit default port equal to none; anything else is refused `400` with the problem type `curia/request/host-not-served`, title "The Forum is not served under this name", **no detail, and nothing of the request in the body or any header**; at `/oauth/token` it is RFC 6749's `{"error":"invalid_request","error_description":<the title>}` as `UnreadableRequests` writes it (R11.33). **No route is exempt, `/health` and the Reader Contract included**: a readiness check that works under any name would pass while every real request is refused, and one that must send the Forum's name is the check that the Forum and its proxy agree (the runbook, PR O, says so). `400` and not `421`: Kestrel's own filter answers `400`, no client here retries on `421`, and nothing turns on it. The refusal does **not** name the origin (the Forum telling an agent where to go is a redirect an intermediary could abuse; the owner who configured the URL has it). `AllowedHosts` set by an operator still answers its HTML `400` before this check; that is the operator's, the hosting runbook says so, and the Forum neither requires nor reads it (lead B).
5. **The Host refusal must not mask the binding.** If the middleware alone stops D41's relay, then restoring `request.Host` in `TokenEndpointUrl` leaves every probe green, which is trap 299's lesson and FSRS11's: a second line that hides the first. So **the binding's probes use `Host` spellings the middleware admits and the origin does not spell** (ORG6b: the case variant; ORG6c: the explicit default port; ORG5: the Reader Contract URL under the case variant; ORG7: a scheme the origin does not have; ORG8: a path base; ORG9: forwarded headers), and FORG1, FORG2, FORG3 and FORG4 are expected red there and FORG5 (the middleware removed) is expected to leave ORG6a's relay still refused, by the binding, **and is recorded as the evidence that each control stands alone**. T0-2 settles that the framework passes these spellings through unnormalised; if it normalises one, that probe is replaced by the next spelling and the plan says which.
6. **The Forum is served at its origin's root; a path base is not part of the name.** The origin has no path and the client cannot dial under one (`new Uri(base, "/x")`). **T0-5 measures whether a path base can be set by configuration or environment at all; if it can, the start refuses a non-empty `PathBase` setting naming this rule and ORG8 becomes that refusal; if it cannot, ORG8 is the probe that a test host with `UsePathBase` is still answered by the origin's name** (a proof for `origin/oauth/token` honoured, one for `origin/forum/oauth/token` refused). The ruling is conditional on T0-5 by design, and the amendment says which branch ran.
7. **The origin is resolved eagerly.** `Program.Build` resolves `PublicOrigin` right after `Build`, beside `ILifecycleAppendGate`, so a missing or malformed value stops the start and no request is ever served without a name. ORG1 asserts the failure at host construction, before a request, which a lazy singleton would fail only at the first request (FORG20). The message names `Curia:PublicOrigin` **and** `CURIA_PUBLIC_ORIGIN`.
8. **Every fixture's base address equals the configured origin** (D41's own sentence), and the conversion is made harmlessly first. `ForumFixture` gains a virtual `PublicOrigin` (default `http://localhost`, what `TestServer` dials and what the 253 literals already say) and sets `Curia:PublicOrigin`; **Task 2 does this on the unmodified Forum, which ignores the key**, so the whole suite stays green and ORG15 can be written against it. > ## G82 — The Forum knows its own name: one configured origin is what every `htu`, `aud`, `iss` and served contract URL is built from, the request's `Host`, scheme, path base and forwarded headers name nothing, and a request that is not addressed to the Forum is refused by the Forum
>
> **Location.** R5.1 (the assertion's `aud`), R5.2 (tokens audience-restricted to one resource server), R5.13 (the one validation module, its `htu` check), R5.19 and R4.46 (the enrolment proof's `aud`), R10.21 (the Reader Contract's well-known URL), R11.33 (a request a route cannot read), R7.1 (the edge half), R14.10 (the fuzzer's oracle); errata D29's closing note in the A series ("the token endpoint takes that `htu`'s host ... from the request's `Host` header ... the register's D41", superseded here, not edited), G79 non-property (n); register defect D41, items 374 and 376 (the FEPP5c survivor), 293 and 375 (annotated).
>
> **How it surfaced.** D41 was found on 2026-10-12 by the review of the rotation stage's PR 0: a token request signed for `another.example` and sent under that `Host` was honoured by a Forum whose own configuration said `https://forum.local`, because the expected `htu` and `aud` were rebuilt from the request. The enrolment stage added a third site (the enrolment proof's `aud`) and measured the same relay on it (LEP10), found that `AllowedHosts`, the only mitigation, answers a foreign `Host` with an HTML `400` outside the Forum's contract (item 374), and recorded that a falsification row that built the enrolment `aud` from a copy of the URL logic survived (item 376's FEPP5c) because no request the suite sends has a `Host`, scheme or path base other than the fixture's. This stage's reading found that the reader-contract URL every provenance envelope carries is built from the same `Host`, that a Forum started without `Curia:Issuer` and `Curia:Audience` mints tokens and publishes a `token_endpoint` for `https://forum.local`, and that the test host does exactly that beside requests addressed to `http://localhost`, which is why no probe could notice. [Task 0 T0-1, T0-2 and T0-12 set the final wording of this paragraph.]
>
> **Argument.** An audience binding exists to stop a credential made for one place being used at another (R5.1's own reason). It can do that only if the Forum compares the credential with a name the Forum holds; compared with a name the request supplies, the check asks the caller what the caller meant, and a relay that signs for itself and forwards under its own name is answered. The old comment's argument, that a configured value would "pass if the Forum were reached through an unexpected host", has it backwards: a proof made for an unexpected host is a proof made for another origin, and refusing it is the binding. The remedy is one configured origin, read at start and refused when absent or ambiguous, from which every compared URL is built with the request's path and nothing else; the request's `Host`, scheme and path base are then not inputs, so a TLS-terminating proxy needs no forwarded-header trust and a header a proxy adds can move nothing. The Forum also refuses a request addressed to a name it does not serve, in its own words, because the framework's filter answers in HTML and a refusal the fuzzer's oracle never sees is outside the contract; **that refusal is not the control**: the binding must hold on a `Host` the refusal admits (the same host in another case, an explicit default port) in a spelling the origin does not use, so the two are separate facts with separate probes. A signed post names no Forum (Table 9); what stops a relay moving an agent's post into another Forum is that Forum's token for the author, which this entry binds to that Forum's origin.
>
> ### Requirement text
>
> **R5.26** The Forum SHALL hold exactly one public origin, configured and never derived from a request, and SHALL build from it and from the request's path alone every URL a credential is compared with: the `htu` of a DPoP proof on the token endpoint and on every resource route, the `aud` of a client assertion (R5.1) and the `aud` of an enrollment proof (R4.46); SHALL issue access tokens whose `iss` and `aud` are that origin and accept no other (R5.2); and SHALL state it as the `issuer` of its authorization-server metadata and as the origin of the Reader Contract URL every provenance envelope carries (R10.21). The request's `Host`, scheme, path base and any forwarded header SHALL NOT be read for any of them, and a comparison against the origin's URL SHALL be exact. The reason: a credential compared with the name the caller supplies is compared with nothing, and a name the Forum was never told is a default somebody else chose.
>
> **R5.27** The Forum SHALL refuse, before any route is selected and on every route without exception, a request whose `Host` is not the origin's authority (the host compared without regard to case; a port equal to the origin scheme's default being the same as none): with status `400` and a problem document of type `curia/request/host-not-served` carrying no detail and no value of the request, or, at the token endpoint, RFC 6749's `invalid_request` object with the same title (R11.33). It SHALL NOT rely on the framework's host filtering, which answers in HTML. The refusal SHALL NOT be what makes R5.26 hold: the binding SHALL refuse a credential made for a spelling of the Forum's own host that the origin does not use, on a `Host` this check admits. The reason: a request addressed to another name cannot carry a credential made for this one, and saying so in the Forum's own words costs a caller one request; but a second control that stops the probe hides whether the first one works.
>
> **R11.109** The Forum SHALL NOT start without its origin: it SHALL read it from `Curia:PublicOrigin`, then `CURIA_PUBLIC_ORIGIN`, before it serves a request, refuse an absent or empty value naming both, and refuse any value that is not an `http` or `https` origin in its canonical form (lower-case ASCII host, no trailing dot, the scheme's default port omitted, no userinfo, path, query, fragment or trailing slash), naming the canonical form and quoting the value as text. It SHALL NOT read `Curia:Issuer` or `Curia:Audience`, and SHALL refuse the start naming `Curia:PublicOrigin` if either is set. The reason: a default is an origin nobody chose, a value the Forum silently corrects is a configuration that says one thing and a Forum that does another, and a key the build has stopped reading and does not mention is the quietest way for a deployment to keep a name the Forum no longer uses.
>
> **R4.46 (rev.)** The enrollment proof's `aud` is "the absolute URL of the enrollment route as the Forum names itself (R5.26)", and not "as the Forum received it". **R5.1 (add.)** The token endpoint URL an assertion's `aud` must match is the origin's (R5.26). **R10.21 (add.)** The well-known URL at which the contract is retrievable, as every provenance envelope serves it, is the origin's.
>
> ### Non-properties (stated so that no later reading takes them for guarantees)
>
> (a) **A signed post names no Forum.** Table 9 has no audience, forum or origin member, so a post is attributable to its author and not to the place it was written for; what keeps another Forum from receiving it from a third party is that Forum's token for the author (R5.26's `iss`/`aud`), and a Forum's own operator can append a copy of a post it holds to its own log. A `forum` member is a format change and is a lead (register A to E), not a precondition of hosting. (b) **The origin is only as right as the operator's setting.** The start validates form, not reachability or ownership: a Forum configured with a name nobody dials refuses every request `host-not-served` and mints tokens for a name nobody signs, loudly, and nothing in the Forum can tell it is mis-named. (c) **A TLS-terminating front keeps the origin `https` over an `http` listener**, and must forward the `Host` it received; a proxy that rewrites `Host` to its upstream makes every request `host-not-served`, loudly. The Forum reads no scheme and trusts no forwarded header. (d) **`AllowedHosts`, if an operator sets it, answers an HTML `400` before this entry's refusal**; unset is the supported configuration, and the Forum neither reads nor requires it (register lead B). (e) **One origin is the issuer's and the resource server's**: `iss` equals `aud`; a split issuer host would need a second setting, and none is built (lead A). (f) **No path prefix.** The origin has no path and `curia` cannot dial under one; a path base is not part of the name, and [T0-5's branch is stated here: either the start refuses a configured path base, or a test host with one is still answered by the origin's name]. (g) **The decoded-path caveat is unchanged**: the `htu` is the origin and the decoded request path, so a proof still replays between `%2F` and `%252F` spellings of one path, bounded as `KeyRouteValues` says. (h) **A `Host` that matches proves nothing**: the check refuses names that are not the Forum's and authenticates no one. (i) **IDN and other non-canonical spellings are refused at start**, not mapped. (j) **Item 293 and 375 stand as the owner ruled on 2026-11-24:** the hosted instance makes no claim that enrolment is non-repudiable, a backdated root still buys tenure and a root planted before an identity enrols still squats it, and a signed enrolment root is built before any hosting that claims otherwise. (k) **Tokens minted before this build are refused** (their `iss`/`aud` are the old default); they live 300 seconds. (l) **The request fuzzer varies `Host` and does not vary a forwarded header**, which no Forum code reads (the fence is what holds that).
>

**#5. The IDN decode: the comparison reads the header as received.**

*The measurement.* On Kestrel, `Host: xn--bcher-kva.example` arrives as `Request.Host.Value = Host.Host = "bücher.example"`; `ToUriComponent()` and the raw header stay `xn--bcher-kva.example`. `Request.Host` is `HostString.FromUriComponent(header)`, which decodes an A-label to Unicode; `Host.Host` for IPv6 also keeps the brackets and the port is separate (`Host: [::1]:5000` gives Host `[::1]`, Port 5000). Every fixture and every ORG probe is ASCII, so **a middleware comparing `Request.Host.Host` or `.Value` passes the entire suite** and refuses every request of a Forum whose origin is an A-label (ruling 2 tells the operator to configure the A-label).

*The rule (R5.27's comparison, exact).*
```
wire = request.Headers.Host                 // the header as received: no HostString, no decoding
served = wire.Count == 1
      && ( wire[0] equals origin.Authority            , OrdinalIgnoreCase
        || origin.PortIsSchemeDefault
           && wire[0] equals origin.Authority + ":" + origin.DefaultPort , OrdinalIgnoreCase )
```
`origin.Authority` is the canonical origin's text after `://` (host, then `:port` only when not the scheme's default; an IPv6 literal bracketed). **No member of `HttpRequest.Host` or `HostString` is read** (`Host`, `Value`, `Port`, `ToUriComponent`, `Equals`); no decoding, no trailing-dot removal, no trimming. A missing header, an empty value, two values, `a,b`, a space, a trailing dot, a user-info `@`, and a U-label all fail the equality and are refused `host-not-served`. Kestrel's own 400 for the malformed ones (`a,b`, `a@b`, `a b`, two headers, HTTP/1.1 with no `Host`, raw Latin-1) comes first and is the first line of defence, not this one; TestServer passes `a,b` through, so the same rows reach the middleware in process.

*Why the raw header and not `ToUriComponent()`.* Both survive the IDN trap. The raw header is chosen because (a) it is what the client sent, so "exact" means exact; (b) `ToUriComponent()` would map a U-label on the wire to the origin's A-label and admit a spelling the origin does not use, which this entry's argument says the Forum should not do; (c) it is **immune to a forwarded-headers middleware**: `ForwardedHeadersMiddleware` rewrites `Request.Host` from `X-Forwarded-Host` (when an operator's code enables `XForwardedHost`) and leaves the header alone, so any compare through `Request.Host` would read a forwarded value, which R5.26 forbids. The fence reads this as: `HttpRequest.get_Host`, `get_Scheme`, `get_PathBase` and every `HostString` member are banned in `Curia.Api`'s IL **with no row for the middleware** (it does not call them); the middleware's row is `IHeaderDictionary.get_Host`; and `KeyRouteValues`' row is `HttpRequest.get_PathBase`.

**#6. The trailing-dot and userinfo rules are explicit and each has its own probe, because the client cannot see them.**

- T0-3: `Uri` normalises case, default ports, `127.1`/`0x7f.1`, IPv6 zero-runs and hex case, a trailing slash, a query and a fragment (each fails the round trip, so the round trip refuses them); it does **not** normalise a trailing dot (`forum.example.`) or userinfo (`u@forum.example`), and both pass the round trip. So **R11.109's grammar is checked by the parser itself and the round trip is a second, independent check**: both must pass. The grammar, written out so the parser has no judgement to exercise: scheme `http` or `https`; host one of (a) DNS labels of `[a-z0-9-]`, 1 to 63 each, none starting or ending with a hyphen, joined by single dots, total at most 253, **no trailing dot**; (b) four decimal octets without leading zeros; (c) a bracketed IPv6 literal whose text equals `Uri`'s own rendering; **no `@` anywhere in the authority**; a port, if present, 1 to 65535 without leading zeros and not the scheme's default; nothing after the authority.
- Added to the grammar by this ruling (the plan's list did not name them): the DNS label alphabet (T0-3 measured `http://forum_x.example` as accepted by the round trip; an underscore is not a host name, and an operator who typed one has a Forum nobody can reach: refused), and **a value that carries `@` is never quoted in the refusal.** The plan said every refusal "quotes the offending value as a display literal"; a configured `https://svc:s3cret@forum.example` would put a password in the start log, which is the R10.27 shape. The refusal says "the value has a user or password part" and names the canonical form of the *rest* only when that rest is computable without the userinfo; it quotes nothing of that value.

Rows owned by the grammar alone: trailing dot, userinfo (`u@`, `u:p@`, `:@`), underscore, a trailing-dot host with a port. > ## G82 — The Forum knows its own name: one configured origin is what every `htu`, `aud`, `iss` and served contract URL is built from, the request's `Host`, scheme, path base and forwarded headers name nothing, and a request that is not addressed to the Forum is refused by the Forum
>
> **Location.** R5.1 (the assertion's `aud`), R5.2 (tokens audience-restricted to one resource server), R5.13 (the one validation module, its `htu` check), R5.19 and R4.46 (the enrolment proof's `aud`), R10.21 (the Reader Contract's well-known URL), R11.33 (a request a route cannot read), R7.1 (the edge half), R14.10 (the fuzzer's oracle); errata D29's closing note in the A series ("the token endpoint takes that `htu`'s host ... from the request's `Host` header ... the register's D41", superseded here, not edited), G79 non-property (n); register defect D41, items 374 and 376 (the FEPP5c survivor), 293 and 375 (annotated).
>
> **How it surfaced.** D41 was found on 2026-10-12 by the review of the rotation stage's PR 0: a token request signed for `another.example` and sent under that `Host` was honoured by a Forum whose own configuration said `https://forum.local`, because the expected `htu` and `aud` were rebuilt from the request. The enrolment stage added a third site (the enrolment proof's `aud`) and measured the same relay on it (LEP10), found that `AllowedHosts`, the only mitigation, answers a foreign `Host` with an HTML `400` outside the Forum's contract (item 374), and recorded that a falsification row that built the enrolment `aud` from a copy of the URL logic survived (item 376's FEPP5c) because no request the suite sends has a `Host`, scheme or path base other than the fixture's. This stage's reading found that the reader-contract URL every provenance envelope carries is built from the same `Host`, that a Forum started without `Curia:Issuer` and `Curia:Audience` mints tokens and publishes a `token_endpoint` for `https://forum.local`, and that the test host does exactly that beside requests addressed to `http://localhost`, which is why no probe could notice. Operating the unmodified build (Task 0, T0-1, T0-2, T0-5, T0-12) measured it: a token request, a resource request and an enrolment, each signed for `another.example` and sent under that `Host`, answered `200`, `200` and `201`, while the same proof under the honest `Host` was refused (`401 curia/authn/url-mismatch`) and an honest `Host` with a foreign `htu` was refused (`400 invalid_dpop_proof`); the authorization-server metadata and every minted token carried `https://forum.local` under every `Host`; the relay worked on real sockets whenever it forwarded the `Host` unchanged; and `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`, the framework's own door, changed the scheme of every compared URL (`X-Forwarded-Proto: https` gave `https`), so the Forum's name followed whatever a proxy said. It also measured the framework's reading of the header that this entry must not repeat: Kestrel hands the code `Request.Host` with an internationalized name **decoded** (`Host: xn--bcher-kva.example` arrives as `bücher.example`) while the header itself is unchanged, so a comparison made through `Request.Host` would refuse every request of a Forum whose origin is an A-label, and no fixture in the suite uses one.
>
> **Argument.** An audience binding exists to stop a credential made for one place being used at another (R5.1's own reason). It can do that only if the Forum compares the credential with a name the Forum holds; compared with a name the request supplies, the check asks the caller what the caller meant, and a relay that signs for itself and forwards under its own name is answered. The old comment's argument, that a configured value would "pass if the Forum were reached through an unexpected host", has it backwards: a proof made for an unexpected host is a proof made for another origin, and refusing it is the binding. The remedy is one configured origin, read at start and refused when absent or ambiguous, from which every compared URL is built with the request's path and nothing else; the request's `Host`, scheme and path base are then not inputs, so a TLS-terminating proxy needs no forwarded-header trust and a header a proxy adds can move nothing. The Forum also refuses a request addressed to a name it does not serve, in its own words, because the framework's filter answers in HTML and a refusal the fuzzer's oracle never sees is outside the contract; **that refusal is not the control**: the binding must hold on a `Host` the refusal admits (the same host in another case, an explicit default port) in a spelling the origin does not use, and must honour a credential made for the origin's own spelling under those same `Host`s, so the two are separate facts with separate probes. The refusal compares the header **as received**, not a parsed or decoded form of it: what arrived is what is compared, and a name the origin does not spell is not the Forum's name however the framework would read it. A signed post names no Forum (Table 9); what stops a relay moving an agent's post into another Forum is that Forum's token for the author, which this entry binds to that Forum's origin.
>
> ### Requirement text
>
> **R5.26** The Forum SHALL hold exactly one public origin, configured and never derived from a request, and SHALL build from it and from the request's path alone every URL a credential is compared with: the `htu` of a DPoP proof on the token endpoint and on every resource route, the `aud` of a client assertion (R5.1) and the `aud` of an enrollment proof (R4.46); SHALL issue access tokens whose `iss` and `aud` are that origin and accept no other (R5.2); and SHALL state it as the `issuer` of its authorization-server metadata and as the origin of the Reader Contract URL every provenance envelope carries (R10.21). The request's `Host`, scheme, path base and any forwarded header SHALL NOT be read for any of them, and a comparison against the origin's URL SHALL be exact. The reason: a credential compared with the name the caller supplies is compared with nothing, and a name the Forum was never told is a default somebody else chose.
>
> **R5.27** The Forum SHALL refuse, before any route is selected and on every route without exception, a request whose `Host` header is not the origin's authority: with status `400` and a problem document of type `curia/request/host-not-served` carrying no detail and no value of the request, or, at the token endpoint, RFC 6749's `invalid_request` object with the same title (R11.33). The header SHALL be compared **as received**: exactly one value, equal to the origin's authority ASCII case-insensitively, a port equal to the origin scheme's default being the same as none; no internationalized name is decoded, no trailing dot is removed, and an absent, empty or repeated header is refused. The comparison SHALL NOT read the framework's parsed `Host` (which decodes an internationalized name and, where a forwarded-headers component is configured, is replaced by a forwarded value) and SHALL NOT rely on the framework's host filtering, which answers in HTML. The refusal SHALL NOT be what makes R5.26 hold: the binding SHALL refuse a credential made for a spelling of the Forum's own host that the origin does not use, on a `Host` this check admits, and SHALL honour a credential made for the origin's own spelling on that same `Host`. The reason: a request addressed to another name cannot carry a credential made for this one, and saying so in the Forum's own words costs a caller one request; but a second control that stops the probe hides whether the first one works.
>
> **R11.109** The Forum SHALL NOT start without its origin: it SHALL read it from `Curia:PublicOrigin`, then `CURIA_PUBLIC_ORIGIN`, before it serves a request, refuse an absent or empty value naming both, and refuse any value that is not an `http` or `https` origin in its canonical form: a host that is DNS labels of lower-case letters, digits and hyphen with no trailing dot, or a dotted-decimal IPv4 address, or a bracketed IPv6 address in its canonical rendering; the scheme's default port omitted; no userinfo, path, query, fragment or trailing slash. The refusal SHALL name the canonical form when it can be stated without the offending part, and SHALL quote the value as text **except a value that carries a userinfo part, which it SHALL NOT quote at all**. It SHALL NOT read `Curia:Issuer` or `Curia:Audience`, and SHALL refuse the start naming `Curia:PublicOrigin` if either is set. The reason: a default is an origin nobody chose, a value the Forum silently corrects is a configuration that says one thing and a Forum that does another, a key the build has stopped reading and does not mention is the quietest way for a deployment to keep a name the Forum no longer uses, and a refusal that echoes a configured password into the start log has made the log a credential store.
>
> **R4.46 (rev.)** The enrollment proof's `aud` is "the absolute URL of the enrollment route as the Forum names itself (R5.26)", and not "as the Forum received it". **R5.1 (add.)** The token endpoint URL an assertion's `aud` must match is the origin's (R5.26). **R10.21 (add.)** The well-known URL at which the contract is retrievable, as every provenance envelope serves it, is the origin's.

> ### Non-properties (stated so that no later reading takes them for guarantees)
>
> (a) **A signed post names no Forum.** Table 9 has no audience, forum or origin member, so a post is attributable to its author and not to the place it was written for; what keeps another Forum from receiving it from a third party is that Forum's token for the author (R5.26's `iss`/`aud`; a token minted under one origin is refused `401 curia/authn/issuer-mismatch` by a Forum configured with another, measured), and a Forum's own operator can append a copy of a post it holds to its own log. A `forum` member is a format change and is a lead (register A to E), not a precondition of hosting. (b) **The origin is only as right as the operator's setting.** The start validates form, not reachability or ownership: a Forum configured with a name nobody dials refuses every request `host-not-served` and mints tokens for a name nobody signs, loudly, and nothing in the Forum can tell it is mis-named. (c) **A TLS-terminating front keeps the origin `https` over an `http` listener**, and must forward the `Host` it received; a proxy that rewrites `Host` to its upstream makes every request `host-not-served`, loudly. The Forum reads no scheme and trusts no forwarded header; a proxy that rewrites `Host` was, before this entry, answered `401 curia/authn/url-mismatch` by a client whose proofs named the public name. (d) **`AllowedHosts`, if an operator sets it, answers an HTML `400` before this entry's refusal**; unset is the supported configuration, and the Forum neither reads nor requires it (register lead B). (e) **One origin is the issuer's and the resource server's**: `iss` equals `aud`; a split issuer host would need a second setting, and none is built (lead A). (f) **No path prefix.** The origin has no path and `curia` cannot dial under one. The Forum has no configuration or environment setting for a path base (measured: `ASPNETCORE_PATHBASE`, `ASPNETCORE_APPL_PATH` and `PATHBASE` change nothing, in a real process and in process), so none is refused; a host built in code with a path base is answered by the origin's name and the path alone: a credential for `origin/oauth/token` is honoured at `/forum/oauth/token` and one for `origin/forum/oauth/token` is refused, and the Forum reads no forwarded prefix. (g) **The decoded-path caveat is unchanged**: the `htu` is the origin and the decoded request path, so a proof still replays between `%2F` and `%252F` spellings of one path, bounded as `KeyRouteValues` says. (h) **A `Host` that matches proves nothing**: the check refuses names that are not the Forum's and authenticates no one. (i) **Internationalized and other non-canonical spellings are refused, not mapped**: at start (configure the A-label), and on the wire (a `Host` that spells the origin's host as a U-label, or with a trailing dot, is refused `host-not-served` even though it names the same host). (l) **The request fuzzer varies `Host` and does not vary a forwarded header**, which no Forum code reads (the fence, and the two forms of the forwarded-headers probe, are what hold that).
