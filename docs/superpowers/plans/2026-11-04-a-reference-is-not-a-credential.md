## What the reading found that the ruling did not know

1. **The scanner reads six views of one text, and a text is refused if any view refuses.** `ContentScreener.Detect` runs `SecretScanner.Scan` over the original, `despaced`, `unmarked-up`, `unconfused`, each decoded base64 run and `rot13` (the `line-joined` view runs `ScanShapes`, which reads neither rule). `unmarked-up` deletes `*`, `_`, `` ` `` and `~`, so `$DB_PASS` is `$DBPASS` there and `****` is nothing. A predicate probed against the original alone proves nothing about the screen. The identity view is strict ASCII, so a reference that is one only after a fold is refused by the original; the other direction (a reference that stops being whole in a view) is what the per-view sweep (RNC2) holds. Names are letters, digits and underscores. `rot13` preserves them and `unmarked-up` deletes the underscores: Task 0 M1 measured `password=${A_}` as `password=${A}` there, refused through that view though the first wording of R10.96 called it a reference, so the name class is stated on what survives the deletion (ruling 15). The sixteen forms' names (`DB_PASS` to `DBPASS`) survive.
2. **The pattern, not the rule, chose the token's end, and a whole-token test on it refuses the commonest case.** The keyword rule's value class is `[^\s;"']{4,}`, so `` `--password=$DB_PASS` ``, `(password=$DB_PASS)`, `**password=$DB_PASS**` and `password=$DB_PASS.` are one longer token each, and "whole" cannot be "the value". The rule is: a reference, then nothing or closing characters only (`` ` * ~ . , ) ] } > ! ? ``, the characters Markdown and prose put against a word, none of which a name holds; `*` and `~` and the backtick because `unmarked-up` deletes them). This is the finding that changes the ruled mechanism: without it the exercise's own body passes and every Markdown-quoted reference is still refused.
3. **Two of the ruling's forms are already quiet.** `{{ db_pass }}` with blanks is cut at the first blank and never reaches the four-character floor (only `{{db_pass}}` matches), and the URI rule's password class excludes `:`, so `postgres://u:${DB_PASS:-hunter2}@h` is not matched at all: a default that carries a live value is a **false negative today**, in the URI form only. The first is a control row (quiet before and after), the second a known evasion; the ruling's "no `:-default`" binds the keyword form alone.
4. **`password` is read in one form only.** `password="hunter2x"`, `password: hunter2x` and the JSON `"password": "hunter2x"` are quiet (a quotation mark is excluded from the value's first character; `:` is not `=`; the high-entropy rule's keyword list has no `password`). It predates this PR, goes the other way (a miss, which the screen's own comment calls the unrecoverable direction), and is **not changed here**: tightening it refuses every YAML schema and every `password: <string>`, a decision of its own. It is filed as a lead and its rows enter the known-evasions list (ruling 11). **For the owner's awareness: this is the larger hole in this rule than the one the PR opens.**
5. **A reference can be put in front of a value.** The URI class stops at `@`, so `postgres://u:$DB_PASS@u2:hunter2@h/db` is matched at its first `@`; a parser that splits userinfo at the last `@` reads the password as `$DB_PASS@u2:hunter2`. ## What this loosens, judged as a defender and as an agent

**What now gets through, and what it costs.** (1) A live password that is, whole, an upper-snake `$NAME`, `${NAME}` or `%NAME%`, or four or more `*`, or a `<name>` or `{{name}}`, optionally followed by closing punctuation: stored. A generated password is whole one of these with a probability of the order of 10^-8 at sixteen characters (94-character alphabet, derived, not measured), so the case is a person who chose `$HUNTER2` or `<hunter2>` and wrote it into a connection string; they have shown the Forum a name, which the same post would have shown anyway. (2) `Pwd=C:\...` where the password is a drive-letter path: stored; vanishingly rare as a password, and the working directory's name is the keyword's commoner use. (3) What is **not** admitted: any value, a lower-case name after a sign, a name with a suffix, a default (`${NAME:-x}` in a keyword), a reference with letters after its punctuation, a reference followed by a second `@` in a URI, and anything the other seven rules read (a vendor prefix in the username position, a JWT, a PEM block, a long assigned run), in any of the six views. (3a, Amendment 2) A reference that is a run of `*` followed by a separate word (`password=**** EXAMPLE...`) is stored, as `password=$DB_PASS EXAMPLE...` always was; a reference followed directly by `"`, `'` or `;` is stored whatever follows; a three-asterisk mask followed by a word is refused. (4) The screen's own comment names a false negative as the unrecoverable direction, and this PR moves against it on purpose, on a bounded predicate whose admitted set is tested from the corpus in both directions and recorded as evasions; it is reversible by deleting the predicate.

**As an agent.** The refusal of a reference is the worst case the screen has: every observed refusal of this class (four observations: M14, Task 8, F1, R8) was of text with no secret in it, the advice was to rotate a credential that did not exist, and an instruction that is wrong every time it is seen is an instruction that stops being followed on the day it is right (R10.27's rotation advice is the screen's one remedy; a screen that trains its readers to ignore it has removed the remedy as surely as a leak). The ruled forms are what agents write (`$DB_PASS` in the contributor's and the reproducer's bodies; `<password>`, `{{db_pass}}` and `****` in documentation). What the predicate does not clear (`$password`, `YOUR_PASSWORD`, `changeme`, `REDACTED`, lower-case names) is refused as before, and is the likeliest next sighting: the sentence turns that refusal into a one-step rewrite instead of a guess about which line to drop (the contributor's words), and the two commonest are kept as known false positives, which fails the build if the predicate ever clears them by accident. **R10.x on what the screen must never miss:** R10.25 lists connection strings with embedded passwords; R10.26's reason is that nothing is redactable afterwards; R10.11 says a rate is not safety. None is weakened for a **value**: every value-shaped password, including `$ecret1` and `Secr3t`, is refused in every view, and the plan's positives are the proof (RNC3 to RNC8), built first.

## Rulings (decided, not asked)

1. **Where it lives.** In `Scan`, by code, over each match; no new pattern, no change to a pattern's text, span or floor. The predicate is applied to both keywords' alternatives and to the URI form, in every view `Scan` runs in, and not in the line-joined view, which does not read the rules.
2. **The forms.** As R10.96: `$NAME`, `${NAME}`, `%NAME%` (NAME: `_*[A-Z][A-Z0-9_]*` holding at least two characters that are not underscores, so a letter first once any underscores are passed; ruling 15); `<name>` and `{{name}}` (name: `_*[A-Za-z][A-Za-z0-9_.-]*`, so at least one character that is not an underscore and a letter first once any underscores are passed; ruling 15); four or more `*`; then nothing or closing characters. **Not widened:** lower-case names after a sign, bare `NAME`, `changeme`, `secret`, `REDACTED`, `[REDACTED]`, `xxxx`, `...`; the corpus holds no body of real passwords and no body of placeholders large enough to separate them, so the narrowest predicate that clears the ruling's negatives is the rule. **Task 0 may narrow** the name class of `<name>` and `{{name}}` where the corpus separates a positive from a negative (a rule it records as a dated ruling), and never widens it.
3. **The closing set** is `` ` * ~ . , ) ] } > ! ? ``, derived from what prose and Markdown put against a word and from the characters `unmarked-up` deletes; none is in a name. A reference followed by a letter, a digit, `_`, `:`, `=`, `/`, `-` or a quotation mark is not whole.
4. **The `@` read.** A reference clears a URI match only where, from the end of the match to the first of `/`, `?`, `#` or a blank, there is no `@`. Linear: a match consumes its own `://`, so reads do not overlap.
5. **`pwd`.** R10.86's position rule and leading-character exclusions unchanged, and a value that begins `[A-Za-z]:[\\/]` is a path and not a password (D61 item 37's second form; the ruling was silent). Only `pwd`: the keyword is the working directory's name; `password=C:\...` is a value.
6. **The username is not a password.** `postgres://admin:$DB_PASS@h` is stored; `postgres://$DB_USER:EXAMPLE-NOT-A-REAL-SECRET@h` is refused.
7. **The words.** "Rotate it" stays in every refusal (R10.27); R11.84's sentence is added, for `ConnectionStringPassword` only, in both clients, from one definition; the Forum's `422` words are unchanged and a hand-built client sees no sentence about references (a recorded non-property).
8. **The description and the help** carry one sentence from the same definition. `curia-mcp` 0.10.2.
9. **Sizing.** Live run: six legs (below). Cold read: needed, four readers (the sentence is new words an agent acts on, and the harm it could do, an agent re-spelling a real value as a name, is the thing to look for), not ten.
10. **Corpus placement.** Ten rows that stay refused to `payloads.jsonl`; sixteen that clear to `benign.jsonl`, each with a value of at least four characters so that the unmodified rule refuses it (the row is red before the change); `password=changeme` and `password=$password` to `known-false-positives.jsonl` (they stay refused, and the file fails the build if one stops); five rows to `known-evasions.jsonl`. 12. **The version** is the build day's date, written into G60, `SecretScanner.Version` and TRW35's object in one commit; the history line says which rule changed and that nothing stored is rescreened.
13. **Cost.** Two rules derived in Task 0 before they are measured (M7); the scaling row runs alone in Release.

### Rulings

15. **(2026-11-04, M1; the report's ruling 15, decided the other way.) R10.96's name class is closed under the markup view's deletion.** The report proposed to leave R10.96's "at least two characters" as written and record `${A_}` as a non-property. That leaves a requirement that says `${A_}` SHALL NOT be reported and a screen that reports it: the spec and the build disagree about a form, and the corpus could never hold the sixteen forms and this one at once (vacuity question 4: the claim and the check would come from different readings). Ruling: the class is stated on what survives the deletion. `$NAME`, `${NAME}`, `%NAME%`: NAME is upper-case letters, digits and underscores, with at least two characters that are not underscores, a letter first once any underscores are passed (`_*[A-Z][A-Z0-9_]*`). `<name>`, `{{name}}`: at least one character that is not an underscore, a letter first once any are passed (`_*[A-Za-z][A-Za-z0-9_.-]*`). So `${A_}`, `%X_%`, `$_1X`, `{{_}}` and `<_1>` are not references, in the original and in the view alike, and the first non-underscore being a digit is the same defect the report found by length (`$_1X` is `$1X` in the view, which does not begin a name).
