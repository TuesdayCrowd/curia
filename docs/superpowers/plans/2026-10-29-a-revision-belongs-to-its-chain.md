## Rulings (decided, not asked)

1. **The placement rule (D85; the architect's decision 4, made exact).** A post of kind `revision` is a member of a thread exactly when `ChainRootOf(post)` is a member of it, the thread rooted at the revision itself excepted (the requested root is always listed). Every other post is a member when its `parent` is, a revision counting as a member of the threads this rule gives it, so a comment on a revision lands where the revision does. One forward pass still suffices: the chain root is older than the revision (its digest is in the revision's signed `prev`). **Membership is computed on all the log's posts, before the route's serving filter**, so a withheld hop does not detach what is placed by it (the route's own comment says a reply to a withheld post is still the reply its author signed). The chain root is `CorrectionIndex.ChainRootOf`, R8.75's rule, not a second copy.
2. **The cases.** (a) *An answer's revision*: in the answer's thread (the question's), whatever its `parent` says. (b) *A question's revision*: in the question's thread, which is the thread rooted at the question; it can never be accepted (the accept route refuses it, R8.75, and `ThreadOf` is `null`), so it carries no `thread` line. (c) *A comment's revision*: in the comment's thread. (d) *A revision whose chain root is itself* (its `prev` names no stored post, or a post of another author; **the third form, "something R9.28 does not call a predecessor", is struck by ruling 19: any post of the revision's own author is one**): **in no thread but the one it roots.** The architect's text lists it "with the chain root's own thread" (a comment's, a question's), which describes (b) and (c); for (d) the root is the revision, which has no thread of its own, and the fallback to `parent` is the author's word for exactly the posts the chain cannot vouch for. It stays on its board, in search and by its id. Table 10 and ingest refuse a stranger's revision and a dangling `prev` (PK4, PK7 seed them through the store seam), so (d) is a log this code did not write. **Measured (M3, ruling 19): the route stores none of the (d) forms and answers each `403` `own-resource-only`, so (d) is reachable only in a log this code did not write.** (e) *LP2*: a revision of a comment with the right `prev` and a `parent` that names no post is in its comment's thread, which it never was. (f) *A prev cycle or a repeated digest in a log this code did not write*: `ChainRootOf` ends the walk at the first post seen twice; the thread route neither hangs nor throws (CHN8).
3. **The author's `parent` is printed and ignored.** Every reader prints it as the author's word, escaped, as it prints every field; G38's recorded non-property (the Forum does not compare a revision's `parent` or a post's board) stands, and adds "and does not use it". Ingest keeps storing a lying revision (CHN13): refusing it would make the field's meaning a rule, and the Forum's answer to a field it cannot trust is to ignore it. **Amended 2026-10-29 (ruling 19):** measured, it is stored for a `parent` that is another thread's question, another own post, a digest string, `not-an-id` and a well-formed id no post bears; CHN13 uses all five.
4. **Logs that already hold lying parents need nothing.** `Thread` is a pure function of the events computed per request (R11.9); no read model stores a placement, so there is no migration, no event written and nothing to replay differently. The next read after the change lists LP1 with its chain (EQ5's count goes from 2 to 3) and not under EQ6 (4 to 3), and LP2 in its comment's thread. The thread route serves no validator (`ETag` is on the single read, per post, and is unchanged); Task 0's M1 confirmed it (no validator header on the thread route). **The facts that pinned the old listing change their object, never their strength:** PK34 now asserts the stranger's thread does not hold RL, the true thread does and marks it accepted, the true question names it; PK34b's crafted acceptance recorded under the stranger's question still marks RL accepted in no thread, now read through the true thread and the listing asked for at the answer. Each change is named in the commit that makes it, and PK34's message is corrected to say what it asserts.
5. **`curia_read`'s walk is left, its guard is pinned, and the consequence is stated.** The client cannot learn a revision's chain root from the post it holds without reading the chain, and it already refuses to present a listing that does not hold the post. So `curia_read` of a revision whose `parent` lies prints `NOT READ` and the post alone, with the reason ("the thread the Forum served did not include the post"), which is the truth of a post whose author named a thread it is not in; before the change it printed `thread root=EQ6 posts=4` beside a stranger's question. For LP2 the walk's existing `CUT` line ("the parent ... could not be read") is unchanged. The honest revision is unaffected (`curia revision` and `curia_revise` write the revised post's id as `parent`, `WriteTools.cs:160`). Recorded non-property (c); CHN20 holds both halves and FCHN20 removes the guard. Reopen on evidence that an agent needs a lying revision read in its true thread.
6. **The `thread` line for a revision (R10.87).** `Passage` gains one definition keyed by kind: for `revision`, `accepted as the text of the answer it revises, by the asker of that answer's thread` followed by the same parenthesis (`(the Forum's word: no signature covers an acceptance, and it checks nothing about the answer)`); for every other kind the constant is byte for byte what it is. `AnswerStanding.Basis` keeps being cut from the parenthesis. The line form, the titled index and the screen's header call the one definition; the statement is a code span in R10.87 and the probes read it from there.
7. **A listing asked for at a revision or an answer is the subtree under that id.** The thread rooted at LP1 holds LP1 and what is placed under it (a comment on it), and not the later revisions of its chain (they are placed by their root). This narrows what the route gave an honest chain (a later revision, whose `parent` was the earlier one). No reader asks for it; CHN7 pins it so a change is deliberate. Recorded in the entry's "What this costs".
8. **D86(a), the refusal (R11.62).** The success sentence is rewritten from the reads the walk made: it names the question by its post id (unchanged), then states the question's standing from the question's own `superseded_by` (the revisions, each by post id or digest; FORKED for two or more; the same core as the receipt's note), then states the named revision's: that it is the latest the Forum reports (an empty list) or the revisions that supersede it (a non-empty one; an absent list is `NOT STATED`). **The remedy stays "answer that question instead", because the original is the only legal parent; the sentence now also tells the agent which text stands, so that an agent that answers the original knows what it is answering and can say so in the body.** The hedge `may itself have been revised` is deleted. No read is added; the bound of eight is unchanged; the fixed-words failures are unchanged and state no standing (CHN25). The core is one function shared with the receipt (`Supersession`); the receipt keeps its tail (CHN24).
9. **D86(b), the first block.** After the root line, in the branch that already writes the `accepted` line (the thread read and not cut), a `revision` line in the passage's own words: `SUPERSEDED by ...` with FORKED for two or more, `NOT STATED` for a list the Forum did not serve, and nothing for an unrevised root (the passage's convention: silence for none; CHN28 holds both the silence and the `NOT STATED`, so the silence is not a probe that cannot fail). It is written from `top`, the root the walk reached, never from the post that was read (CHN27 reads through a non-root post). For a superseded root it also names `the text that stands`: starting at the root, follow each successor digest to the member of the thread that bears it, recursing through that member's own `superseded_by`; a member with an empty list is a head, a member with an absent list is `NOT STATED`, and a digest no member bears says so ("leads outside what this thread holds") and claims no head; a fork names every head and picks none. **Amended 2026-10-29 (ruling 20):** the realistic fork has a branch the Forum does not serve: its digest is in the root's list with no post id and no member of the thread bears it, so the line names the served heads, says that digest leads outside what the thread holds, says FORKED and picks none (CHN57). Any depth; the bound is the member count.
