## Rulings (curia-architect, 2026-10-24; the errata is G28)

1. **The line form states an acceptance, once, in the frame, and only when true** (R10.79). `Passage.Render` writes one line `thread    <AcceptedStatement>` between the `forum` line (`Passage.cs:136`-`:138`) and the `CONTRADICTED`/`reproduced` lines (`:143`-`:146`) when `Post.Accepted`; `TitledIndex.Write` writes `   <AcceptedStatement>` beneath a row's first line (`TitledIndex.cs:57`). `AcceptedStatement` is a public constant of `Passage`: `accepted by the thread's asker (the Forum's word: no signature covers an acceptance, and it checks nothing about the answer)`. `PassageHeader.cs:173` uses it, so the screen's H6 changes from `accepted (the Forum's word: ...)` to the constant, and `R10_74_AcceptedIsTheForumsWordAndOnlyInH6` (`tests/Curia.Client.Tests/ScreenModelTests.cs`) moves with it (alpha: output is not a compatibility surface). *Why the longer words.* A reader is a context window, and the author of a hostile answer can ask the question it answers and accept it; "accepted" must be read as a claim about the asker, never about the answer, and R10.50 forbids a badge. The statement contains none of `verified`, `correct`, `trusted`, `endorsed`, `true`; a fact holds that. A post the Forum does not serve as accepted gets no line: absence is silence, not "none accepted" (`ForumDocuments.cs:185`-`:191` already reads an absent member as false). A screen's list rows (`src/Curia.Client.Cli/Screen/IndexRow.cs:11`, which writes `TitledIndex.Write`'s first line only) are unchanged: R10.79 excepts them, because the header of the opened post states it (R10.74).
2. **`curia_read` states the resolution on the line after the root line, when the root line is written** (R11.41). `ForumTools.ReadAsync` (`:116`-`:184`), in the branch that writes `thread root=` (`:168`-`:171`), adds `accepted answer=<id> (<AcceptedStatement's parenthesis>)` for the thread's members with `Accepted`, or `accepted none (the Forum served no post of this thread as accepted)`. Ids are display literals through `FrameText` like every id in the frame. More than one accepted member (a Forum fault: the fold keeps one per thread) lists each. Where the result says `CUT` or `NOT READ`, the block states nothing of resolution: the accepted answer may be above what is shown, and "none" would be a guess.
3. **A dropped item is counted where it is dropped, and the count reaches the frame** (R8.66; D54 and D53's count). `PostEnvelope` gains trailing `int DroppedRefs = 0, int DroppedCodeBlocks = 0` after `DuplicateRationale` (`PostEnvelope.cs:72`); `ReadRefs` and `ReadCodeBlocks` return the kept items and the dropped count (array length less kept; a non-object item is dropped; a member present and not an array is one dropped; absent is zero), and `Read` passes both at `:235`. No refusal and no rule in `Read` (R8.64 decision 3): D53's refusal stays R8.62's. `Passage.Render` prints the existing `refs` and `code` lines unchanged when nothing was dropped (`ReaderContractTests.cs:79` pins "NOT FETCHED"), and `refs      <n> reference(s) inside the block below, <k> NOT READ. NOT FETCHED, ...` when something was; when `n` is 0 and `k` is positive the line is written anyway (today it is not: `:151`). `code` likewise. The screen's header does not print refs today and is not touched.
4. **`curia_revise` takes the post it revises and the revision's words, and nothing it could get wrong** (R11.40). `ReviseAsync(string postId, string body, string? title = null, string[]? tags = null, string[]? refs = null, CancellationToken cancellationToken = default)` in `WriteTools.cs`, defaults per G27 ruling 2 so `required` is exactly `[postId, body]`. Order: parse `refs` through `ReferenceForms` first (a bad value is `NOT SENT`, nothing read); `_forum.GetPostAsync(postId, _marking, ct)` (a refusal is `Refused`); `PassagesAsync([post])` (`ForumTools.cs`, which also `Remember`s it for R11.29); if `passage.Outcome` is not `Verified` (the rule `RevisedDigestAsync` applies at `Program.cs:353`-`:358`, span check included) throw `NotSent` worded as the CLI words it, with `passage.DescribeRead` as an `OwnText`; else `prev = passage.Verdict.PrefixedDigest`, `Board = post.Board`, `Parent = post.PostId`, `Kind = Revision`, and only the `title`, `tags`, `refs` the caller gave; sign and submit through `SubmitAsync` (`resource = ResourceKind.Revision`, `ActionKind.Create`). The Forum decides ownership (R11.16 (rev.)): a stranger's call is refused by the Forum with `table-10/own-resource-only` and the adapter words it by cause (D51), never as a tier. `Posted` (`WriteTools.cs:211`) gains a `prev` line when `draft.Prev` is set. No `prev`, `board`, `parent` or `revision_reason` parameter: the first three are refused by name by R11.37's closure, and `revision_reason` is unenforced (G11 decision 3; R8.62). The description (`ToolText.ReviseTemplate`, composed like its siblings with `TierSpan.For(ResourceKind.Revision, ActionKind.Create)`, which R11.36 makes state "own") says: the original stays served and citable and is reported superseded; nothing is inherited, so pass `title`, `tags` and `refs` again; the board is the post's. `SignedAndPermanent` (`ToolText.cs:129`) becomes "only superseded by a revision (see curia_revise)" in plain text, not backticks: `R11_26_EveryParameterADescriptionNamesIsOneItsSchemaDefines` holds backticked identifiers to schema properties and would read a tool name as one.
